**عرض تجريبي مباشر: <https://enterprise.aiworkin.com>**

مشروع مفتوح المصدر يدمج وينقل **منصة عمل خدمات المؤسسات** (Hono + Prisma + MySQL + Next.js / Ant Design) مع **التواصل الاجتماعي للأعمال SNS**
(العلاقات / المنشورات / المجموعات / الرسائل الخاصة / السيرة الذاتية / ساحة العرض والطلب / التوظيف).

إنه ليس أداة أحادية، بل قاعدة كاملة لـ «الإدارة الداخلية للمؤسسة + استقطاب العملاء الخارجي + الوساطة التجارية»: فوق نظام الحسابات والهويات،
يستقبل الزائر أولاً **الصفحة الرئيسية للموقع** (`/`، صفحة هبوط لغير المسجلين، أعلاها تسجيل الدخول / التسجيل فقط)، ثم يدخل إلى قمرة القيادة، و21 مدخلاً لمنصة العمل (مهامي، Agent، سير العمل، قاعدة المعرفة، Workbuddy السحابي، الجداول متعددة الأبعاد، RPA، إنشاء المحتوى، أدوات التسويق،
الأصول الرقمية، بريد الذكاء الاصطناعي، CRM، BI، OA، OKR، خدمة العملاء بالذكاء الاصطناعي، منصة الموارد البشرية، إدارة المشاريع، المخزون والمبيعات، مركز التطبيقات، قاعة الموضوعات)،
و11 خط خدمة أعمال (التسويق / التوريد / الضرائب / التوسع الخارجي / العمل المرن / الخدمات اللوجستية / تقنية المعلومات / الملكية الفكرية / القانون / مراكز الفكر / تداول الأصول)، والتواصل الاجتماعي للأعمال والتوظيف،
إضافة إلى لوحة إدارة للمنصة منظمة في 5 تصنيفات و26 قسماً (نظرة بيانات المنصة مدمجة في قمرة القيادة `/dashboard`). جميع قدرات التواصل الاجتماعي والعرض والطلب **حلقة محلية مغلقة، قابلة للاستخدام دون مفتاح** ؛
عند الحاجة إلى النشر لسوق المنبع (AIworkin) للطلبات / الخدمات، وإعداد ملفات المؤسسة وطلب المؤهلات، يكفي ربط مفتاح AIPDD APIKey
——**هذا النظام لا يتعامل بالعملات المشفّرة، ولا يستضيف حسابات المنبع، وكل الأنماط والتفاعلات أعيد كتابتها محلياً**.

> راجع التصميم ومواصفات النقل في [`docs/开源版整体设计方案.md`](docs/开源版整体设计方案.md).

## 📸 معاينة الواجهة

> الصور التالية مأخوذة من الموقع التجريبي <https://enterprise.aiworkin.com> (من منظور المسؤول الأعلى، وعلى اليسار قائمة «منصة العمل / خدمات الأعمال»).

**منصة Agent**: المحادثة تُنتج صوراً / مقاطع فيديو مباشرة؛ وتغطي التبويبات المحادثة والمهام المجدولة والمساعد والنسخة الرقمية والمهارات والخبراء وموصل MCP (بوابة تفويض «الإجراءات القابلة للتنفيذ التلقائي» معلّقة تحت تبويب موصل MCP).

**أدوات التسويق**: الاستقطاب والوصول وأدوات البيانات معروضة على شاشة واحدة، وكل بطاقة تحمل شرحاً ومدخلاً مستقلاً (استقطاب بالذكاء الاصطناعي: رادار العملاء المحتملين → الوصول → ملف العميل → سيناريو المبيعات → المتابعة → فحص الجودة واللوحة؛ والجمع والوصول ينفذهما إضافة AIPDD Enterprise؛ SCRM لـ WeCom: مزامنة العملاء الأصلية، الإرسال الجماعي بتأكيد بشري، SOP، الشريط الجانبي للموظف، الكلمات الحساسة وفحص الجودة بالذكاء الاصطناعي؛ الربط بالمؤثرين، الاتصال الصوتي / دفع البريد من Alibaba Cloud، تحسين GEO، تحسين SEO، أكواد QR الجاذبة، Tencent Qidian، تنقيب العملاء المحتملين، البيانات الكبرى العالمية، التوزيع متعدد المنصات، تصميم الاستبيانات والبحث، SalesBuddy).
<img src="docs/screenshots/marketing-tools.png" width="900" alt="أدوات التسويق">

**إنشاء المحتوى**: نص إلى صورة، صورة إلى فيديو، استنساخ الفيديو، النسخة الرقمية، تعديل الصور وإزالة العلامة المائية، استخراج النص، تركيب الصوت، الموسيقى، الدبلجة، المونتاج، عكس السيناريو ونص الإلقاء، مع حزم تحسين «صفحة المنتج» للتجارة الإلكترونية عبر الحدود والمحلية؛ «مجتمع قوالب الفيديو» يتصفح العينات بحسب الاستخدام / الأحدث / الأكثر حفظاً، ويستنسخ بموجهات وصورة مرجعية ونماذجك الخاصة، والاستنساخ مهمة غير متزامنة تُتابَع داخل تبويب «مهام الإنشاء» بالتقدم والناتج (مشاهدة الوصفة المدفوعة تمنح الناشر نقاطاً، ويمكن للوحة الإدارة اختيارياً إضافة قوالب منصة AIworkin)؛ وفي الختام أداة إنشاء فيديو قابلة للنشر محلياً.

## 📖 تفصيل الوظائف

### ١、الحسابات والهويات والجلسات

- **حلقة حساب محلية مغلقة**: التسجيل (اسم المستخدم / البريد / الجوال كخيارات)، تسجيل الدخول، الاستعادة، تغيير كلمة المرور، إعادة الربط، إلغاء الحساب؛ سجل تسجيل الدخول والحظر على مستوى المنصة.
- **طرق تسجيل الدخول والتحقق عند التسجيل**: تُصيَّر صفحة تسجيل الدخول ديناميكياً بحسب مفاتيح الإدارة «الدخول العادي (حساب + كلمة مرور) / رمز تحقق بالبريد / رمز تحقق بالجوال / رمز QR عبر WeChat»؛
  ويُصيَّر التسجيل بحسب الطرق التي شغّلها المسؤول «اسم المستخدم / البريد / الجوال»، ويتطلب التسجيل بالبريد أو الرسائل التحقق أولاً برمز (يحتاج البريد إعداد SMTP، والجوال إعداد رسائل Alibaba Cloud؛
  وأي قناة غير مهيأة لا يمكن تعليمها في الإدارة ولا تظهر في الواجهة). بعد تعليم «تسجيل الدخول التلقائي خلال 30 يوماً» تُمدَّد الجلسة إلى 30 يوماً.
- **تسجيل الدخول / التسجيل بمسح QR عبر WeChat**: رمز QR لتطبيق «موقع الويب» في منصة WeChat المفتوحة؛ إن كان مرتبطاً يدخل مباشرة، وإن لم يكن وكان التسجيل التلقائي مفعّلاً يُنشأ الحساب ويُربط (اسم المستخدم `wx_<آخر 8 محارف من openid>`،
  ويُجلب الاسم المستعار والصورة للتحضير)، وإن كان التسجيل التلقائي متوقفاً يُوجَّه للتحقق بالحساب وكلمة المرور أو برمز البريد / الجوال ثم الربط؛ و`state` الخاص بالرمز لمرة واحدة وصالح 5 دقائق،
  ويُخزَّن AppSecret مشفّراً ولا تعيد الإدارة سوى قناع.
- **الإدارة «إعدادات النظام → الحسابات وتسجيل الدخول»**: صيانة موحدة لطرق التسجيل والدخول وSMTP ورسائل Alibaba Cloud ومعاملات WeChat؛ وقبل تشغيل أي قناة يجب تجهيز بيانات اعتمادها المقابلة.
- **توحيد اسم المستخدم والبريد إلى أحرف صغيرة**: ترتيب MySQL غير حساس لحالة الأحرف وPostgreSQL حساس، لذا يُخزَّن ويُتحقق التكرار بحروف صغيرة لتطابق السلوك على القاعدتين؛ ويمكن على قاعدة قائمة إعادة التعبئة
  عبر `pnpm --filter aiworkin-enterprise-api db:normalize-usernames`.
- **جلسة موقّعة ذاتياً**: تُقبل فقط جلسات SSO الصادرة محلياً (issuer `enterprise-sso`، والمفتاح مشتق من `JWT_SECRET` عبر HKDF)،
  ويُتحقق في كل طلب من حالة الحساب و`tokenVersion`——فيبطل تغيير كلمة المرور أو إعادة الربط أو الحظر فوراً؛ وتُرفض رموز المنبع كلياً.
- **إعادة التحقق من المخرجات المخزَّنة**: الروابط العامة القديمة، تنزيل ملفات التصدير، رموز إضافة Chrome، المهام المجدولة دون مراقبة، تشغيل سير العمل بالجدولة / الأحداث، وعضوية مشروع المؤسسة في low-code — يُعاد التحقق قبل الاستخدام بحسب جداول قاعدة البيانات الحالية «حالة الحساب + العلاقة بالنظام»، فتبطل فوراً عند مغادرة الموظف أو تغيّر الدور (دون انتظار التنظيف غير المتزامن للأعضاء أو التخزين المؤقت)؛ ويُرَدّ خارجياً بصورة موحدة «غير موجود / منتهٍ» دون كشف سبب الإبطال.
- **الهويات المتعددة وأنواع الكيان**: مسؤول المنصة، مستخدم مؤسسة، مزود خدمة، موظف مزود خدمة (وكيل)، أربع هويات؛
  والكيان إما مؤسسة أو منشأة فردية أو فرد. وبعد تبديل الهوية تُعاد بنية الشريط الجانبي: يرى مسؤول المنصة لوحة إدارة المنصة فقط
  (خمس مجموعات: المستخدمون ومزودو الخدمة / الإشراف على التشغيل / الفاتورة والمنتجات / القدرات والأمان / النظام والمحتوى، ونظرة بيانات المنصة تُدمج مباشرة في قمرة الإدارة `/dashboard`)،
  دون «إعدادات الإدارة» الخاصة بمنظور الحساب الشخصي.
- **التوثيق والمؤهلات**: بيانات المؤسسة تسري بمجرد الإرسال؛ تسجيل مزود الخدمة يحتاج مراجعة المنصة؛ والموظف يحتاج ربطاً أو انتساباً لمزود خدمة.
- **رمز الدعوة**: لكل حساب رمز دعوة خاص، ويُتيح إدخاله (اختياري) عند التسجيل إنشاء علاقة الدعوة؛ وتعرض «دعواتي» الرمز ورابط التسجيل ومن دعاك وعدد المدعوين؛ و«دعوة للتسجيل» في قائمة صورة الرأس تنتقل مباشرة إلى هذه الصفحة.

### ٢、قمرة القيادة

- مداخل سريعة في أعلى يمين الصفحة: **إدارة مفتاح API**، **شحن النقاط**، ثم زر الهوية (للمسؤول «لوحة الإدارة»، ولغيره «الهوية والمؤهلات»)؛ وعند عدم ربط مفتاح AIPDD API Key تظهر في أقصى اليسار شارة حمراء **ربط مفتاح AIPDD API Key** تنتقل مباشرة إلى قسم الربط في «إدارة مفاتيح API» وتختفي بعد الربط.
- بطاقات الإحصاء: **«مهامي» دائماً في الصدارة** (عدد غير المنجز في مركز المهام، والنقر ينقل إلى `/tasks`)، و**«العقود السارية» دائماً في الختام»، وما عدا ذلك من بطاقات لها صفحة مستقلة قابل للنقر؛ ولكل هوية مجموعتها——المؤسسة (مهامي / المهام المطلوبة / موافقات OA / رسائل جديدة / العقود السارية)، ومزود الخدمة (مهامي / المؤسسات المخدومة / المهام المطلوبة / موافقات OA / العقود السارية)، والموظف (مهامي / الهيئة المرتبطة / المؤسسات المتولى بها / المهام المطلوبة / موافقات OA)، ومسؤول المنصة (مهامي / المهام المطلوبة / رسائل جديدة).
- أول قسم تحت بطاقات الإحصاء هو **التنقل السريع**: بطاقة التنقل الشائع قابلة للنقر بالكامل، و«الإعداد» أعلى اليمين يضيف / يحذف ويرتّب، ويُحفظ على مستوى الحساب؛ ثم يأتي **قمرة النمو** لهوية المؤسسة (تقدم الأهداف، التحصيل، المشاريع قيد التسليم، تحويل الاستقطاب، تحويل خدمة العملاء إلى عملاء محتملين)، ثم «مهامي المطلوبة» (الإجمالي حسب الأقسام غير المنجزة، وتُخفى فئات الخدمة غير المفتوحة بحسب الهوية)، ثم **أعلى 5 من مهامي** (ينتقل كل سطر إلى الوحدة المصدر للإنجاز)، ثم نظرة «بحاجة إليّ» والرسائل الجديدة.
- **«بحاجة إليّ» تعتمد معياراً واحداً فقط هو `bySource` في مركز المهام** (بنفس مصدر `/tasks`): لا تدرج إلا ما يخصّك فعلاً وله عدد حالي (استفسارات الموقع، OA، CRM، OKR، المشاريع، سير العمل، عقود بحاجة إلى تأكيد، مراجعة المنصة)；و«دعوات الربط بحاجة إلى تأكيدي» لا تنتمي لأي مصدر مهام وتُضاف في سطر مستقل.
- مسؤول المنصة: قمرة القيادة هي نظرة بيانات المنصة (التسجيلات / المؤسسات / مزودو الخدمة / التعاقدات / مستندات الأعمال المختلفة ومقادير الضريبة)، والموافقات المعلّقة (تسجيل مزودي الخدمة) وتوزيع أنواع خدمات مزودي الخدمة؛ ويُنتقل من الشريط الجانبي مباشرة إلى أقسام الإشراف.

### ٣、منصة العمل (21 مدخلاً)

| الوحدة | النقاط الرئيسية |
|---|---|
| **مهامي** | مركز مهام موحّد: يجمع في شاشة واحدة ثمانية أنواع من المهام العالقة — موافقات OA، مهام OKR، مهام المشروع، مهام CRM، محادثات خدمة العملاء، تأكيد التعاقد، مراجعة المنصة، والعقد البشرية في سير العمل (تجميع كامل على مستوى الحساب، مع تصفية بالمصدر / المجموعة + بحث + ترقيم صفحات)؛ ويعرض كل سطر وصف المهمة وحالة المركز وحالة الجهة المعنية ومدخل التنفيذ فقط، ويبقى التفصيل في الوحدة المصدر. وتُعرض حالة المركز (غير منفّذ → قيد التنفيذ → منجز / ملغى / منتهٍ) منفصلة عن الحالة المرجعية للأعمال، ويمكن للشخص إغلاقها / إعادة فتحها (بتأكيد كلمة المرور)، وتُغلق تلقائياً عند بلوغ الحالة النهائية في الوحدة المصدر؛ ولقمرة القيادة لوحة أعلى 5 مستقلة. |
| **Agent** | الحوار مع النموذج ينتج صوراً / فيديوهات مباشرة، وتُحفظ النتائج تلقائياً في الأصول الرقمية AIPDD لهذا الحساب؛ وقد دُمجت الذاكرة طويلة المدى / مكتبة الموارد / ذاكرة العمليات في تبويب «قاعدة المعرفة → الذاكرة» (المكتبة والذاكرة طويلة المدى تتحدان في قاعدة المعرفة، ويحتفظ Agent بمعيار بحث واحد على مستوى الموقع)؛ وبوابة تفويض «الإجراءات القابلة للتنفيذ التلقائي» معلّقة تحت تبويب موصل MCP وتضبط نوعين من التفويض — إجراءات كتابة العقود، وأدوات موصل MCP ذاتي البناء (أدوات الموصل مرفوضة افتراضياً، وتُفتح بالتعليم على الموصل بأكمله، وغير المصرّح يعيد مسودة فقط، ولا يُنفَّذ شيء دون مراقبة). وعند رفع المهارة / الإضافة تمر أولاً بمراجعة أمان بالذكاء الاصطناعي (بالمفتاح والنموذج المهيأين في «إعدادات النموذج»)، ولا تدخل المخزن إلا إذا اجتازت، ومن أعلن أذونات يلزمه تأكيد قبل التمكين؛ وفي وقت التشغيل توجد حواجز لعدد الاستدعاءات والاستدعاء المتكرر واحتياطي المخرجات. ويُهيَّأ النموذج والمفتاح في «خدمات النماذج → إعدادات النموذج». |
| **سير العمل** | تنسيق مرئي متعدد الخطوات: سحب العقد والوصلات على اللوحة، ودليل العقود مشتق من سجل قدرات موحّد (إجراءات العقود، وأدوات مدمجة / أعمال / موصلات / أجهزة / مهارات / إضافات، وعقد مدمجة للتحفيز / التفريع الشرطي / التوازي والدمج / الذكاء الاصطناعي / البشري / Webhook)، وتُولَّد نماذج المعاملات تلقائياً من العقود؛ ويمكن عند الإنشاء اختيار 5 قوالب وصفات مدمجة (متابعة الاستقطاب / تجديد العقد / تسريع التحصيل / فحص جودة التذاكر / تمكين الالتحاق)، فتملأ الاسم والوصف وتجلب مخطط التدفق، وافتراضي الاستلام للمُنشئ نفسه، ويعمل بمجرد النسخ؛ ويمكنك أيضاً النقر على «الإنشاء بالذكاء الاصطناعي» ووصف الحاجة بجملة أو بضع جولات، فيعيد النموذج النصي كتابة اللوحة الحالية من عقد النظام الحالية (تمر بنفس تحقق DAG قبل القبول، وما لا يمكن ربطه يُوجَّه إلى عقدة «الوكيل الذكي»)، ثم انقر «تطبيق على اللوحة» واحفظ؛ حفظ المسودة → التجربة خطوة بخطوة في Playground (مدخل / مخرج / مدة / خطأ لكل خطوة) → نشر إصدار مجمّد. ويُجرى وقت التشغيل كشف حلقات DAG وحل متغيرات القالب (`{{input.x}}` / `{{vars.x}}` / `{{nodes.id.x}}` / `{{actor.userId}}`)، وتُعلَّق العقد البشرية ثم يستيقظها الإغلاق من «مهامي»؛ وسير العمل المشترك يدخل دليل أدوات Agent والمهارات عبر `wf__<id>`. وقبل التشغيل بالجدولة / أحداث المجال / أحداث المهام يُعاد التحقق من حساب المُنشئ وأهليته التنظيمية بحسب الجداول الحالية، فلا يبدأ تلقائياً بعد المغادرة أو الإخراج من المؤسسة. وتُجمَّع القائمة بحسب «مهامي + تبويب لكل كيان» (`شركة أ · مشاركة الشركة` / `مزود ج · مشاركة المزود`، والاسم من الهيئة التي تنتسب إليها، ويُقص الطويل مع إظهاره كاملاً عند المرور)، ونطاق بيانات كل كيان مستقل ولا يختلط أبداً في قائمة واحدة، ويمكن عند الإنشاء تحديد المشاركة إلى أي شركة / أي مزود. |
| **قاعدة المعرفة** | إلقاء محاضر الاجتماعات والمقالات والنصوص المكتوبة للمكالمات في فضاء المعرفة، فيصرّفها النظام إلى صفحات wiki قابلة للتتبع؛ و`[[الروابط]]` في النص تُنمّي خريطة معرفية تلقائياً، ويتاح البحث الهجين (الكلمات المفتاحية + المتجهات) والأسئلة بأسانيد فور الكتابة، وعند غياب النموذج الكبير تمر السلسلة كاملة عبر تراجع حتمي قائم على القواعد؛ وتغطي التبويبات فضاء المعرفة والموارد والصفحات والأسئلة والخريطة والمستهلكين والذاكرة. ويمكن استخلاص آثار عمل الوكلاء في **ذاكرة العمليات**، ويعود السياق قبل الإجابة من هنا أيضاً؛ وتتحد الذاكرة طويلة المدى والمكتبة في قاعدة المعرفة، ويحتفظ Agent بهذا المعيار الواحد على مستوى الموقع. |
| **Workbuddy السحابي** | المهام المجدولة: يُوضَّح الكلام العام عبر الذكاء الاصطناعي إلى مستند مهمة، ويُقسَّم ويُوزَّع، وتُزامَن رسائل Agent؛ Agent: إنشاء / إصدار / جلسة؛ حساب Workbuddy Enterprise: يُخزَّن SecretId / SecretKey الخاص بالمستخدم مشفّراً وقابلاً للتعدد المتوازي؛ حساب استدعاء الذكاء الاصطناعي: تُخزَّن كلمات المرور / مفاتيح API / الكوكيز لمنصات الطرف الثالث مشفّرة، وتُفوض بالربط بحساب السحابة، وتُستخدم عبر قناة الجهاز بحسب الربط. |

| **أتمتة RPA** | مهام RPA (ربط المهمة بالسكربت + الحساب + معاملات التشغيل)، حسابات RPA (كلمات مرور مخزَّنة مشفّرة)، سكربتات RPA (Automa JSON / JS / Python، ويمكن للنموذج النصي في AIPDD توليدها بحسب الطلب)؛ ويتولى متصفح Bit المحلي التنفيذ بمفتاح API ويعيد النتائج. **وكيل المتصفح (Chrome المحلي)** — الإضافة نفسها AIPDD Enterprise تسجّل الدخول بحساب هذا الموقع فتصبح جهازًا متصلًا: يمكن لنموذج LLM السحابي أن يقرّر خطوة بخطوة وتنفّذ الإضافة داخل متصفحك (تعيد خريطة الصفحة ولقطات شاشة، وتتوقف عند الإجراءات الحساسة لتأكيد يدوي، وقابلة للإيقاف الفوري في أي وقت، ولا تستقبل أبدًا كلمات مرور المنصات المستهدفة)، أو اضغط Alt+A لفتح **اللوحة الجانبية** للإضافة، وصف النتيجة بجملة واحدة، فيخطّط الوكيل وينفّذ خطوات متعددة باستقلالية على المواقع التي سجّلت الدخول إليها ويعيد نتائج منظّمة؛ وثلاثة أنماط Act / Crawl / Extract، مع نماذج من ساحة النماذج في هذا النظام وتُحتسب بنقاط المنصة. ويمكنك حفظ **المهارات** (معرفة شخصية / بمعرفة موقع) و**التسجيل ← الأدوات** (يُعاد تشغيلها في مسار التنفيذ المحلي نفسه للوكيل، ولا تُسجَّل حقول كلمة المرور)، وتأتي الإضافة بـ **MCP** افتراضي: حين يكون الجهاز أخضر (متصل)، يمكن لوكيل المنصة وعملاء MCP الخارجيين إرسال المهام إليه عبر `/api/v1/mcp` بأدوات `browser_*`. ويمكن كذلك ربط سلسلة إجراءات محدَّدة (chrome_actions) لإعادتها بالتسلسل دون LLM، أو تشغيلها وجدولتها من Agent / MCP وقسم «مهام RPA المصفوفية» على جهاز متصل. ويمكن للوحة الجانبية أيضًا إنشاء **مهام مجدولة** (مرة واحدة / بتكرار دوري) ليقوم هذا الجهاز المتصل بتشغيل هدف تلقائيًا عند الاستحقاق؛ وإذا كان الجهاز غير متصل تُتخطى تلك الجولة (دون تعويض)، وعند تعطيل الحساب تُعلَّق تلقائيًا. |

| **إدارة المشاريع** | الملف الرئيسي للمشروع، الأعضاء والمعالم، التكرارات واعتماديات المهام، سجل الساعات والموافقة على الجدول الأسبوعي؛ ويقدّم الذكاء الاصطناعي اقتراحات تفكيك WBS وتقييم صحة المشروع، ولا تُكتب نتيجة التفكيك في المهام إلا بعد تأكيد بشري. ويحسب تبويب **التكلفة** تلقائياً تكلفة القوى العاملة وفق «الساعات المعتمدة × المعدل الساري»، وتُسجَّل المواد / المعدات / الخدمات الخارجية سطراً بسطر، مع ظهور استغلال الميزانية والساعات دون معدل مهيأ فورياً؛ ويصون تبويب **التعاون الخارجي** بشكل موحّد دليل المورّدين / OPC / الأفراد / الشركاء وأوامر التعاون (مسودة → تنفيذ → بانتظار القبول → تسوية / إلغاء)، ويولّد القبول الناجح بند تكلفة خارجية تلقائياً. وتدعم المهام ثلاث طرق للتعاقد: الموظف الداخلي، تعاقد المهمة، والطرف الخارجي، مع صيانة معايير القبول ودرجات الجودة وأوزان التقييم. ويمكن **تصدير المهمة كطلب** إلى جهات خارجية: نشر النطاق / المخرجات / الميزانية / المدة / معيار القبول، ثم اعتماد العرض والمدة الملتزم بها بعد استرجاعهما، فينشئ النظام أمر التعاون الخارجي تلقائياً ويعيد تعيين المهمة ويدرج هذا التعاون في القبول والتكلفة. ويسجّل تبويب **تدقيق الساعات** القيم قبل وبعد كل تعديل ويجمعها بحسب الشخص، ويدعم تبويب **مزامنة المهام** المزامنة ثنائية الاتجاه مع Jira / Teambition / TAPD. ويحمل المشروع والمهام درج «التعاون»: التعليقات / الردود / الإشارة إلى الزملاء، الوسوم، روابط الموارد والحفظ، وتُنقّى التعليقات وفق قائمة بيضاء قبل الكتابة، وتقتصر الإشارة على أعضاء المؤسسة النظاميين وتدخل الإشعارات الداخلية. ولتفاصيل المشروع تبويبان مجمّعان «التسليم» و«التكلفة»: يعرض التسليم المهام المنجزة / الجارية / المتأخرة ووزن القبول، وتعرض التكلفة الميزانية والتكلفة المتحققة ونسبة استغلال الميزانية والتعاون الخارجي والساعات المسجلة (وتبقى إجراءات الصيانة في تبويب «التكلفة» بصفحة المشروع). |
| **المخزون والمبيعات** | المنتجات / المتغيرات / التصنيفات / المستودعات، حركة المخزون والتحويل، موافقة الصرف، أوامر الشراء والإدخال، المورّدون، المدينون والدائنون والمقبوضات والمدفوعات، المصاريف، معدلات الضريبة واستراتيجية السعر؛ ويقدّم الذكاء الاصطناعي رؤى تشغيلية بأربعة أنواع (المخزون / الشراء / الذمم المدينة / التدفق النقدي)، ويُخرج قواعدياً عند عدم تهيئة مفتاح نموذج. |
| **خدمة العملاء بالذكاء الاصطناعي** | خدمة عملاء على مستوى الحساب: يمكن لحساب واحد ربط عدة مواقع رسمية، يدخل الزوار من نافذة خدمة الموقع (iframe من نفس النطاق `/embed/service-desk`) ويستقبلهم موظفو / وكلاء المؤسسة شخصياً؛ وتضم ثمانية تبويبات: المحادثات، **تذاكر ما بعد البيع**، فريق الخدمة، إعدادات الاستقبال، العبارات والمعرفة، المواقع والربط، ربط القنوات، الإحصاءات. وتسير تذاكر ما بعد البيع عبر آلة حالات: بانتظار المعالجة → مراجعة → اعتماد / استلام / إرسال → إنجاز، مع خط زمني للأحداث. وتنقسم حالة الاستقبال إلى متصل / بعيد / غير متصل، ولا تشارك في التوزيع التلقائي إلا حالة الاتصال؛ ويطبّق الذكاء الاصطناعي بحسب الإعداد نصاً ثابتاً أو اقتراح رد أو رداً تلقائياً، ويمكن في النمط التلقائي التحويل إلى بشري في أي وقت، بينما لا يحوّل نمط الذكاء الاصطناعي الصرف. |
| **مركز التطبيقات** | مدخل مدمج للتطبيقات المدمجة وسوق التطبيقات: تبحث الصفحة الرئيسية بالكلمات المفتاحية عن «ما بنيته / ما بنته مؤسستي / تطبيقات السوق»، مع أربعة تبويبات: إنشاء مؤسسة، ما أنشأته، ما انضممت إليه، سوق التطبيقات. وتُسجَّل كيانات التطبيقات المدمجة في جداول متعددة الأبعاد، ويقرأ الأعضاء ويكتبون وفق أذونات الأدوار؛ والسوق عرض للقراءة فقط لدليل عام خارجي، ولا يستضيف هذا الموقع تطبيقات ولا ينشرها ولا يقيّمها. |
| **قاعة الموضوعات** | نشر نقاشات موضوعية داخل المؤسسة أو عامة: يشارك داخلياً موظفو المؤسسة وشركاء التعاقد / التنفيذ، وتُفتح للجميع للجميع من الحسابات المسجلة؛ ويمكن للمنشئ إنهاء الموضوع (يلخّص الذكاء الاصطناعي كل المداخلات والردود)، وإعادة الإنهاء، والإغلاق أو الحذف؛ ويمكن توقيع المداخلات بالاسم الشخصي أو بالنسخة الرقمية. |

### ٤、خدمات الأعمال (11 خط خدمة + ساحة العرض والطلب)

الشكل الموحّد: **مكتبة موارد مزودي الخدمة** (تصفح القائمة → التفاصيل → بدء التعاقد) + **معلومات الطلب / سوق الخدمات** + **سجل الأعمال**.
ويجب أن يُكمل مزود الخدمة التسجيل ويُؤهَّل في الفئة المقابلة قبل أن تظهر موارده للخارج؛ وعندما لا يوجد في قسم ما إلا مزود خدمة واحد لا تُعرض القائمة وتُدمج تفاصيله مباشرة.
وساحة العرض والطلب سوق عام عابر للأقسام دون بوابة تسجيل بحسب القسم؛ والقائمتان الطلب / الخدمة **مرقّمتان بالصفحات** (دون سحب لا نهائي)،
ويمكن تصفيتهما بـ**المنطقة (المحافظة / المدينة) والفئة الثانوية**، وتُعرض أعمدة الفئة (الأولى / الثانية) مع السطر؛ وإلى جانب القائمتين تبويب **التقييمات** (توزيع الدرجات، سجل التقييمات)، وتُعدّ بيانات التقييم أيضاً مصدراً لدرجة عرض مزود الخدمة.

ولقوائم **الطلب / الخدمة** في كل سوق خدمات وفي ساحة العرض والطلب زوج إضافي من الفلاتر «**الكل (طلب / خدمة)** / **المنشور بواسطتي**»:
«الكل» يقرأ مباشرة المخزون العام للفئة المقابلة في AIworkin؛ و«المنشور بواسطتي» يقرأ سجل هذا النظام (تُسجَّل عملية النشر محلياً أولاً،
ثم تُزامَن مع المنصة ويُعاد تسجيل معرّف محتوى المنصة). وبحسب معيار المستخدم بتاريخ 2026-11-09، يُصيَّر «المنشور بواسطتي» **لهوية مزود الخدمة فقط**،
ولا تظهر هذه التصفية لهوية المؤسسة إطلاقاً (الكل فقط). والسجلات المنشورة رسمياً على AIworkin لا تُعدَّل ولا تُحذف في هذا النظام،
ولا يبقى سوى «عرض»——وواجهات REST للكتابة في المنصة (PATCH / DELETE) تُرجع 401 دائماً مع مفتاح API، وMCP ليس فيه أداة تعديل / حذف.
**سوق الخدمات** (اللوجستيات / التسويق / التوسع الخارجي / العمل المرن / تقنية المعلومات / الملكية الفكرية / القانون / مراكز الفكر / الأصول / التوريد / الضرائب): مفاتيح القائمة كلها «سوق خدمات ××»،
والمتن هو البند نفسه: كل الخدمات = المخزون العام للمنصة، وخدماتي المنشورة = السجل المحلي؛ وقد أُعيدت تسمية التوريد / الضرائب ودمجهما من
«نشر الخدمات» في 2026-11-09 (المستخدم: «التوافق مع بقية الأسواق، مع رؤية المخزون العام وخدماتي المنشورة معاً»).
**ويظهر تبويب سوق التوريد في الواجهة أيضاً للجهة المؤسسية** (2026-11-09): السوق متاح للتصفح في كل الموقع، لكن المؤسسة لا يمكنها نشر الخدمات——
فمدخل «نشر خدمة» لا يُصيَّر بحسب الهوية، ولا تظهر تصفية «خدماتي المنشورة»، ويعترض الخادم بنفس المعيار عبر `assertPublishAllowed`.

- **التعاقد**: تبدأ المؤسسة → يؤكد مزود الخدمة → الدخول إلى سجل التعاقدات؛ ويمكن لمسؤول المنصة إنهاء تعاقد سارٍ من «الإشراف على التعاقدات».
- **حزم الخدمات الرسمية**: تعرض فئة مزودي الخدمة في كل قسم أعمال الحزم الرسمية للمنصة (سعر مرجعي باليوان + سعر بالنقاط محوّل بحسب سعر الصرف في الإدارة)، وتُشترى مباشرة بنقاط المؤسسة؛ وبعد الشراء تتولى المنصة التعاقد والتسليم بنداً بنداً بين المؤسسة وعده من مزودي الخدمة المتميزين، ومعيار الحزمة هو «تنجز هذه الحزمة من قبل المنصة عبر دمج مزودي خدمة متميزين»، ولا يسري أي تعاقد إلا بعد تأكيد مزود الخدمة (فالمزود المعيّن يُطلق تلقائياً فقط ولا يؤكد تلقائياً)، ويُقرأ تقدم التسليم من حالة التعاقد فورياً. وتصون إدارة «حزم الخدمات» الدليل وقائمة التسليم (المطابقة، إطلاق الاستضافة، تغيير الكيان، الاسترداد الجزئي / الكلي)، ويُحتسب حد الشراء لكل مؤسسة، ولا تشارك الحزم في إدارة دورة التسليم والانتهاء؛ ويعرض «حزمي» في الواجهة الحزم المشتراة وتقدم التسليم بنداً بنداً.
- **تفعيل القدرات**: التقديم الإلكتروني للضرائب / الفاتورة الإلكترونية قدرتان مدفوعتان، يهيئهما مزود الخدمة للمؤسسة المخدومة، وترسل المؤسسة طلب التفعيل فتراجعه المنصة؛
  ويُوحَّد التفعيل / الإيقاف على مستوى المؤسسة ومطابقة حساب Qixiangyun في إدارة «الإدارة الضريبية».
- **لوحات الأعمال**: تقرأ قوائم **معلومات الطلب** في أقسام الضرائب / التوريد / التوسع الخارجي سجل هذا النظام (`market_listing_records`)،
  ولم تعد تقرأ المخزون العام للمنصة مباشرة؛ وتُزامَن عملية النشر مع منصة AIworkin عبر قناة MCP الموحّدة، فيُعاد تسجيل رقم الطلب على المنصة (معرّف المحتوى)
  في السجل المحلي، ولا تتاح السجلات المنشورة رسمياً على المنصة في هذا النظام إلا للعرض. وقد أُوحّدت **أعمدة الخدمة** في هذه الأقسام منذ
  2026-11-09 على شكل «**سوق خدمات ××**»، تقرأ سجل خدمات هذا النظام (`provider_service_listings`) مع إمكانية التبديل بين
  «كل الخدمات / خدماتي المنشورة» (الكل = المخزون العام للمنصة)، ويُسجَّل النشر محلياً أولاً ثم يُزامَن مع المنصة مع إعادة تسجيل رقم الأمر.
- **ساحة العرض والطلب**: مدخل القائمة تحت «خدمات الأعمال»، وتُعيد الواجهات استخدام `/enterprise/market/:domain/...` مع
  `domain=HUB` للتعبير عن العابر للأقسام: ولتبويبي الطلب / الخدمة فلاتر «الكل / المنشور بواسطتي»——«الكل» يقرأ فقط **المخزون العام** للمنصة
  (لذا لا يحدث فشل تفويض القناة حتى دون ربط مفتاح)، و«المنشور بواسطتي» يقرأ فقط سجل هذا النظام (`scope=mine`، ويُصيَّر لهوية مزود الخدمة فقط)؛
  ويدعم الاثنان التصفية بالمنطقة (المحافظة / المدينة) والفئة الثانوية (اختيار الفئة عبر أي قسم أعمال، مع عرض الفئة الأولى على السطر)؛
  وتُعرض القائمة بالصفحات، فلا يُجلب المقطع التالي إلا عند تغيير الصفحة، دون تفريغ تمرير طويل على يمين القائمة؛
  ويُستخدم للنشر مفتاح AIPDD API Key المرتبط بالحساب الحالي للكتابة المباشرة على المنصة مع سجل محلي، ويمر المحتوى المنشور أيضاً بمراجعة أمان المحتوى التلقائية من Alibaba Cloud؛
  ولا يمكن تعديل أو حذف السجلات المنشورة على المنصة في هذا النظام، ولا يبقى سوى «عرض».

### ٥、تواصل الأعمال (اجتماعي / توظيف / عرض وطلب)

- **التواصل الاجتماعي للأعمال**: التعرّف على الزملاء (أصدقاء / حظر)، نشر المنشورات (عامة / للأصدقاء فقط)، مجموعات على نمط Douban (اكتشاف / انضمام، النشر بالتصنيف،
  إخفاء الهوية لكل مشاركة، الردود بالطوابق والتوصيات، تثبيت رئيس المجموعة / المشرف وتمييزه، واعتماد الانضمام)، الرسائل الخاصة الداخلية، السيرة الذاتية المهنية (صفحة HTML مستقلة متفرعة عن الملف الشخصي،
  يمكن إرسالها في الرسائل الخاصة، ويفتحها صاحب العمل فوراً ويصدّرها PDF). وعند حظر الحساب تُعترض قدرات التواصل الاجتماعي تلقائياً.
- **التوظيف**: نشر وظائف بدوام كامل / جزئي / تدريب / مؤقت / إعارة عمالية في تدفق ساحة التوظيف، والتواصل عبر الرسائل الخاصة (مع إمكانية إرفاق السيرة)،
  ولا يُدير هذا النظام مكتبة سير ذاتية بنظام ATS ولا فرزها؛ وعند ربط مفتاح AIPDD يمكن مزامنة الوظائف كطلب قوى عاملة في AIworkin (تُثبَّت الفئة على شجرة «العمل المرن»).
- **ساحة العرض والطلب**: نشر عام للطلبات / الخدمات، في التدفق المحلي، قابل للتصفح والتواصل بالرسائل الخاصة.
  والنشر على **مرحلتين** هو المعيار الأساسي لهذا المشروع: افتراضياً نشر محلي دون مفتاح؛ وعند تعليم «المزامنة إلى AIworkin»
  يُستدعى المنبع `POST /market/listings` عبر محلّل بيانات الاعتماد الموحّد بمفتاح المستخدم المرتبط، وينعكس حالة المراجعة / السحب من المنبع.

### ٨、خدمات النماذج

- **إدارة مفاتيح API**: مجموعتان تُداران منفصلتين——مفتاح `ek_` في هذا النظام لاستدعاء الواجهات المفتوحة (`/api/v1`) وساحة النماذج، والإنشاء / النسخ / إعادة الضبط / الإلغاء في هذه الصفحة،
  ويمكن لكل مفتاح ضبط «حصة نقاط» منفصلة (حد استهلاك تراكمي للاستدعاءات الخارجية، ويُرفض عند التجاوز، ويمكن ضبطه غير محدود)؛
  ويُربط مفتاح AIPDD API Key (`sk-`) في الصفحة نفسها، فيفتح القدرات الأمامية كالنشر المتزامن ومزامنة بيانات مزود الخدمة وموارد التعارف. ويُخزَّن المفتاح مشفّراً، ولا يمكن نسخه في هذه الصفحة إلا لصاحبه، ولا يراه غيره.
- **ساحة النماذج** (`/model-plaza`): دليل النماذج المتاحة المعتمدة من المنصة——وحدة الفاتورة مطابقة للمنبع (المحادثة / المتجهات بالرمز Token، الصور بالعدد، الفيديو والتعرف الصوتي بالثانية، تركيب الصوت بالمرة)،
  مع تجربة مباشرة، وعرض سجل الاستخدام، واستخدام بوابة متوافقة مع OpenAI بمفتاح `ek_`؛ ويُصان الدليل وقنوات المنبع والتسعير في الإدارة «الفاتورة والمنتجات → ساحة النماذج».
  ويوجد في الإدارة أيضاً تبويب «النموذج الافتراضي»: تحديد النموذج الافتراضي للمنصة لكل من النص / الرؤية / الصورة / الفيديو / التعرف الصوتي / تركيب الصوت / المتجهات، وتهيئة حدود النقاط للمرة واليوم والشهر مع حفظ سجل التغييرات؛
  والمستخدمون الذين أكملوا شحناً حقيقياً مستلماً يرثون تلقائياً القدرات غير المهيأة منفردة (تُحتسب طلبات الشحن المدفوعة فقط دون الإهداء والتسويات)، وتُخصم الاستدعاءات من نقاطهم بسعر الدليل.
- **API-MCP-Skill** (`/developer/api-mcp-skill`): المدخل الموحّد لخدمات النماذج، بثلاثة تبويبات بهذا الترتيب——
  **Skill**: قائمة حزم المهارات التي يولّدها مسؤول المنصة بحسب نطاق الأعمال (الاسم، الوصف، النطاق، عدد الوظائف المغطاة، نموذج التوليد، وقت التحديث)، والنقر على «تنزيل» يأخذ الـ zip؛
  ولا تحتوي الحزمة إلا على دليل الاستدعاء والأمثلة دون مفتاح حقيقي، وإعادة توليد نفس الاسم تستبدل الحزمة القديمة، والقائمة والتنزيل يخضعان لنفس مفتاح القائمة.
  **MCP Server**: يتصل Codex وClaude Desktop وCursor والسكربتات الذاتية وWorkbuddy بنفس مفتاح API؛
  ويحلل الخادم أولاً ذاكرة الوكلاء لهذا الحساب ثم ينفّذ وظائف الموقع تلقائياً وفق التفويض. وتُشتق قائمة الواجهات من طبقة العقود، ويدخل أي وحدة جديدة (المخزون والمبيعات، منصة SEO، الاستقطاب بالذكاء الاصطناعي، SCRM لـ WeCom، مهام المشاريع، الموارد البشرية...) تلقائياً إلى `list_operations`；
  وتُدرج الوظائف التي تغيّر الدفاتر مباشرةً (نتائج الموافقات، المقبوضات والمدفوعات، حركة المخزون، بما يشمل موافقات مخزون / شراء / إدخال / مصاريف ERP، وتسوية المقبوضات والمدفوعات، وحركة الإدخال والإخراج) في قائمة استبعاد دائمة ولا يؤكدها إلا صاحبها في الواجهة.
  **API**: قائمة الواجهات التي يقدّمها هذا النظام فعلاً، مشتقة من طبقة العقود، وبنفس مصدر `list_operations` في خادم MCP ومستند OpenAPI.
  ويبقى العنوانان القديمان `/developer/docs` و`/developer/mcp` مع تحويل، إلى `?view=api` و`?view=mcp` على التوالي.
- **إعدادات النموذج**: تهيئة مشتركة بين Agent وإنشاء المحتوى——تُستخدم قناة AIPDD المدمجة بمفتاح sk- مباشرة، ويمكن أيضاً ربط بوابة أخرى متوافقة مع OpenAI وVolcano MediaKit، واختيار نموذج افتراضي لكل نوع؛
  ويعرض أعلى الصفحة الحالة السارية لـ«النموذج الافتراضي للمنصة» (يُورَّث بحسب أهلية الشحن عند عدم التهيئة الفردية) والحصة المستخدمة اليوم / هذا الشهر.
  ويمكن لمسؤول المنصة في «ساحة النماذج → قنوات المستخدم» ضبط نطاق دعم كل قناة حساب (الدعم الكامل افتراضياً): ولا يمكن للمستخدم على قناة مغلقة الإضافة / التعديل ولا اختيارها؛
  وإغلاق AIPDD يوقف حسابها فقط (إعدادات النموذج / ساحة النماذج)، وتبقى الوظائف الأخرى (خدمات الأعمال...) متاحة بنفس مفتاح AIPDD API Key.
- **آليات المنصة**: المدخل الموحّد للقدرات المستعرضة §5.8——Outbox الأحداث واشتراك Webhook (الاختبار، سجل التسليم، إعادة إرسال الفاشل؛ ويغطي دليل الأحداث عقد الأعمال كالمهام والمشاريع وعملاء / طلبات / تحصيل CRM والطلبات الصادرة والتعاون الخارجي)، الاستيراد CSV (تعيين الحقول، التجربة، إعادة استخدام مخطط التعيين) والتصدير بحسب الوحدة (لم يعد ملف التصدير يُمنح رابطاً عاماً طويل الأمد، بل يُعاد عبر نقطة دخول مسجَّلة بحسب المؤسسة الحالية)، دليل التقارير، محرك القواعد (مطابقة الشروط + استدعاء Webhook / إشعار / رؤية / إنشاء مهمة)، المشاركة العامة (كلمة مرور، صلاحية، إيقاف؛ ويُعاد التحقق عند كل فتح من أهلية المنشئ النظامية، فتبطل عند مغادرته / إخراجه من المؤسسة)، مصدر هوية OIDC (اختبار الاكتشاف، فتح الحساب تلقائياً)، استراتيجية مشاركة المرفقات، ومزامنة دليل Feishu / WeCom والحضور ورسائل البطاقات، مع أثر قبول الشروط (تنبيه في كل الموقع عند عدم قبول إصدار جديد)، وتتبع استخدام المنتج (أحداث الصفحات / الإجراءات ولوحة التجميع) ومبدّل الكيان (تبديل نطاق الموارد البشرية للفرد نفسه بين المؤسسة / مزود الخدمة)، والمساعد المدرك للصفحة (مدخل عائم في كل الموقع). وتُوحَّد تبويبات الأعمال في الموقع على شكل كبسولات ملتفّة (`PanelTabs` / `TabStrip`)، دون خلط Tabs من antd.
- **مركز المساعدة**: قاعدة معرفة مُصدَّرة بالفصول على `/help` تُصان مع إصدار الكود (ملفات المعرفة في `backend/src/help`)، وتغطي استخدام كل وحدة؛ وتوجد في الصفحة نفسها تبويب «سجل التحديثات» يعرض changelog المنتج؛ ويُفتح نص المعرفة بثلاث أدوات MCP للقراءة فقط `Help_chapters / Help_topic / Help_search`، ويمكن للمستخدم سؤال Agent مباشرة للحصول على الاستخدام الرسمي.
- **لقطة OpenAPI**: `/api/openapi.json` (1947 عملية)، تتحقق CI من تطابقها مع لقطة المستودع.

### ٩、الأجهزة الذكية

قسم **الأجهزة الذكية** مستقل في الشريط الجانبي (مجموعة أولى، بعد إعدادات الإدارة): يتصفح المستخدم الأجهزة وحزم التطوير، ويربط أجهزته بالمنصة، ويستدعي بحسب نوع الجهاز أدوات MCP **مخصصة** (تحكم Agent) وواجهات API (تحكم برمجي)؛ ويصون مسؤول المنصة دليل الموديلات وإصدارات حزم التطوير والأدوات الافتراضية للموديل.

- **ساحة الأجهزة** (`/hardware`): يُعرض دليل الموديلات بحسب التوصية / الترتيب، ويعطي كل موديل المواصفات وإصدار حزمة التطوير (قناة مستقرة / معاينة) والتنزيل؛ ويُرفع ملف الحزمة مباشرة إلى OSS هذا الموقع، ويُعد التنزيل، وتقدّم الصفحة SHA-256 للتحقق؛ ويدخل تفاصيل الموديل لعرض قائمة أدوات API / MCP الافتراضية له.
- **إضافة جهاز** (`/hardware/devices`): اختيار موديل لربط الجهاز وتوليد رمز جهاز يبدأ بـ`hw_` (يظهر النص الصريح مرة واحدة فقط عند التوليد، ولا يُخزَّن في القاعدة إلا SHA-256)؛ وبعد إدخال عنوان الخدمة والرمز وفق SDK / البرنامج الثابت في الحزمة يتصل الجهاز عبر النبض، وتُعرض القائمة بثلاث حالات: متصل / غير متصل / لم يُبلّغ قط (يتحول إلى غير متصل بعد 180 ثانية دون نبض)، ويمكن استعراض سجل النبض / الأوامر / الإيصالات لكل جهاز للتشخيص.
- **MCP الأجهزة** (`/hardware/mcp`): خادم MCP للأجهزة مستقل `aiworkin-hardware-mcp` (نقطة `/api/v1/hardware/mcp`)، منفصل تماماً عن MCP المنصة——لا تأتي الأدوات إلا من جدول أدوات الأجهزة، بأسماء `hw__<رمز الموديل>__<رمز الأداة>`، وتُصادَق بمفتاح `ek_` من «المطور → مفتاح API». وتمر أدوات الكتابة ببوابة تفويض ثلاثية: عدم تعليم «قابل للتنفيذ التلقائي» في هذه الصفحة، أو القدوم من مهمة مجدولة دون مراقبة، أو إعلان المستدعي dryRun — كلها تعيد مسودة فقط دون تنفيذ فعلي؛ و«التجربة» الشخصية غير مقيدة بذلك.
- **API الأجهزة** (`/hardware/api`): تمر نفس الأدوات بقناة الجهاز `/api/v1/hardware/**` بمفتاح `ek_`، ويمكن سردها واستدعاؤها بـ`curl`؛ وتُعتمد معاملات الأدوات والاستجابات على أمثلة JSON المذكورة في الصفحة.
- **حزمة التطوير (Dev Kit)**: يوفّر المستودع الجذري `hardware-devkit/` SDK وأمثلة قابلة للبناء والتشغيل مباشرة——مكوّن ESP-IDF لـ ESP32، وحزمة Python بمكتبة قياسية خالصة لـ Jetson / Raspberry Pi، ومثالان قابلان للتشغيل، إضافة إلى جهاز Node محاكى بلا تبعيات (يمكنه إتمام الحلقة الكاملة «نبض → سحب أمر → إيصال» دون أجهزة) ومستند بروتوكول حقلاً بحقل؛ وتُضاف البرامج الثابتة المبنية مسبقاً بعد أول بناء على أجهزة حقيقية.
- **الصيانة في الإدارة**: ينقسم قسم «الأجهزة الذكية» لمسؤول المنصة إلى ثلاثة تبويبات «موديلات الأجهزة / حزم التطوير / الأدوات الافتراضية»——صيانة الدليل، ورفع حزم كل إصدار، وصيانة أدوات API / MCP الافتراضية بحسب الموديل، ويظهر التعديل فوراً للمستخدم. والأدوات الذاتية للمستخدم مرئية ومتاحة له فقط، ولا تدخل أدوات الموديل الافتراضية، ولا تُتاح في السوق في الإصدار الأول.

وقناة الأجهزة (`/api/public/hardware/heartbeat` و`/commands` و`/result`) تقبل رمز الجهاز فقط، دون تسجيل دخول، و**تقصد عدم الاعتراض بمفاتيح الوظائف**: فعندما يغلق المسؤول قسم «الأجهزة الذكية» لا يُقطع نبض الأجهزة المرتبطة.

### ١٠、النقاط والفاتورة

- **النقاط**: الشحن عبر WeChat، الإهداء بين الحسابات، تسعير الوحدات وخصم الاستخدام (تخزين الأصول الرقمية، CRM / BI / OA / خدمة العملاء بالذكاء الاصطناعي)، والسجل وطلبات الشحن في شاشة واحدة؛ وأُسعّرت مسبقاً وحدات رؤى الذكاء الاصطناعي / الموارد البشرية / قاعدة المعرفة / التسويق / التوظيف / فحص المهارات، وتسري بظهور الوحدة المقابلة.
- **قاعدة التخزين**: تُرفع المرفقات والأصول الرقمية مباشرة إلى OSS Alibaba Cloud الخاص بهذا الموقع (دون وساطة المنبع)؛ ويمكن حذف الأصول سطراً بسطر، وتعرض الإدارة «إعدادات النظام → تخزين الملفات» السعة والتسعير والترحيل المجمّع للأصول التاريخية (قابل للقطع والاستئناف، ويُعاد عند الفشل).
- **AWcoin**: عرض للقراءة فقط للرصيد والمصدر، و**لا يُحوَّل أبداً**.
- **تهيئة الإدارة**: سعر الصرف وفئات الشحن، مكافآت التسجيل / الدعوة، حد الإهداء والمخاطر، تسعير كل وحدة، تعديل الحساب واستعلام الطلبات.

  ويمكن للمسؤول ضبط اللغة الافتراضية للموقع، ويبدّلها الزائر في أي وقت، والعربية بترتيب من اليمين لليسار على مستوى الموقع.

- **ظهور القوائم**: يمكن إخفاء كل قائمة في الشريط الجانبي الأمامي (مدخل قمرة القيادة + كل مجموعة، بما يشمل الرابط الخارجي «منصة حساب AIPDD») بنداً بنداً في الإدارة «إعدادات الموقع → ظهور القوائم لدى المستخدم»؛ وتختفي المجموعة تلقائياً عند إخفاء كل بنودها (إخفاء القائمة فقط، ويبقى الرابط قابلاً للوصول).
- **ظهور تبويبات الأقسام**: يمكن إخفاء تبويبي «معلومات الطلب» و«سوق الخدمات» في 12 صفحة قسم «خدمات الأعمال» (التسويق / التوريد / الضرائب / التوسع الخارجي / العمل المرن / اللوجستيات / تقنية المعلومات / الملكية الفكرية / القانون / مراكز الفكر / تداول الأصول / ساحة العرض والطلب) بنداً بنداً بحسب القسم في الإدارة «إعدادات الموقع → تبويبات أقسام خدمات الأعمال (التعليم للإخفاء)»؛ وبنفس معيار ظهور القوائم——إخفاء متطابق لجميع الهويات (بما فيها المسؤول)، وضبط العرض فقط (الروابط المباشرة والواجهات غير مقيدة).
- **مدخل إضافة المتصفح في الأعلى**: الأيقونة الموحّدة في الشريط العلوي إلى جانب الإشعارات وحساب خدمة WeChat، وهي المدخل الوحيد لتنزيل وتثبيت عميل المنصة (AIPDD Enterprise)——يشترك فيه التوزيع التسويقي واستقطاب الذكاء الاصطناعي ووكيل المتصفح (Chrome المحلي) والمسارات المستقبلية لصفحات المنتج / SEO، بدل نوافذ «تثبيت الإضافة» لكل وظيفة. ويفتح الدرج أربعة تبويبات: التنزيل والتثبيت (الإصدار الحالي، أدنى إصدار متوافق، المتصفحات المدعومة، حزمة التثبيت، الخطوات)، دليل الاستخدام (مداخل كل قدرة أعمال والأسئلة الشائعة)، سجل التحديثات، المواقع المفوّضة (عرض / سحب المواقع الموثوقة للإضافة). ويفتح المصافحة التلقائية عند الفتح (دون زر تحديث يدوي): فإن لم تكن مثبتة يُقدَّم إرشاد خطوة بخطوة، وإن كان الإصدار قديماً تحمل الأيقونة نقطة تنبيه وتوجّه للتحديث؛ وعند تقييد المتصفح للكشف يمكن تأكيد «لقد ثبّتُها» يدوياً، لكن المصافحة الحقيقية تتحقق قبل أي تنفيذ أعمال. وإذا لم تنشر المنصة حزمة إضافة، أو أغلق المسؤول «إعدادات الموقع → مدخل إضافة المتصفح في الأعلى»، فلا تُصيَّر الأيقونة كلها؛ ويُركَّب عنوان الحزمة وفق إعداد نطاق الموقع، دون ترميز نطاق أي عميل.
- **رسائل النظام**: ست فئات من الأحداث تُنبَّه مركزياً: خدمة العملاء، الطلبات والفرص، الهوية والتعاقد، الضرائب والإقرار، الأتمتة والتكامل، الحساب والمنصة.

> تُولَّد مخرجات Prisma Client وتعليمات إنشاء الجداول بحسب اللهجة: بعد تبديل القاعدة أعد تنفيذ `pnpm setup` (أو `pnpm --filter aiworkin-enterprise-api prisma:generate:pg`).

### المتغيرات البيئية الرئيسية

| المتغير | الوصف |
|---|---|
| `DATABASE_URL` | سلسلة اتصال القاعدة: MySQL `mysql://user:pass@127.0.0.1:3306/enterprise` أو PostgreSQL `postgresql://user:pass@127.0.0.1:5432/enterprise?schema=public` |
| `DB_PROVIDER` | `mysql` / `postgres`: أساس تفريع لهجة SQL الأصلية (تزايد رقم المستند، استخراج عمود JSON)؛ ويُستنتج من بروتوكول `DATABASE_URL` عند الغياب |
| `PORT` | منفذ استماع الخادم، الافتراضي `1690` |
| `JWT_SECRET` / `JWT_ISSUER` | مفتاح توقيع الجلسة المحلية، ويجب استبداله بقيمة عشوائية في الإنتاج |
| `EXTERNAL_CRED_KEY` | مفتاح مشتق بـAES-256-GCM لمفاتيح AIPDD / بيانات الإقرار الخارجي، يُهيَّأ منفصلاً دون الرجوع إلى JWT_SECRET |
| `AIPDD_PLATFORM_KEY` | احتياطي النشر لمفتاح AIPDD APIKey على مستوى المنصة (قناة البيانات الأساسية)؛ وبعد الحفظ في الإدارة «تهيئة النظام → مفتاح منصة AIPDD» يُعتمد النص المشفّر في القاعدة |
| `AIWORKIN_BASE_URL` / `AIWORKIN_ENABLED` | عنوان السوق المنبع ومفتاحه (بعد الإغلاق لا تتاح إلا الحلقة المحلية) |
| `CORS_ORIGIN_PATTERNS` | الأصول المسموح بها عبر النطاقات (مفصولة بفواصل) |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD` | بيانات الاعتماد التي يقرأها سكربت `seed-admin` لإنشاء مسؤول المنصة (لا يُنشأ تلقائياً عند البدء) |

> تُخزَّن كل المفاتيح في `.env` المحلي فقط (وهو مُدرج في `.gitignore`)، ولا تعيد أي واجهة أبداً النص الصريح لمفتاح AIPDD.

### توافق قواعد البيانات (MySQL / PostgreSQL)

يُختار أحدهما عند التثبيت، ويُعتمد وقت التشغيل على `DB_PROVIDER` (يُستنتج من بروتوكول `DATABASE_URL` عند الغياب)، والأعمال متكافئة على القاعدتين. ولمعالجة فروق اللهجات أُجري ما يلي:

- **مصدر واحد للحقيقة في المخطط**: يُعتمد `prisma/schema.prisma` (MySQL)، وعند تثبيت PostgreSQL يشتق `scripts/gen-prisma-schema.mjs` بشكل حتمي `schema.postgres.prisma` (`provider=postgresql`، و`@db.TinyInt→@db.SmallInt`، و`@db.DateTime→@db.Timestamp`). ويستخدم MySQL سجل الترحيل، وPostgreSQL `prisma db push`.
- **تزايد رقم المستند**: يفرّع `document-number.ts` بحسب اللهجة——MySQL بـ`INSERT IGNORE`+`LAST_INSERT_ID`، وPostgreSQL بـ`ON CONFLICT DO NOTHING`+`UPDATE … RETURNING`.
- **استخراج عمود JSON**: يولّد `jsonText()` في `common/sql-json.ts` مسار `->>` بحسب اللهجة (PostgreSQL `col->>'key'` / MySQL `col->>'$.key'`)، ويُستخدم في استعلام إزالة التكرار بين المهام للبيانات الكبرى وتنقيب العملاء.
- **أسئلة / مخططات BI**: يُصدر `internalScope()` في `bi/bi.internal.ts` العلامات بحسب اللهجة (PostgreSQL `$1`/`ANY($2::text[])` / MySQL `?`)؛ ويُختار اقتباس معرّفات المخطط في `bi.query.service.ts` بحسب القاعدة الهدف (علامات اقتباس مزدوجة PG / backticks MySQL لقاعدة التطبيق أو المصدر الخارجي).
- **توليد العميل**: يمر `postinstall` عبر `scripts/prisma-generate-auto.mjs`، ويولّد بحسب `DB_PROVIDER`/`DATABASE_URL` بالمخطط الافتراضي أو المشتق، لتفادي استبدال عميل PG بنسخة MySQL عند إعادة تثبيت التبعيات.
- **حالة أحرف اسم المستخدم**: تتبع تسجيل الدخول وقيود الفرادة معياراً **موحّداً بحروف صغيرة** (ترتيب MySQL الافتراضي غير حساس لحالة الأحرف، وPostgreSQL حساس)، ويُخزَّن البريد بحروف صغيرة أيضاً، بما يضمن اتساق سلوك الدخول / التحقق من التكرار على القاعدتين؛ وتبقى الحسابات ذات الأحرف المختلطة القائمة قبل التغيير قابلة للدخول على MySQL (مغطاة في CI)، ويمكن على قاعدة قائمة إعادة التعبئة مرة واحدة بـ`pnpm --filter aiworkin-enterprise-api db:normalize-usernames` (تكافؤي، ويعمل على القاعدتين، وتُتخطى التسميات المتعارضة وتُدرَج).

> فرق معروف: البحث بالنص الحر (كلمة `contains`) غير حساس لحالة الأحرف على MySQL وحساس على PostgreSQL——ولأن `mode:'insensitive'` في Prisma غير مدعوم على موصل MySQL، لا تُوحَّد كل استعلامات البحث قسراً. والمحتوى الرئيسي (الصينية...) خالٍ من حالة الأحرف فلا يتأثر؛ ولتوحيد البحث اللاتيني أيضاً يمكن إنشاء قاعدة PostgreSQL بترتيب ICU غير حساس لحالة الأحرف، أو توحيد الحقول المعنية بحروف صغيرة قبل البحث.

## 🌐 نطاق الموقع (عنوان الوصول الخارجي)

لا يُرمَّز أي عنوان محلي في كل الموقع: نقاط MCP / API، واستدعاءات IM وروابط «معالجة» في البطاقات، وسكربت تضمين خدمة العملاء،
ومداخل الأكواد الجاذبة، وروابط الدعوة، والقيم المقترحة لاستدعاء الدفع، تُركَّب عناوينها المطلقة وفق الأولوية التالية:

1. القيمة المدخلة في «لوحة إدارة المنصة → إعدادات الموقع → نطاق الموقع» (يُقبل http/https فقط، مع إمكانية المنفذ، والسريان فور الحفظ دون إعادة تشغيل)
2. متغير بيئة الخادم `SITE_URL`
3. عنوان الزائر الحالي (`window.location.origin`، ولا يلزم أي إعداد لنشر بنطاق واحد)

في التطوير المحلي لا يلزم إدخال شيء: في التطوير يحوّل وكيل Next `/api/*`، وفي الإنتاج يأخذ Nginx أولاً `/api/*`،
لذا يصلح عنوان مثل `https://نطاقك/api/v1/mcp` في الحالتين.
وبعد تغيير النطاق في الإدارة يُضمّ تلقائياً إلى القائمة البيضاء لـCORS / تحقق المصدر؛ ويظل تغيير متغير `SITE_URL` نفسه يحتاج إعادة تشغيل.

## 🔑 ربط مفتاح AIPDD API Key وقنوات المنبع

- يربط المستخدم مفتاح API (`sk-`) صادراً من منصة AIPDD في قسم «ربط مفتاح AIPDD API Key» بصفحة «خدمات النماذج → إدارة مفاتيح API»؛
  ويمكن لعدة مستخدمين ربط نفس المفتاح (N:1، بالدمج حسب البصمة)، ويُخزَّن النص المشفّر بـAES-256-GCM.
  وقد دُمجت الصفحة المستقلة القديمة «ربط مفتاح AIPDD» (`/developer/aipdd`) في إدارة مفاتيح API، ويحوّل العنوان القديم إلى `/developer/keys`.
  وهاتان الصفحتان (إدارة مفاتيح API / إعدادات النموذج) خدمة ذاتية على مستوى الحساب، و**لا تظهران في الشريط الجانبي تحت هوية مسؤول المنصة**؛ ولتهيئتهما بدّل إلى هوية المؤسسة / الفرد (ويوجد مفتاح مستوى المنصة في «تهيئة النظام → مفتاح منصة AIPDD»)، مع إمكانية الوصول المباشر عبر الرابط.
- ويتولى القسم نفسه دليل التسجيل: بعد إدخال المسؤول رمز إحالة AIPDD في «إعدادات الموقع»، يحصل المستخدم الجديد باتباع الدليل على التسجيل في www.aipdd.work وإدخال هذا الرمز
  على حساب محسوب مهدى (وتعود عمولة الإحالة للمسؤول)؛ ويمكن للمتغير `AIPDD_REFERRAL_CODE` ضبط رمز افتراضي، ولـ`AIPDD_REGISTER_URL` تجاوز عنوان التسجيل (يُقبل http/https فقط).
- `backend/src/common/upstream-token.ts` هو **المدخل الوحيد لبيانات الاعتماد** للوصول إلى المنبع: فلم يعد كود الأعمال يعتبر رمز الجلسة المحلية بيانات اعتماد المنبع،
  بل يستبدله بمفتاح المستخدم المرتبط؛ ويحصل المستخدم غير المرتبط عند إطلاق إجراء منبع على `403` إرشادي (ولا يتأثر النشر المحلي).
- **البيانات الأساسية تمر بمفتاح المنصة لا بمفتاح المستخدم**: البيانات المرجعية كقاموس المحافظات / المدن وعناصر قاموس المنصة، وهي مستقلة عن هوية المستخدم، يهيئها المسؤول في
  «لوحة إدارة المنصة → تهيئة النظام → مفتاح منصة AIPDD» بمفتاح منصة موحّد (بنفس تحقق الصيغة `sk-` والتحقق الحي عبر الإنترنت،
  وتشفير AES-256-GCM في `system_settings.aipdd_platform_key`، ويعيد قناعاً فقط، وله أولوية على متغير `AIPDD_PLATFORM_KEY`،
  ومعزول قراءةً وكتابةً عبر واجهة معاملات النظام العامة). وسلسلة التحليل: مفتاح المنصة → مفتاح المستخدم المرتبط → وإن غابا يتراجع القاموس الإقليمي المحلي المدمج
  (`backend/src/shared/region-dictionary.ts`، والمصدر `GEO_CENTERS`)، فلا يتعطل أي نموذج دون مفتاح منصة، لكن عناصر قاموس المنصة تحتاج مفتاحاً.
- و**إجراءات المستخدم** كالنشر والمزامنة مع المنبع والربط بالموارد تستخدم مفتاحه المرتبط نفسه، دون تأثر بمفتاح المنصة.
- مع `AIPDD_KEY_VERIFY=off` لا يجري الربط تحققاً حياً عبر الإنترنت (مفيد للعرض دون اتصال)؛ وفي النمط المتصل يستدعي التحقق من المنبع.

## 🧪 البناء والاختبار وCI

تعمل الاختبارات الوحدوية للخادم تحت `backend/test/jest-unit.json` (ts-jest)، واختبارات مكونات الواجهة بـVitest + Testing Library (jsdom)، وتشغّل CI إضافةً قوالب البيئة ولقطة OpenAPI وتحقق الرفع والترحيل:

pnpm build                                          # contracts → tsc للخادم → next build للواجهة

- **سقف الكومة في بناء الواجهة**: تمر `build` و`typecheck` و`lint` جميعها عبر `frontend/scripts/with-heap.mjs`، بقيمة افتراضية
  `--max-old-space-size=10240` (فكومة ~4GB افتراضياً تُفضي إلى OOM عند بناء 55 صفحة بارداً أو تشغيل lint واعٍ بالأنواع، برمز خروج 134)؛
  ويمكن تجاوزها بـ`NODE_HEAP_MB`، وتُمرَّر كما هي إن كانت مهيأة صراحة.
- **CI (GitHub Actions)**: تثبيت التبعيات → بناء contracts → خط أساس المسارات والمعمارية (`check-architecture`، مع فحص الاتصال المباشر ببوابة الذكاء الاصطناعي) → قوالب البيئة →
  لقطة OpenAPI → typecheck → **بوابة معايير الكود الصلبة (`pnpm lint`، مع تنسيق prettier)** → اختبارات الخادم → اختبارات مكونات الواجهة → تحقق الرفع →

  (يفشل عند انزياح رقم سطر لأي بند مسجَّل)، وهو موصول في CI (بعد الاختبار الذاتي المقياسي، وقبل بقية البوابات).
- **معيار نهاية السطر**: يضبط `backend/.prettierrc` القيمة `endOfLine: "auto"`، ويُتحقق وفق نهاية السطر القائمة للملف؛ وعلى Windows مع
  `core.autocrlf=true` يُستخرج بـCRLF، بينما فهرس المستودع وCI بـLF، فلا إيجابيات كاذبة على الجانبين. وتبقى بقية خيارات التنسيق قواعد prettier الافتراضية.
- **سكربتات تكامل تعتمد على القاعدة**: `pnpm test:regression` / `test:query-plans` / `test:performance` / `test:geo-recovery`
  تستهدف قاعدة PostgreSQL محلية فارغة تُنشأ مرة واحدة (`createdb` + `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`)،
  وهي غير متوافقة مع لهجة MySQL الافتراضية، وتُبقى للتنفيذ المحلي عند الطلب.

## 🧹 التقليص مقارنةً بالنسخة التجارية المنبع

هذه النسخة المفتوحة ناتج «دمج + إخفاء هوية + توطين»، و**لا تشمل** صراحةً:

- خادم SNS الأصلي بـNestJS والمظهر الأزرق-الأبيض لـaiworkin.com (مع الحفاظ على معمارية المعلومات، وإعادة كتابة كل الأنماط بـAntD)；
- أعمال العملة awcoin (المكافآت / التسوية، إلخ) (فساحة العرض والطلب تعكس حالة المنبع فقط دون عملة؛ وAWcoin في مركز النقاط للعرض فقط)；
- آليات منصة الاستعلام / الطلب بالنيابة عن مفتاح `sk-`، وإصدار `DEV_AUTO_LOGIN` في الموقع، إلخ (وتُوفَّر بيانات العرض عبر `prisma:seed`،
  لكن هويات العرض لا تُدخل بنقرة واحدة، بل يلزم تسجيل محلي عادي)；
- خدمة دليل Java المنبع: وقد صار مصدر البيانات جدول `users` المحلي.
