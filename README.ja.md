**オンラインデモ：<https://enterprise.aiworkin.com>**

**企業サービスワークベンチ**（Hono + Prisma + MySQL + Next.js / Ant Design）と**ビジネスネットワーキング SNS**
（リレーション / フィード / グループ / ダイレクトメッセージ / 職務履歴書 / 需給広場 / 採用）を統合・移植したオープンソースプロジェクト。

単 point ツールではなく、「企業内管理 + 対外顧客獲得 + ビジネス仲介」を揃えた完全な基盤一式です：アカウントとアイデンティティ体系の上に、
まず**公式サイトホーム**（`/`、未ログイン向けランディングページ、上部はログイン / 登録のみ）で訪問者を受け入れ、続いてエグゼクティブダッシュボード、21 のワークベンチ入口（My タスク、エージェント、ワークフロー、ナレッジベース、Workbuddy 企業クラウド、マルチディメンションテーブル、RPA、コンテンツ作成、マーケティングツール、
デジタルアセット、AI メール、CRM、BI、OA、OKR、AI カスタマーサービス、HR ワークベンチ、プロジェクト管理、販売仕入在庫、アプリセンター、テーマホール）、
11 本の業務サービスライン（マーケティング / 供給販売 / 财税 / 越境展開 / 柔軟雇用 / 物流 / IT / 知的所有権 / リーガル / シンクタンク / アセット取引）、ビジネスネットワーキングと採用、
そして 5 大分類に整理された計 26 板块のプラットフォーム管理バックエンド（プラットフォームデータ総覧はダッシュボード `/dashboard` に統合）へと繋がります。すべての SNS・需給機能は**ローカルで閉ループ、Key なしで利用可**；
上流市場（AIworkin）への需要 / サービス発行や、企業档案・資格申請を行うには、AIPDD APIKey を 1 本紐付けるだけで繋がります
——**本システムは暗号資産を扱わず、上流アカウントを託されず、スタイルとインタラクションはすべてローカルで書き直し**。

> デザイン・移行仕様は [`docs/开源版整体设计方案.md`](docs/开源版整体设计方案.md) を参照。

## 📖 機能詳解

### 一、アカウント、アイデンティティとセッション

- **ローカルアカウントの閉ループ**：登録（ユーザー名 / メール / スマホチャネルは選択可）、ログイン、パスワード再設定、バインド変更、退会；ログインログとプラットフォームレベルの BAN を備える。
- **ログイン方式と登録検証**：ログインページは管理画面のスイッチに従って「通常ログイン（アカウント + パスワード）/ メール認証コード / スマホ認証コード / WeChat QR」を動的に渲染；
  登録は管理者が有効にした方式で「ユーザー名 / メール / スマホ番号」を渲染し、メールと SMS 登録は先に認証コード検証を通過する必要がある（メールは SMTP、スマホは Alibaba Cloud SMS の設定が必要で、
  未設定の方式は管理画面で選択できず、フロントにも表示されない）。「30 日間自動ログイン」にチェックするとセッションは 30 日まで延長。
- **WeChat QR ログイン / 登録**：WeChat オープンプラットフォームの「Web サイトアプリ」で QR スキャン；既にバインド済みなら直接ログイン、未バインドで自動登録が有効ならアカウントを作成してバインド（ユーザー名は `wx_<openid 后 8 位>`、
  ニックネームとアバターを取得して予填）、自動登録が無効ならアカウントパスワードまたはメール / スマホ認証コードで本人確認後にバインドへ誘導；QR の `state` はワンタイムで 5 分間有効、
  AppSecret は暗号化保存され、管理画面にはマスクのみ返す。
- **管理画面「システム設定 → アカウントとログイン」**：登録方式、ログイン方式、SMTP、Alibaba Cloud SMS と WeChat のパラメータを一元維持；各チャネルを有効にする前に必ず対応する認証情報を揃える必要がある。
- **ユーザー名とメールの小文字正規化**：MySQL の照合順序は大文字小文字を区別せず、PostgreSQL は区別するため、統一して小文字で保存・重複チェックし、両データベースの挙動を一致させる；既存データベースは
  `pnpm --filter aiworkin-enterprise-api db:normalize-usernames` で冪等にバックフィルできる。
- **本システム自己発行のセッション**：ローカルで発行した SSO セッションのみ受け入れ（issuer は `enterprise-sso`、鍵は `JWT_SECRET` を HKDF で導出）、
  リクエストごとにアカウント状態と `tokenVersion` を照合——パスワード変更、バインド変更、BAN ですぐに失効；上流プラットフォームのトークンは一切拒否。
- **永続化済み成果物の在籍再検証**：過去の公開共有、エクスポートファイルのダウンロード、Chrome プラグイントークン、無人值守の定期タスク、ワークフローの定期 / イベントトリガー、ローコード組織のプロジェクトメンバー資格は、
  いずれも取得時に現在のテーブルで「アカウント状態 + 組織在籍関係」を再検証し、退職や角色変更后就即座に失効（非同期のメンバー削除やキャッシュを待たない）；対外は一律「存在しない / 失効済み」で応答し、失効理由を漏らさない。
- **複数アイデンティティと主体タイプ**：プラットフォーム管理者、企業ユーザー、サービスプロバイダー、サービスプロバイダー従業員（代理人）の 4 アイデンティティ；
  主体は企業、個人工商戸、個人の 3 種。アイデンティティ切替後にサイドバーはアイデンティティに応じて再構成：プラットフォーム管理者はプラットフォーム管理バックエンド
  （ユーザーとサービスプロバイダー / 業務運営監督 / 課金と商品 / 能力とセキュリティ / システムとコンテンツの 5 分類、プラットフォームデータ総覧はエグゼクティブダッシュボード `/dashboard` に直接統合）のみを表示し、
  個人アカウント視点の「管理設定」は含まない。
- **認証と資格**：企業情報は提出後すぐ有効；サービスプロバイダーの登録はプラットフォーム審査が必要；従業員はサービスプロバイダーへのバインドまたは所属が必要。
- **招待コード**：各アカウントに専属の招待コード 1 本、登録時に任意入力で招待関係を構築；「My 招待」は招待コード、登録リンク、誰に招待されたか、招待済み人数を表示；ページヘッダーのアバタードロワー内の「招待登録」から同ページへ直行。

### 二、ダッシュボード

- ページヘッダー右上のショートカット入口：**API Key 管理**、**ポイント充值**、その後にアイデンティティボタン（管理者は「管理バックエンド」、その他は「アイデンティティと資格」）；AIPDD API Key 未バインド時は左端に赤い **AIPDD API Key バインド**が 1 つ追加され、クリックすると「API Key 管理」のバインド板块へ直行、バインド完了後は自動で消える。
- 統計カード：**「My タスク」は常に先頭**（タスクセンターの未処理件数を取得、クリックで `/tasks` へ）、**「有効契約」は常に末尾**、その他ランディングページを持つカードはクリックで直行；アイデンティティごとにカードセットが異なる——企業（My タスク / 処理待ち / OA 承認待ち / 新着メッセージ / 有効契約）、サービスプロバイダー（My タスク / 支援企業 / 処理待ち / OA 承認待ち / 有効契約）、従業員（My タスク / バインド済み組織 / 受託企業 / 処理待ち / OA 承認待ち）、プラットフォーム管理者（My タスク / 処理待ち / 新着メッセージ）。
- 統計カードの直下の最初の板块は**クイックナビ**：デフォルトの常用ナビはカード全体がクリック可能、右上の「設定」で追加 / 削除と並び替えができてアカウント単位で永続化；続いて企業アイデンティティの**成長ダッシュボード**（目標進捗、入金、納品中プロジェクト、顧客獲得転換、カスタマーサービスからリードへの転送）、「My ToDo」（板块別の未完合集計、未開通のサービスカテゴリはアイデンティティに応じて非表示）、**My タスク Top5**（個別にソースモジュールへ飛んで処理）、対応待ちと新着メッセージの概要が並ぶ。
- **「対応待ち」はタスクセンターの `bySource` という一種の基準のみ採用**（`/tasks` と同源）：本人に帰属し現在件数のある項目のみ列挙（公式サイト問い合わせ、OA、CRM、OKR、プロジェクト、ワークフロー、確認待ち契約、プラットフォーム審査）；「私が確認すべきバインド招待」はどのタスクソースにも属さないため、別途 1 行補充。
- プラットフォーム管理者：ダッシュボードがそのままプラットフォームデータ総覧（登録 / 企業 / サービスプロバイダー / 契約 / 各業務伝票と税額）、審査 ToDo（サービスプロバイダー登録）とサービスプロバイダーのサービスタイプ分布；サイドバーから各監督板块へ直接入る。

### 四、業務サービス（11 のサービスライン + 需給市場）

統一形態：**サービスプロバイダーリソースライブラリ**（一覧閲覧 → 詳細 → 契約開始）+ **需要情報 / サービス市場** + **業務台帳**。
サービスプロバイダーはまず登録を完了し対応するカテゴリ資格を通過して初めて、リソースが外部へ表示される；ある板块のサービスプロバイダーが 1 社だけの場合は一覧を表示せず、その詳細を直接埋め込み。
需給市場は板块横断の公開市場で、板块登録のゲーティングを設けない；需要 / サービスの両一覧はいずれも**ページ表示**（無限スクロールはしない）、
**地域（省 / 市）と二次カテゴリ**でフィルタ可能で、カテゴリ列（一次 / 二次）は行随で表示；2 つの一覧の他に別途**評価**タブ（評価分布、評価台帳）があり、評価データはサービスプロバイダー表示スコアのソースも兼ねる。

各サービス市場と需給市場の**需要 / サービス**一覧には、もう 1 対のフィルタ「**すべて（需要 / サービス）** / **自分が発行者**」がある：
「すべて」は AIworkin の対応カテゴリ公開プールを直接読む；「自分が発行者」は本システム台帳を読む（発行動作はまずローカルへ登記し、
その後プラットフォームへ同期してプラットフォームのコンテンツ ID を記録）。2026-11-09 のユーザー基準により、「自分が発行者」は**サービスプロバイダーアイデンティティに対してのみ渲染**、
企業アイデンティティには当該フィルタを一切表示しない（「すべて」のみ）。AIworkin へ正式発行済みのレコードは本システムで変更・削除せず、
「閲覧」のみ残す——プラットフォームの REST 書き込み API（PATCH / DELETE）は API Key に対して一律 401、MCP にも変更・削除ツールはない。
**サービス市場**（物流 / マーケティング / 越境展開 / 柔軟雇用 / IT / 知的所有権 / リーガル / シンクタンク / アセット / 供給販売 / 财税）のメニューキーはいずれも「××サービス市場」で、
本文は同一条目：全サービス＝プラットフォーム公開プール、自分が発行者のサービス＝ローカル台帳；供給販売ネットワーク / 财税サービスは 2026-11-09 に
「サービス発行」から改名・統合（ユーザー：「他の市場と統一し、公開プールも自分のサービス発行も見えるように」）。
**供給販売ネットワークの市場タブは企業側にも表示**（2026-11-09）：市場は全站で閲覧可能、企業はサービス発行ができないだけ——
「サービス発行」入口はアイデンティティにより非表示、「自分が発行者のサービス」フィルタも出ず、バックエンドの `assertPublishAllowed` も同じ基準で遮断。

  発行時は現在アカウントのバインド済み AIPDD API Key でプラットフォームへ直接書き込みローカルに台帳を残す、発行内容は同様に Alibaba Cloud コンテンツ安全の自動審査を経由；
  プラットフォームへ発行済みのレコードは本システムで変更・削除できず、「閲覧」のみ残す。

### 五、ビジネス人脈（SNS / 採用 / 需給）

- **ビジネスネットワーキング**：同行者とつながる（フレンド / ブロック）、フィードの公開（公開 / フレンド限定）、douban 風グループ（発見 / グループ参加、カテゴリ別投稿、
  1 件ごとの匿名、フロア返信と推荐、グループ管理者 / 運営によるトップ固定・精华と参加審査）、站内ダイレクトメッセージ、職務履歴書（主页と分岐した独立 HTML ページ、
  メッセージ内で提出でき、雇用主はクリックして即閲覧し PDF へ書き出し）。アカウントが BAN されると SNS 機能は自動で遮断。
- **採用**：正社員 / パート / インターン / 臨時 / 労働派遣の求人を発行して採用広場のフィードに入れ、站内ダイレクトメッセージで対応（履歴書を添付可）、
  本システムは ATS の履歴書データベースと選抜を行わない；AIPDD Key バインド済みなら求人を AIworkin の労務需要として同期できる（カテゴリは固定で「柔軟雇用」サブツリーを採用）。
- **需給広場**：需要 / サービスを汎用発行してローカルフィードに入れ、閲覧とダイレクトメッセージ対応が可能。
  **二段式発行**が本プロジェクトの中核基準：デフォルトはローカルで Key なし発行；「AIworkin へ同期発行」にチェックすると、
  統一認証情報リゾルバ経由でユーザーのバインド済み Key を使い上流の `POST /market/listings` を呼び、上流の審査 / 撤回ステータスを反映。

### 八、モデルサービス

- **API Key 管理**：2 種の Key を分けて管理——本システムの `ek_` Key は开放インターフェース（`/api/v1`）とモデル広場の呼び出し用で、生成 / コピー / リセット / 失効はすべて本ページ、
  各 Key には個別に「ポイント額度」を設定可能（対外呼び出しの累計消費上限、超過すれば拒否、上限なしも選択可）；
  AIPDD API Key（`sk-`）も同ページでバインドし、同期発行、サービスプロバイダーデータ同期、リソース開拓などの上流機能を解放。Key は暗号文で保存され、本人のみ本ページでいつでもコピーでき、他者には見えない。
- **モデル広場**（`/model-plaza`）：プラットフォームが統一上架した利用可能モデルのカタログ——課金単位は上流と一致（会話 / ベクトルは Token、画像は枚、動画と音声認識は秒、テキスト読み上げは回）、
  オンライン試用と用量台帳の確認ができ、`ek_` Key で OpenAI 互換ゲートウェイへ；カタログ、上流チャネルと価格設定は管理画面「課金と商品 → モデル広場」で維持。
  管理画面には別途「既定モデル」タブ：テキスト / ビジュアル / 画像 / 動画 / 音声認識 / 音声合成 / ベクトルそれぞれにプラットフォームの既定モデルを指定し、1 回・1 日・1 月のポイント上限を設定して変更記録を保全；
  真实充值が着金したユーザーは、個別未設定の能力について自動で継承（支払済み充值注文のみ認識、赠送と調整は対象外）、呼び出しはカタログ価格で本人のポイントから控除。
- **API-MCP-Skill**（`/developer/api-mcp-skill`）：モデルサービスの統一入口、3 タブはこの順——
  **Skill**：プラットフォーム管理者が業務ドメイン別に生成したスキルパッケージのリスト（名称、説明、業務ドメイン、カバーアクション数、生成モデル、更新時刻）、「ダウンロード」で zip を取得；
  パッケージ内は呼び出し説明とサンプルのみで実際の Key を含まず、同名スキルを再生成すると旧パッケージを上書き、リストとダウンロードは同一メニューのスイッチに従う。
  **MCP Server**：Codex、Claude Desktop、Cursor、自作スクリプトと Workbuddy が同一の API Key で接続；
  サーバーはまず本アカウントのエージェントメモリを分析し、認可に従って本站アクションを自動実行。インターフェースリストは契約層から派生し、新規モジュール（ERP 販売仕入在庫、SEO ワークベンチ、AI 顧客獲得、WeCom SCRM、プロジェクトタスク、HRM など）が契約に入れば自動で `list_operations` に入る；
  承認結論、資金の回収・支払、在庫流水のように直接帳簿を動かすアクション（ERP の在庫 / 購買 / 入庫 / 経費承認、消込回収・支払、入出庫流水を含む）は恒久的な除外リストに載せ、本人が画面上で確認するしかない。
  **API**：本システムが実際に外部へ提供するインターフェース一覧、契約層から派生し、MCP サーバーの `list_operations`、OpenAPI ドキュメントと同源。
  旧アドレス `/developer/docs`、`/developer/mcp` はリダイレクトを保持し、それぞれ `?view=api` と `?view=mcp` に落ちる。
- **モデル設定**：エージェントとコンテンツ作成が共用するモデル設定——AIPDD 内蔵チャネルは sk- Key を直接使い、他の OpenAI 互換ゲートウェイや火山 MediaKit も接続可、タイプごとに既定モデルを選択；
  ページ上部に「プラットフォーム既定モデル」の現在の有効状況（個人未設定時は充值資格で継承）と本日 / 今月の使用済み額度を表示。
  プラットフォーム管理者は「モデル広場 → ユーザーチャネル」で各算力チャネルのサポート範囲を設定（デフォルトは全てサポート）：閉じたチャネルはユーザーが追加 / 変更できず、選択もできない；
  AIPDD を閉じるとその算力だけを停止（モデル設定 / モデル広場）、他の機能（業務サービスなど）は同一の AIPDD API Key で引き続き通常利用可。
- **プラットフォーム機構**：§5.8 の横断能力の統一入口——イベント Outbox と Webhook 購読（テスト、配信記録、失敗時の再投函；イベントカタログはタスク、プロジェクト、CRM リード / 注文 / 入金、外部公開需要、外部協力などの業務ノードをカバー）、CSV インポート（フィールドマッピング、试运行、マッピング方案の再利用）とモジュール別エクスポート（エクスポートファイルは長期の公開直リンクを廃し、ログイン状態の API が現在の組織で権限を再検証して返送）、レポートカタログ、ルールエンジン（条件マッチ + Webhook / 通知 / インサイト / タスク作成の呼び出し）、公開共有（パスワード、有効期限、停止；開くたびに発起人の在籍資格を再検証し、発起人の退職 / 組織外への移動で失効）、OIDC アイデンティティソース（発見テスト、自動アカウント作成）、添付ファイル共有戦略、Feishu / WeCom の連絡先、勤怠とカードメッセージ同期、条項接受の保全（新バージョン未接受時は全站でリマインド）、プロダクト使用トラッキング（ページ / アクションのイベントと集計ダッシュボード）と主体切替器（同一自然人が企業 / サービスプロバイダーを跨いで HRM スコープを切替）、ページ認識コパイロット（全站フロート入口）。全站の業務タブは統一して折返しカプセル（`PanelTabs` / `TabStrip`）とし、antd Tabs と混在させない。
- **ヘルプセンター**：`/help` の章立てナレッジベースはコードと共にバージョン管理（ナレッジファイルは `backend/src/help`）、各モジュールの使い方をカバー；同一ページには別途「更新履歴」タブでプロダクトレベルの changelog を表示；ナレッジ本文は MCP の `Help_chapters / Help_topic / Help_search` の 3 つの読み取り専用アクションで開放し、ユーザーが直接エージェントに聞いても公式の使い方を得られる。
- **OpenAPI スナップショット**：`/api/openapi.json`（1947 の操作）、CI でスナップショットと契約層の一致を検証。

### 九、スマートハードウェア

サイドバー独立の**スマートハードウェア**板块（一次グループ、管理設定の後）：ユーザーはハードウェアと開発パッケージを閲覧し、手持ちのデバイスをプラットフォームへ接続し、ハードウェアタイプに応じて**専用**の MCP ツール（エージェント制御）と API（プログラム制御）を呼び出す；プラットフォーム管理者は型号カタログ、開発パッケージバージョンと型号既定ツールを維持。

- **ハードウェア広場**（`/hardware`）：型号カタログを推荐 / 並び替えで表示、各型号に仕様、開発パッケージバージョン（安定 / プレビューチャネル）とダウンロードを提供；開発パッケージのバイナリは本站 OSS へ直接アップロードし、ダウンロード時に計数、ページには SHA-256 を検証用に掲載；型号詳細に入ると当該型号の既定 API / MCP ツールリストを確認できる。
- **ハードウェア追加**（`/hardware/devices`）：型号を選択してデバイスを接続、`hw_` プレフィックスのデバイストークンを生成（平文は生成の瞬間に一度だけ表示、データベースには SHA-256 のみ保存）；デバイス開発パッケージ内の SDK / ファームウェアでサービスアドレスとトークンを設定すれば心跳でオンライン化、一覧はオンライン / オフライン / 未報告の 3 種ステータスで表示（180 秒を超えて心跳なしならオフラインへ移行）、デバイス別に心跳 / 指令 / 回执の流水を調べて問題排除可能。
- **ハードウェアMCP**（`/hardware/mcp`）：独立したハードウェア MCP サーバー `aiworkin-hardware-mcp`（エンドポイントは `/api/v1/hardware/mcp`）、プラットフォームの MCP と完全分離——ツールはハードウェアツールテーブルのみに由来し、命名は `hw__<型号コード>__<ツールコード>`、「開発者 → API Key」の `ek_` Key で認可。書き込みツールは 3 層の認可ゲートを経る：本ページで「自動実行可」に未チェック、無人值守の定期タスク由来、または呼び出し側が dryRun を宣言した場合は、一律ドラフトのみ返し、実際に下发しない；本人の「テスト呼び出し」はこの制限を受けない。
- **ハードウェアAPI**（`/hardware/api`）：同じ一群のツールを `ek_` Key で `/api/v1/hardware/**` のマシンチャネルへ、`curl` だけで列挙と呼び出しが可能；ツールのパラメータとレスポンスはページ掲載の JSON サンプルを基準とする。
- **開発パッケージ（Dev Kit）**：リポジトリ直下の `hardware-devkit/` に直接コンパイルして実行できる SDK とサンプルを提供——ESP32 の ESP-IDF コンポーネント、Jetson / Raspberry Pi の純標準ライブラリ Python パッケージ、2 つの実行可能サンプル、加えてゼロ依存の Node シミュレーションデバイス（ハードウェアなしで「心跳 → 指令取得 → 回执」の完全な閉ループを回せる）とフィールド別プロトコルドキュメント；プリコンパイル済みファームウェアは首批実機コンパイル後に補充予定。
- **管理画面の維持**：プラットフォーム管理者の「スマートハードウェア」板块は「ハードウェア型号 / 開発パッケージ / 既定ツール」の 3 タブ——型号カタログの維持、各バージョンの開発パッケージアップロード、型号別の既定 API / MCP ツール維持で、変更後はユーザー側に即反映。ユーザー自作のツールは本人のみ閲覧・利用可能で、型号既定ツールには入らず、初版はマーケットにも上架しない。

デバイスチャネル（`/api/public/hardware/heartbeat`、`/commands`、`/result`）はデバイストークンのみ認可し、ログイン不要、**意図的に機能スイッチの遮断を受けない**：管理者が「スマートハードウェア」板块を閉じても、接続済みデバイスの心跳は途絶えない。

## 🚀 クイックスタート（ローカル開発）

前提：Node ≥ 24、pnpm ≥ 10、アクセス可能な **MySQL 8 または PostgreSQL** インスタンス（いずれか 1 つ）。

### 方法 A：ワンクリックインストール（推荐、データベースは選択可）

```bash
pnpm install
pnpm setup            # インタラクティブ：MySQL / PostgreSQL を選択 → 接続情報を入力 → backend/.env へ書き込み → クライアント生成 → テーブル作成
# または非対話：pnpm setup --db postgres --host 127.0.0.1 --port 5432 --user app --password *** --database enterprise --yes
pnpm dev:api & pnpm dev:web
```

`pnpm setup` の処理：① `backend/.env` に `DATABASE_URL` と `DB_PROVIDER` を書き込む；② MySQL はマイグレーション履歴で `prisma migrate deploy`、PostgreSQL は `schema.prisma` から `schema.postgres.prisma` を派生して `prisma db push`；③ 選択した方言で Prisma Client を生成。

> Prisma の Client とテーブル作成ステートメントは方言ごとに生成：データベース切替後は `pnpm setup`（または `pnpm --filter aiworkin-enterprise-api prisma:generate:pg`）を再実行すればよい。

```bash

# 2) バックエンドの環境変数を設定
```

### データベース互換性（MySQL / PostgreSQL）

システムのインストール時にいずれかを選択し、実行時は `DB_PROVIDER`（未指定時は `DATABASE_URL` のプロトコルから推定）を基準とし、業務は 2 種のデータベースで等価に動作する。方言差をならすため以下の処理を済ませている：

- **Schema の単一真実源**：`prisma/schema.prisma`（MySQL）を基準とし、PostgreSQL インストール時は `scripts/gen-prisma-schema.mjs` が決定論的に `schema.postgres.prisma` を派生（`provider=postgresql`、`@db.TinyInt→@db.SmallInt`、`@db.DateTime→@db.Timestamp`）。MySQL はマイグレーション履歴でテーブル作成、PostgreSQL は `prisma db push` を実行。
- **伝票番号の自動採番**：`document-number.ts` が方言で分岐——MySQL は `INSERT IGNORE`+`LAST_INSERT_ID`、PostgreSQL は `ON CONFLICT DO NOTHING`+`UPDATE … RETURNING`。
- **JSON 列の値取得**：`common/sql-json.ts` の `jsonText()` が方言ごとに `->>` パスを生成（PostgreSQL は `col->>'key'` / MySQL は `col->>'$.key'`）、ビッグデータの取得、リード発掘のタスク横断重複排除クエリに使用。
- **BI クエリ / チャート**：`bi/bi.internal.ts` の `internalScope()` が方言ごとにプレースホルダを下发（PostgreSQL は `$1`/`ANY($2::text[])` / MySQL は `?`）；`bi.query.service.ts` のチャート識別子の引用符は対象データベースで選択（PG はダブルクォート / MySQL はバックスラッシュ）。
- **クライアント生成**：`postinstall` は `scripts/prisma-generate-auto.mjs` を実行、`DB_PROVIDER`/`DATABASE_URL` に応じて既定または派生 schema を自動選択して生成し、依存再インストール時に PG クライアントが MySQL 版で上書きされるのを回避。
- **ユーザー名の大文字小文字**：ログインと一意制約は**小文字正規化**で基準を統一（MySQL はデフォルトの照合順序で大文字小文字を区別せず、PostgreSQL は区別）、メールも小文字で保存し、両データベースのログイン / 重複チェックの挙動を一致；変更前に存在した混在大小文字のアカウントは MySQL では引き続き正常にログイン可能（CI がヒット）、既存データベースでは `pnpm --filter aiworkin-enterprise-api db:normalize-usernames` を一度実行してバックフィル（冪等、両データベース共通、名前衝突時はスキップして一覧で通知）。

> 既知の差異：自由テキスト検索（`contains` キーワード）は MySQL では大文字小文字を区別せず、PostgreSQL では区別——Prisma の `mode:'insensitive'` は MySQL コネクタで未サポートのため、全ての検索ステートメントを強制的に統一しない。中国語などの主コンテンツは大小文字を含まないため影響なし；ラテン文字検索でも挙動を揃えたい場合は、PostgreSQL 側で大文字小文字を区別しない ICU 照合順序でデータベースを作成するか、該当フィールドを小文字正規化してから検索すること。

## 🐳 Docker Compose（MySQL 同梱）

リポジトリ直下の `docker-compose.yml` は **MySQL + バックエンド + フロントエンド** の 3 サービスをオーケストレーション、ワンクリック体験向け：

```bash
# 全サービスの依存にローカルのデモ既定値を内包（${VAR:-default}）、そのまま起動可能：
docker compose up --build
# パスワード / ドメインをカスタムする場合はリポジトリ直下に .env を作成して MYSQL_* / JWT_SECRET / EXTERNAL_CRED_KEY などを上書き
# バックエンド http://localhost:1690  フロントエンド http://localhost:15890
```

初回起動時にバックエンドは自動で `prisma migrate deploy` を実行してテーブルを作成。初回起動後はコンテナ内でプラットフォーム管理者を作成する必要がある（compose は
`ADMIN_USERNAME` / `ADMIN_PASSWORD` を注入済み、デフォルトは `admin` / `admin-Startup-2026`、リポジトリ直下の `.env` で上書き可）：

```bash
docker compose exec api pnpm --filter aiworkin-enterprise-api exec tsx scripts/seed-admin.ts
```

本番デプロイでは `JWT_SECRET` / `EXTERNAL_CRED_KEY`
を強いランダム値に置き換え、独立したデータベースとリバースプロキシを使用すること（`infra/nginx/` にサンプル設定あり）。

## 🌐 サイトドメイン（対外アクセスアドレス）

全站で本機のアドレスをハードコードしない：MCP / API の接続エンドポイント、IM 回调とカードの「処理へ」リンク、オンライン客服の埋め込みスクリプト、
ライブコード入口、招待リンク、決済回调の推奨値などの絶対アドレスは、統一して以下の優先度で組み立てる：

1. 「プラットフォーム管理バックエンド → サイト設定 → サイトドメイン」に入力した値（http/https のみ認識、ポート付き可、保存即反映、再起動不要）
2. バックエンドの環境変数 `SITE_URL`
3. 訪問者の現在のアクセスアドレス（`window.location.origin`、単一ドメインデプロイなら設定不要）

ローカル開発では一つも入力不要：開発時は Next が `/api/*` をリバースプロキシし、本番では Nginx が先に `/api/*` を取得
するため、`https://あなたのドメイン/api/v1/mcp` のようなエンドポイントは両形態で成立。
管理画面でドメインを変更すると、当該ドメインは自動で CORS / 由来検証のホワイトリストに編入；`SITE_URL` 変数自体の変更は依然再起動が必要。

## 🔑 AIPDD API Key のバインドと上流チャネル

- ユーザーは「モデルサービス → API Key 管理」ページの「AIPDD API Key バインド」板块で、AIPDD プラットフォーム発行の API Key（sk-）を 1 本バインド；
  複数ユーザーが同一の Key をバインド可能（N:1、フィンガープリントで統合）、暗号文は AES-256-GCM でデータベースへ保存。
  旧独立ページ「AIPDD Key バインド」（`/developer/aipdd`）は API Key 管理へ統合済み、旧アドレスは `/developer/keys` へリダイレクト。
  この 2 ページ（API Key 管理 / モデル設定）はアカウント単位のセルフサーブで、**プラットフォーム管理者アイデンティティではサイドバーに表示されない**、設定する場合は企業 / 個人アイデンティティへ切替ること（プラットフォームレベルの Key は「システム設定 → AIPDD プラットフォーム Key」）、リンクへの直接アクセスは引き続き可能。
- 同一板块は登録誘導も担当：管理者が「サイト設定」に AIPDD 推荐コードを入力すると、新規ユーザーは誘導に従い www.aipdd.work で登録し当該コードを入力
  すれば算力をプレゼント（招待手数料は管理者に帰属）；env の `AIPDD_REFERRAL_CODE` でデフォルトコードを設定、`AIPDD_REGISTER_URL` で登録アドレスを上書き可能（http/https のみ認識）。
- `backend/src/common/upstream-token.ts` は上流アクセスの**唯一の認証情報入口**：業務コードはローカルセッショントークンを上流の認証情報として使わず、
  ユーザーのバインド済み Key に置き換える；未バインドユーザーが上流动作を実行すると誘導付きの `403` を返す（ローカル発行は影響を受けない）。
- **基礎データはプラットフォーム Key を使い、ユーザー Key を使わない**：省・市ディクショナリ、プラットフォームのディクショナリ項目のような参照データはユーザーアイデンティティと無関係で、管理者が
  「プラットフォーム管理バックエンド → システム設定 → AIPDD プラットフォーム Key」でプラットフォーム Key を 1 本統一設定（同じ `sk-` 形式検証とオンライン真偽確認、
  AES-256-GCM の暗号文を `system_settings.aipdd_platform_key` に保存、マスクのみ返し、env の `AIPDD_PLATFORM_KEY` より優先度が高く、
  汎用システムパラメータ API の読み書き分離 대상）。解決チェーン：プラットフォーム Key → 本人のバインド済み Key → どちらも無い場合は地域はローカルの内蔵省・市ディクショナリへフォールバック
  （`backend/src/shared/region-dictionary.ts`、データソースは `GEO_CENTERS`）、そのためプラットフォーム Key 未設定でもフォームは止まらないが、
  プラットフォームのディクショナリ項目には依然 Key が必要。
- 需要発行、上流同期、リソース開拓などの**ユーザー動作は引き続き各自のバインド済み Key を使用**し、プラットフォーム Key の影響を受けない。
- `AIPDD_KEY_VERIFY=off` の場合、バインド時にオンライン真偽確認を行わない（オフラインデモ向け）；オンラインモードに設定すると上流を呼び出して検証する。

## 🧪 ビルド、テストと CI

バックエンドのユニットテストは `backend/test/jest-unit.json` の下で実行（ts-jest）、フロントエンドのコンポーネントテストは Vitest + Testing Library（jsdom）、CI は別途環境テンプレート、OpenAPI スナップショット、アップロードとマイグレーションを検証：

```bash
pnpm --filter aiworkin-enterprise-api test          # バックエンドユニットテスト（102 スイート / 862 ケース通過、15 ケースは環境によりスキップ）
pnpm --filter aiworkin-enterprise-web test          # フロントエンドコンポーネントテスト（目標書 / AI 拆解 / 顧客 360 / プロジェクト 360）
pnpm test:uploads                                   # 添付と請求書画像のアップロード検証
pnpm test:environment                               # デプロイテンプレートと環境変数の基準
pnpm api:docs:check                                 # OpenAPI スナップショットが契約層と一致するか
pnpm lint                                           # コード規約 + prettier 整形、CI のハードゲート
pnpm build                                          # contracts → バックエンド tsc → フロントエンド next build
```

- **フロントエンドビルドのヒープ上限**：`build`、`typecheck` と `lint` は統一して `frontend/scripts/with-heap.mjs` を経由、デフォルトは
  `--max-old-space-size=10240`（デフォルトの約 4GB ヒープでは 55 ページのコールドビルドや型認識 lint 実行時に OOM、終了コード 134）；
  `NODE_HEAP_MB` で上書き可、明示設定時は透過。
- **CI（GitHub Actions）**：依存インストール → contracts ビルド → アーキテクチャとルートベースライン（`check-architecture`、AI ゲートの直結チェックを含む）→ 環境テンプレート →
  OpenAPI スナップショット → typecheck → **コード規約のハードゲート（`pnpm lint`、prettier 整形を含む）** → バックエンドユニットテスト → フロントエンドコンポーネントテスト → アップロード検証 →
  **MySQL 8 の空データベースで `prisma migrate deploy` を実行（0001→0052）** → フロント・バックエンドのビルド。
- **型のエスケープベースライン**：`pnpm audit:escapes` が `docs/escape-report.md` / `docs/escape-report.json` を生成；
  `pnpm check:escape-budget` は `.escape-budget.json`（総数と分類は下がるばかりで上がらない）と `.escape-allowlist.json`
  （登記済み条目の行番号がずれたら失敗）で把門、CI に接続済み（計測ツール自身のテストの後、他のゲートの前）。
- **行末の基準**：`backend/.prettierrc` は `endOfLine: "auto"`、ファイル既存の行末で検証；Windows では
  `core.autocrlf=true` で CRLF にチェックアウト、リポジトリのインデックスと CI は LF のため、両側とも誤検出しない。他の整形項目は引き続き prettier のデフォルトルール。
- **データベース依存の統合スクリプト**：`pnpm test:regression` / `test:query-plans` / `test:performance` / `test:geo-recovery`
  は本機の PostgreSQL の使い捨て空データベース向け（`createdb` + `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`）、
  デフォルトの MySQL 方言と非互換のため、ローカルで必要な時に実行する形のまま維持。
- **スモークスクリプト**（PowerShell、純 ASCII、ランダムユーザー名で冪等を保証）：

```powershell
pwsh scripts/smoke-m5.ps1   # SNS 板块の閉ループ（リレーション/フィード/グループ/ダイレクトメッセージ/履歴書/BAN 継承）
pwsh scripts/smoke-m6.ps1   # 需給広場：ローカルの Key なし発行 + Key 未バインド時は上流同期 403
pwsh scripts/smoke-site-url.ps1            # サイトドメインの正規化 / CORS / 公開エコー + ページ 200
pwsh scripts/smoke-aipdd-platform-key.ps1  # プラットフォームの AIPDD Key：暗号文を外部に出さない + 地域ディクショナリのフォールバック
```

## 🧹 上流商用版に対するトリミング

本オープンソース版は「統合 + 秘匿化 + ローカル化」の成果物で、明確に**含まれない**もの：

- SNS 原版の NestJS バックエンドと aiworkin.com の青白ビジュアル（情報アーキテクチャは保持、スタイルは全て AntD に書き直し）；
- awcoin の報酬 / 決済など暗号資産関連の業務（需給広場は上流ステータスを反映するだけで暗号資産を扱わない；ポイントセンターの AWcoin は読み取り専用表示のみ）；
- プラットフォームによる `sk-` Key の代行取得 / 代行申請、`DEV_AUTO_LOGIN` によるその場発行などの機構（デモデータは `prisma:seed` で提供されるが、
  デモアイデンティティはワンクリックログインできず、通常どおりローカル登録が必要）；
- 上流の Java ディレクトリサービス：データソースはローカルの `users` テーブルへ変更。
