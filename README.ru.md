**Онлайн-демо: <https://enterprise.aiworkin.com>**

Открытый проект, объединивший и портированный из двух систем: **корпоративный workbench**
(Hono + Prisma + MySQL + Next.js / Ant Design) и **деловая социальная сеть SNS**
(контакты / лента / группы / личные сообщения / резюме / площадка спроса и предложения / найм).

Это не точечный инструмент, а полноценная база «внутреннее управление + внешнее привлечение клиентов + бизнес-мэтчинг». Над системой аккаунтов и идентичностей,
сначала **главная страница сайта** (`/`, лендинг для неавторизованных гостей, в шапке только «Вход / Регистрация») принимает посетителей, далее открываются кабинет руководителя, 21 вход в workbench (Мои задачи, Agent, рабочие процессы, база знаний, корпоративное облако Workbuddy, многомерные таблицы, RPA, создание контента, маркетинговые инструменты,
цифровые активы, AI-почта, CRM, BI, OA, OKR, AI-служба поддержки, HR-workbench, управление проектами, склад/закупки/продажи, центр приложений, зал тематических обсуждений),
11 бизнес-сервисных линий (маркетинг / поставки-сбыт / налоги и финансы / выход на глобальный рынок / гибкая занятость / логистика / IT / интеллектуальная собственность / юридические услуги / think tank / операции с активами), деловая социальная сеть с наймом,
а также административная панель платформы из 26 разделов, сгруппированных в 5 категорий (обзор данных платформы объединён с кабинетом руководителя `/dashboard`). Все социальные функции и функции спроса/предложения работают **полностью локально и доступны без ключей**;
когда нужно публиковать запросы или услуги на вышестоящем рынке (AIworkin), вести профиль предприятия и подавать заявки на квалификацию — достаточно привязать один AIPDD APIKey.
— **эта система не связана с криптовалютами, не хранит вышестоящие аккаунты, а стили и интеракции полностью переписаны локально**.

> Спецификации дизайна и миграции — в [`docs/开源版整体设计方案.md`](docs/开源版整体设计方案.md).

## 📖 Подробное описание функций

### 1. Аккаунты, идентичность и сессии

- **Локальный контур аккаунтов**: регистрация (на выбор — каналы username / email / телефон), вход, восстановление, смена пароля, перепривязка, удаление аккаунта; журнал входов и платформенные блокировки.
- **Способы входа и верификации регистрации**: страница входа динамически рендерит по тумблерам панели «обычный вход (аккаунт + пароль) / код по email / код по телефону / сканирование WeChat»;
  регистрация рендерит «имя пользователя / email / телефон» по способам, включённым администратором; для email- и SMS-регистрации сначала требуется проверка кода (для email нужен SMTP, для телефона — Alibaba Cloud SMS,
  способы с невыключенным каналом нельзя отметить в панели, и они не показываются на сайте). Галочка «Автологин в течение 30 дней» продлевает сессию до 30 дней.
- **Вход и регистрация через сканирование WeChat**: сканирование «web-приложения» открытой платформы WeChat; привязанный аккаунт входит сразу; непривязанный при включённой авторегистрации создаётся и привязывается (имя пользователя `wx_<последние 8 символов openid>`,
  подтягиваются ник и аватар для предзаполнения); при выключенной авторегистрации предлагается подтвердить личность обычным аккаунтом и паролем или кодом email / телефона, после чего привязать; `state` сканирования одноразовый, действует 5 минут;
  AppSecret хранится шифрованным, в панель отдаётся только маска.
- **Панель «Системные настройки → Аккаунт и вход»**: централизованное ведение способов регистрации и входа, SMTP, SMS Alibaba Cloud и параметров WeChat; перед включением канала необходимо полностью настроить его учётные данные.
- **Нормализация имён пользователей и email в нижний регистр**: в MySQL сортировка регистронезависимая, в PostgreSQL — зависимая от регистра; для одинакового поведения обеих СУБД хранение и проверка дублей в нижнем регистре; для существующих баз доступна
  идемпотентная дозаполровка `pnpm --filter aiworkin-enterprise-api db:normalize-usernames`.
- **Собственные сессии сайта**: принимаются только локально выпущенные SSO-сессии (issuer `enterprise-sso`, ключ выводится из `JWT_SECRET` через HKDF);
  каждый запрос сверяет статус аккаунта и `tokenVersion` — при смене пароля, перепривязке или блокировке сессия гаснет мгновенно; токены вышестоящих платформ отвергаются целиком.
- **Проверка реестра для уже сохранённых артефактов**: старые публичные ссылки, скачивание экспортированных файлов, токены Chrome-плагина, периодические задачи без присмотра, триггеры рабочих процессов по расписанию / событиям, членство в lowcode-проектах организации — перед каждым использованием заново проверяются по текущим таблицам «аккаунт активен + состоит в организации», после увольнения или смены роли всё мгновенно теряет силу (не дожидаясь асинхронной чистки участников проекта или кэшей); наружу единый ответ «не существует / недействительно», причина потери силы не раскрывается.
- **Мультиидентичность и типы субъектов**: четыре идентичности — платформенный администратор, пользователь предприятия, поставщик услуг, сотрудник (представитель) поставщика;
  субъекты трёх видов — предприятие, индивидуальный предприниматель, частное лицо. После переключения идентичности боковая панель перестраивается по ней: платформенный администратор видит только панель управления платформы
  (пять групп — пользователи и поставщики / надзор за бизнес-операциями / биллинг и товары / возможности и безопасность / система и контент; обзор данных платформы напрямую объединён с кабинетом руководителя `/dashboard`)
  и не видит «Администрирование» из личного аккаунта.
- **Верификация и квалификации**: данные предприятия действуют сразу после отправки; регистрация поставщика требует проверки платформой; сотрудник должен быть привязан или аффилирован с поставщиком.
- **Приглашающие коды**: у каждого аккаунта персональный приглашающий код; указание при регистрации создаёт приглашательскую связь; «Мои приглашения» показывает код, ссылку регистрации, кто пригласил вас и сколько людей приглашено вы; в выпадающем меню аватара в шапке «Пригласить на регистрацию» ведёт прямо на эту страницу.

### 2. Кабинет руководителя

- Быстрые входы в правом верхнем углу шапки: **Управление API-ключами**, **Пополнение баллов**, за ними — кнопка идентичности (для администратора «Панель управления», для остальных идентичностей «Идентичность и квалификации»); пока ключ AIPDD API не привязан, слева появляется дополнительная красная кнопка **Привязка AIPDD API Key**, ведущая прямо в блок привязки страницы «Управление API-ключами»; после привязки она исчезает.
- Статистические карточки: **«Мои задачи» всегда первая** (берёт число нерешённых из центра задач, клик ведёт в `/tasks`), **«Действующие контракты» всегда последняя**; остальные карточки с собственными страницами кликабельны и ведут прямо туда; у каждой идентичности свой набор карточек — предприятие (мои задачи / дела / OA-согласования / новые сообщения / действующие контракты), поставщик (мои задачи / обслуженные предприятия / дела / OA-согласования / действующие контракты), сотрудник (мои задачи / привязанная организация / порученные предприятия / дела / OA-согласования), платформенный администратор (мои задачи / дела / новые сообщения).
- Первый блок под карточками — **быстрая навигация**: по умолчанию показываются часто используемые переходы, целая карточка кликабельна; справа сверху через «Настройки» можно добавлять / убирать и переставлять, порядок сохраняется на уровне аккаунта; далее идут **дашборд роста** для предприятия (прогресс целей, поступления, проекты в работе, конверсия лидов, поддержка→лиды), «Мои дела» (сумма незавершённого по разделам; недоступные по идентичности категории услуг скрыты), **Топ-5 моих задач** (каждая позиция ведёт в исходный модуль), обзор «требуется моё действие» и новых сообщений.
- **«Требуется моё действие» признаёт только один источник — `bySource` центра задач** (тот же, что у `/tasks`): только позиции, относящиеся лично мне и с ненулевым количеством (консультации с сайта, OA, CRM, OKR, проекты, рабочие процессы, ожидающие подтверждения контракты, платформенные проверки); «ожидающие моего подтверждения приглашения в привязку» ни к одному источнику задач не относятся и добавляются отдельной строкой.
- Платформенный администратор: кабинет = обзор данных платформы (регистрации / предприятия / поставщики / контракты / документы и налоги по бизнесу), ожидания проверок (регистрации поставщиков) и распределение типов услуг поставщиков; сайдбар ведёт прямо в надзорные разделы.

### 4. Бизнес-сервисы (11 сервисных линий + рынок спроса и предложения)

Единый формат: **библиотека поставщиков услуг** (просмотр списка → детали → инициировать контракт) + **запросы / маркет услуг** + **бизнес-журнал**.
Поставщик сначала проходит регистрацию и получает квалификации по соответствующим категориям, только тогда его ресурсы видны снаружи; если в разделе только один поставщик, список не показывается, а его детали встраиваются напрямую.
Рынок спроса и предложения — публичный кросс-секционный рынок без привязки к разделам; оба списка — запросов и услуг — **разбиты на страницы** (без бесконечной прокрутки),
фильтруются по **региону (провинция / город) и подкатегории второго уровня**, категории (первый / второй уровень) показываются в строке; помимо двух списков есть вкладка **отзывы** (распределение оценок, журнал отзывов), отзывы — также источник отображаемого рейтинга поставщика.

У списков **запросы / услуги** сервисных маркетов и рынка спроса / предложения есть пара фильтров «**все (запросы / услуги)** / **мои публикации**»:
«все» читает публичный пул соответствующей категории AIworkin; «мои публикации» читает журнал этой системы (публикация сначала пишется локально,
затем синхронизируется на платформу, обратно записывается ID платформенного контента). По подходу пользователя от 2026-11-09 «мои публикации» **рендерятся только идентичности поставщика**,
у идентичности предприятия этот фильтр не появляется (только «все»). Записи, официально опубликованные на AIworkin, в этой системе не редактируются и не удаляются,
остаётся только «просмотр» — REST write-интерфейсы платформы (PATCH / DELETE) по API-ключу всегда отдают 401, в MCP инструментов изменения / удаления тоже нет.
Ключи меню **маркетов услуг** (логистика / маркетинг / глобальный рынок / гибкая занятость / IT / интеллектуальная собственность / юридические / think tank / активы / поставки-сбыт / налоги-финансы) имеют вид «маркет услуг ××»,
содержимое одинаковое: все услуги = публичный пул платформы, мои опубликованные услуги = локальный журнал; «сеть поставок / сбыта» и «налогово-финансовые услуги»
переименованы из «публикации услуг» и объединены 2026-11-09 (слова пользователя: «единообразие с остальными маркетами — видно и публичный пул, и мои публикации услуг»).
**Вкладки маркета сети поставок / сбыта видны и предприятиям** (2026-11-09): весь маркет можно смотреть, предприятие не может лишь публиковать услуги —
вход «опубликовать услугу» не рендерится по идентичности, фильтр «мои опубликованные услуги» тоже отсутствует, бэкенд отсекает тем же подходом через `assertPublishAllowed`.

- **Официальные сервисные пакеты**: в колонках поставщиков каждого бизнес-раздела показываются официальные пакеты платформы (ориентировочная цена в юанях + цена в баллах по курсу из панели), предприятие покупает напрямую за баллы; после покупки платформа сводит предприятие с несколькими качественными поставщиками и подписывает контракты по каждому пункту, формулировка пакета — «пакет исполняется платформой через отобранных поставщиков», контракт всегда вступает в силу только после подтверждения поставщиком (предустановленные поставщики тоже только автоматически получают инициацию, без автоподтверждения), прогресс исполнения читается из статусов контрактов в реальном времени. В панели «Сервисные пакеты» ведутся каталог и очередь исполнения (подбор, инициирование от лица платформы, замена стороны, частичный возврат / полный возврат), лимит покупок считается по предприятию, пакеты не участвуют в управлении жизненным циклом и сроками; на пользовательской стороне «Мои пакеты» показывают купленные пакеты и прогресс по пунктам.
- **Включение возможностей**: электронное декларирование и электронное выставление счетов-фактур — платные возможности; поставщик настраивает их для обслуживаемого предприятия, предприятие подаёт заявку на включение, платформа проверяет;
  включение / выключение по предприятию и сопоставление аккаунтов qixiangyun централизованы в панели «Налогово-финансовое управление».
- **Бизнес-панели**: списки **запросов** разделов налоги-финансы / поставки-сбыт / глобальный рынок и др. читают журнал этой системы (`market_listing_records`)
  и больше не читают публичный пул платформы напрямую; публикация синхронизируется на платформу AIworkin через единый MCP-канал, номер листинга платформы (ID контента)
  записывается обратно в локальный журнал, опубликованные на платформе записи доступны в этой системе только на «просмотр». **Колонки услуг** указанных разделов
  с 2026-11-09 единообразно называются «**маркет услуг ××**», читают локальный журнал услуг (`provider_service_listings`) с переключением
  «все услуги / мои опубликованные услуги» (все = публичный пул платформы), публикация так же сначала пишет локально, затем синхронизируется на платформу и записывает номер листинга.
- **Рынок спроса и предложения**: вход в меню — в «Бизнес-сервисах», интерфейс переиспользует `/enterprise/market/:domain/...`, межраздельность обозначается как
  `domain=HUB`; на вкладках запросы / услуги есть фильтры «все / мои публикации» — «все» читает только **публичный пул** платформы
  (поэтому без привязанного ключа ошибки авторизации канала не будет), «мои публикации» читает только локальный журнал (`scope=mine`, рендерится только поставщику);
  в обоих местах работают фильтры по региону (провинция / город) и подкатегории (категории выбираются сквозь все бизнес-разделы, категория первого уровня показывается в строке);
  списки постраничны, следующая курсорная страница подтягивается только при переходе, без длинной прокрутки справа от списка;
  публикация напрямую пишет на платформу привязанным AIPDD API-ключом текущего аккаунта, локально остаётся запись в журнале, опубликованный контент так же проходит автоматическую проверку Alibaba Cloud Content Security;
  записи, опубликованные на платформе, в этой системе не редактируются и не удаляются, остаётся только «просмотр».

### 5. Деловые связи (соцсеть / найм / спрос-предложение)

- **Деловая социальная сеть**: знакомство с коллегами по отрасли (дружба / блокировка), публикация постов (публично / только для друзей), группы в духе Douban (обнаружение и вступление в группы, посты по категориям,
  анонимность построчно, поэтажные ответы и рекомендации, закрепление и «избранное» от владельца / администратора, приём в группу), внутрисайтовые личные сообщения, профессиональное резюме (отдельная HTML-страница, не главная,
  можно приложить в переписке, работодатель открывает сразу и экспортирует в PDF). При блокировке аккаунта социальные функции автоматически отсекаются.
- **Найм**: размещение вакансий full-time / part-time / стажировка / временная / аутстаффинг в ленте площадки найма, контакт через внутрисайтовые личные сообщения (можно приложить резюме),
  ATS-библиотека резюме и скрининг этой системой не делаются; при привязанном ключе AIPDD вакансия синхронизируется как запрос на гибкую занятость AIworkin (категория берётся из поддерева «гибкая занятость»).
- **Площадка спроса и предложения**: универсальная публикация запросов / услуг, попадает в локальную ленту, её смотрят и пишут в личные сообщения.
  **Двухэтапная публикация** — центральный подход проекта: по умолчанию публикация локально без ключа; при галочке «синхронизировать на AIworkin»
  через единый резолвер учётных данных выполняется upstream-вызов `POST /market/listings` привязанным ключом пользователя, а статусы проверки / отзыва на upstream зеркалятся обратно.

### 8. Модельные сервисы

- **Управление API-ключами**: два набора ключей разделены — ek_-ключи этой системы служат для вызова открытых интерфейсов (`/api/v1`) и площадки моделей, создание / копирование / сброс / отзыв — всё здесь;
  для каждого ключа отдельно задаётся «лимит баллов» (совокупный потолок потребления при внешних вызовах, при превышении отказ, можно задать безлимит);
  AIPDD API Key (`sk-`) привязывается на той же странице, открывая синхронную публикацию, синхронизацию данных поставщика, ресурсы для аутрича и другие upstream-возможности. Ключи хранятся шифрованными, скопировать их в любой момент может только владелец на этой странице, другим они не видны.
- **Площадка моделей** (`/model-plaza`): каталог моделей, выложенных платформой, — единицы тарификации совпадают с upstream (диалог / эмбеддинги — по токенам, изображения — по штукам, видео и распознавание речи — по секундам, синтез речи — по запросам),
  можно пробовать онлайн и смотреть журнал потребления, а через ключ `ek_` ходить в OpenAI-совместимый шлюз; каталог, upstream-каналы и цены ведёт панель «Биллинг и товары → Площадка моделей».
  В панели есть вкладка «Модель по умолчанию»: для текста / зрения / изображений / видео / распознавания речи / синтеза речи / эмбеддингов задаётся отдельно модель по умолчанию платформы, настраиваются лимиты баллов за запрос, в сутки и в месяц с журналом изменений;
  пользователи, совершившие реальное пополнение с зачислением, автоматически наследуют необозначенные возможности (засчитываются только оплаченные счета пополнения, подарки и ручные корректировки — нет), вызовы списывают баллы по каталожной цене.
- **API-MCP-Skill** (`/developer/api-mcp-skill`): единый вход модельных сервисов, три вкладки в таком порядке —
  **Skill**: список пакетов навыков, сгенерированных администратором платформы по бизнес-доменам (название, описание, домен, число покрытых действий, генеративная модель, время обновления), «Скачать» сразу отдаёт zip;
  внутри пакета только инструкция по вызову и примеры, без реальных ключей; повторная генерация навыка с тем же именем перезаписывает старый пакет, список и скачивание управляются одним тумблером меню.
  **MCP Server**: Codex, Claude Desktop, Cursor, собственные скрипты и Workbuddy подключаются одним и тем же API-ключом;
  сервер сначала анализирует память агента этого аккаунта, затем по авторизации автоматически выполняет действия сайта. Список интерфейсов выводится из контрактного слоя: новый модуль (ERP склад/закупки/продажи, SEO-workbench, AI-лидогенерация, SCRM WeChat Work, проектные задачи, HRM и т. д.) попадает в `list_operations` автоматически, как только enters контракт;
  действия, напрямую меняющие книги, — выводы согласований, движение денежных средств, движения склада (включая согласования склада / закупок / поступлений / авансовых отчётов в ERP, сверку платежей, движения прихода / расхода) — внесены в перманентный список исключений и подтверждаются только владельцем в интерфейсе.
  **API**: фактический список внешних интерфейсов этой системы, выводится из контрактного слоя и идентичен `list_operations` сервера MCP и документу OpenAPI.
  Старые адреса `/developer/docs` и `/developer/mcp` сохранены как редиректы на `?view=api` и `?view=mcp`.
- **Настройки моделей**: общая конфигурация моделей для Agent и создания контента — встроенный канал AIPDD работает сразу по sk-ключу, можно подключить другие OpenAI-совместимые шлюзы и Volcano MediaKit, для каждого типа выбирается модель по умолчанию;
  сверху страницы показана текущая эффективность «моделей платформы по умолчанию» (при ненастроенной личной — наследование по праву пополнения) и использованный лимит за сегодня / месяц.
  Платформенный администратор в «Площадке моделей → Каналы пользователей» задаёт диапазон поддержки каждого вычислительного канала (по умолчанию поддержаны все): закрытые каналы пользователь не может добавлять / изменять и выбрать;
  закрытие AIPDD останавливает только его вычислительную мощность (настройки моделей / площадка моделей), прочие функции (бизнес-сервисы и т. д.) с тем же AIPDD API Key продолжают работать.
- **Механизмы платформы**: единый вход поперечных возможностей §5.8 — событийный Outbox и подписки Webhook (тест, журнал доставки, повторная отправка при сбое; каталог событий покрывает задачи, проекты, лиды / заказы / поступления CRM, внешние запросы, внешние контракты и другие бизнес-узлы), импорт CSV (сопоставление полей, пробный прогон, переиспользование схемы) и экспорт по модулям (экспортируемые файлы больше не получают долговечную публичную ссылку — их по текущей организации повторно отдаёт эндпоинт под логином), каталог отчётов, движок правил (сопоставление условий + вызов Webhook / уведомления / инсайт / создание задачи), публичные ссылки (пароль, срок действия, отключение; при каждом открытии заново проверяется право создателя состоять, при увольнении инициатора или исключении из организации ссылка теряет силу), источник идентичности OIDC (проверка discovery, автоматическое открытие аккаунта), политика общих вложений, синхронизация адресной книги, посещаемости и карточных сообщений Feishu / WeChat Work, регистрация принятия условий (при новой версии без принятия — напоминание по всему сайту), продуктовая событийная аналитика (события страниц / действий и агрегированные панели) и переключатель субъектов (один физический человек переключает область HRM между предприятиями / поставщиками), ко-pilot, распознающий страницу (плавающий вход по всему сайту). Вкладки всех бизнес-страниц единообразно переведены на переносные капсулы (`PanelTabs` / `TabStrip`), antd Tabs больше не смешиваются.
- **Центр помощи**: версионируемая вместе с кодом глава-база `/help` (файлы знаний — в `backend/src/help`) покрывает применение каждого модуля; на той же странице есть вкладка «Журнал изменений» с продуктовым changelog; тексты знаний открыты тремя read-only действиями MCP `Help_chapters / Help_topic / Help_search` — официальный способ применения можно прямо спросить у Agent.
- **Снимок OpenAPI**: `/api/openapi.json` (1947 операций), CI сверяет его с контрактным слоем.

### 9. Умные устройства

Самостоятельный раздел **Умные устройства** в сайдбаре (группа первого уровня, после администрирования): пользователь просматривает оборудование и devkit, подключает имеющиеся устройства к платформе и по типу устройства вызывает **собственные** MCP-инструменты (управление через Agent) и API (программное управление); платформенный администратор ведёт каталог моделей, версии devkit и инструменты по умолчанию.

- **Площадь оборудования** (`/hardware`): каталог моделей с рекомендациями / сортировкой, каждая модель даёт спецификации, версию devkit (канал stable / preview) и загрузку; бинарники devkit напрямую заливаются в OSS этого сайта, скачивание считается, на странице приводится SHA-256 для проверки; в деталях модели виден список её аппаратных API / MCP инструментов по умолчанию.
- **Добавить устройство** (`/hardware/devices`): выберите модель и подключите устройство, генерируется аппаратный токен с префиксом `hw_` (открытый текст показывается ровно один раз в момент генерации, в базе хранится только SHA-256); устройство выходит в online по heartbeat, заполнив адрес сервиса и токен из SDK / прошивки devkit, статусы в списке — online / offline / никогда не отчитывалось (более 180 секунд без heartbeat → offline), по устройству можно смотреть журналы heartbeat / команд / результатов для отладки.
- **Аппаратный MCP** (`/hardware/mcp`): отдельный сервер оборудования MCP `aiworkin-hardware-mcp` (эндпоинт `/api/v1/hardware/mcp`) полностью изолирован от платформенного MCP — инструменты берутся только из таблицы аппаратных инструментов, имена `hw__<код модели>__<код инструмента>`, авторизация ek_-ключом из «Разработчик → API-ключи». Write-инструменты проходят трёхслойный гейт авторизации: если на этой странице не отмечено «выполняется автоматически», вызов пришёл из периодической задачи без присмотра или вызывающий заявил dryRun — всегда возвращается только черновик, ничего реально не отправляется; «пробный вызов» владельцем этого не ограничивается.
- **Аппаратный API** (`/hardware/api`): тот же набор инструментов идёт машинным каналом `/api/v1/hardware/**` через ek_-ключ, `curl` позволяет выводить список и вызывать; параметры и ответы инструментов задаются JSON-примерами на странице.
- **Dev Kit**: в корневом каталоге репозитория `hardware-devkit/` лежат готовые к компиляции SDK и примеры — ESP-IDF компонент для ESP32, чистый Python-пакет стандартной библиотеки для Jetson / Raspberry Pi, два запускаемых примера, плюс zero-dependency Node-эмулятор устройства (полный замкнутый цикл «heartbeat → получение команды → отчёт» без всякого железа) и протокольная документация по полям; предварительно собранные прошивки будут добавлены после первой компиляции на реальном железе.
- **Обслуживание в панели**: раздел «Умные устройства» у администратора платформы делится на вкладки «Модели оборудования / Dev Kit / Инструменты по умолчанию» — ведётся каталог моделей, загружаются devkit каждой версии, по моделям обслуживаются аппаратные API / MCP инструменты по умолчанию, изменения сразу видны пользовательской стороне. Инструменты, созданные пользователем, видны и доступны только ему, в инструменты по умолчанию модели не попадают и в первой версии не выносятся на маркетплейс.

Каналы устройств (`/api/public/hardware/heartbeat`, `/commands`, `/result`) признают только аппаратный токен, без логина, и **намеренно не перехватываются тумблером функции**: когда администратор выключает раздел «Умные устройства», heartbeat уже подключённых устройств не обрывается.

### 10. Баллы и биллинг

- **Баллы**: пополнение через WeChat, переводы между аккаунтами, прайсы модулей и списание за потребление (хранение цифровых активов, CRM / BI / OA / AI-поддержка), история и счета пополнения на одном экране; прайсы уже проставлены для AI-инсайтов / HRM / базы знаний / маркетинга / найма / проверки навыков и вступают в силу с выходом соответствующих модулей.
- **База хранения**: вложения и цифровые активы единообразно заливаются напрямую в Aliyun OSS этого сайта (через upstream больше не идут); на странице активов можно удалять поштучно, в панели «Системные настройки → Файловое хранилище» показаны ёмкость, цены и портовая миграция исторических активов (прерывается и продолжается, сбои повторяются).
- **AWcoin**: баланс и источники отображаются только для чтения, **никогда не размениваются взаимно**.
- **Настройки панели**: курс и уровни пополнения, бонусы за регистрацию / приглашение, лимиты и риск-контроль переводов, прайсы по модулям, корректировки счетов и запросы заказов.

### 11. Мультиязычность, сайт и уведомления

- **8 языков интерфейса**: 简体中文 · English · Tiếng Việt · 日本語 · العربية · Français · Español · Русский;
  администратор задаёт язык сайта по умолчанию, гость переключается в любой момент, для арабского — полностью RTL-макет.
- **Трёхуровневый приоритет домена сайта**: панель «Настройки сайта → Домен сайта» ＞ переменная `SITE_URL` ＞ текущий адрес гостя;
  эндпоинты MCP / API, IM-коллбэки, скрипт встраивания поддержки, входы живых кодов, приглашательские ссылки и другие абсолютные адреса собираются по этому приоритету (см. ниже «Домен сайта»).
- **Видимость меню**: каждый пункт бокового меню фронтенда (вход в кабинет + каждая группа, включая внешнюю ссылку «вычислительная платформа AIPDD») можно поштучно скрывать галочкой в панели «Настройки сайта → Видимость пользовательского меню»; когда в группе скрыты все пункты, группа исчезает автоматически (скрывается только меню, ссылки остаются доступными).
- **Видимость вкладок разделов**: на 12 страницах «Бизнес-сервисов» (маркетинг / поставки-сбыт / налоги-финансы / глобальный рынок / гибкая занятость / логистика / IT / интеллектуальная собственность / юридические / think tank / активы / рынок спроса и предложения) вкладки «запросы» и «маркет услуг» скрываются поштучно по разделам галочкой в панели «Настройки сайта → Вкладки бизнес-разделов (отметка = скрыть)»; тот же подход, что и с меню, — скрытие одинаково для всех идентичностей (включая администраторов) и контролирует только показ (прямые ссылки и интерфейсы не ограничены).
- **Иконка браузерного плагина в шапке**: единая иконка в шапке рядом с уведомлениями и сервисным аккаунтом WeChat — единственный вход скачивания и установки платформенного клиента (AIPDD Enterprise): маркетинговая дистрибуция, AI-лидогенерация, браузерный агент (локальный Chrome), будущие карточки товаров / SEO и другие бизнесы используют её совместно, отдельные окна «установить плагин» больше не делаются. Открывается ящик с четырьмя вкладками: загрузка и установка (текущая версия, минимальная совместимая, поддерживаемые браузеры, установочный пакет, шаги установки), инструкция (входы бизнес-возможностей и частые вопросы), журнал обновлений, авторизованные сайты (просмотр / отзыв доверия сайта к плагину). При открытии автоматически выполняется handshake-проверка (кнопки ручного обновления нет), без установленного плагина даётся пошаговая инструкция, при устаревшей версии иконка отмечает это точкой и ведёт обновиться; если браузер ограничивает проверку, можно подтвердить «я установил» вручную, но перед выполнением бизнес-операции всё равно проводится реальный handshake. Если платформа не выпустила пакет плагина или администратор выключил «Настройки сайта → иконка браузерного плагина в шапке», иконка целиком не рендерится; адрес установочного пакета собирается из настроек домена сайта, домены клиентов не зашиваются.
- **Системные сообщения**: централизованные напоминания о шести категориях событий — поддержка, запросы и возможности, идентичность и контракты, налоги-финансы и декларирования, автоматизация и интеграции, аккаунт и платформа.

## 🧱 Технологический стек и архитектура

- **Бэкенд**: [Hono 4](https://hono.dev) + `@hono/zod-openapi`, Prisma 5.22, MySQL 8 / PostgreSQL, Zod 4, Node.js ≥ 24
- **Фронтенд**: Next.js 16 (App Router) + React 19 + Ant Design 6 / Pro Components + `@tanstack/react-query` 5
- **Контрактный слой**: `packages/contracts` — единственный источник истины для фронтенда и бэкенда, MCP и OpenAPI (1947 операций, коды ошибок, каталог MCP)
- **Аутентификация**: три разделённых канала — собственные SSO-сессии этого сайта (ключ из HKDF + сверка версии аккаунта) + ek_-ключи открытых интерфейсов + sk-ключи AIPDD upstream
- **Права на данные**: данные всегда весят на организационном ключе `(orgType, orgUserId)`, списки / детали / экспорт / вложения / AI / периодические задачи перед использованием единообразно проверяют «аккаунт активен + состоит в организации» (`HrmScopeService.isStanding`), увольнение или смена роли гасят доступ мгновенно, без зависимости от асинхронной чистки или кэшей; построчные и поколоночные права BI входят в единый контур реальных запросов, предпросмотра, графиков и AI-вопросов к данным (фильтр строк по плейсхолдерам `${userId}` / `${deptId}`, скрытые колоночными правами колонки вырезаются и из результатов, и из передачи модели); организационный контекст идёт только через единый сервис резолва тенанта (`TenantScopeService.preferred`), CRM / BI / OA и HRM / OKR делят один подход «текущий субъект» — выбранный в шапке переключателя и всё ещё действующий субъект имеет приоритет, после переключения границы данных по модулям согласованы

```

```

## 🚀 Быстрый старт (локальная разработка)

Предварительно: Node ≥ 24, pnpm ≥ 10, доступный экземпляр **MySQL 8 или PostgreSQL** (один на выбор).

### Вариант A: установка одной командой (рекомендуется, база на выбор)

```bash
pnpm install
pnpm setup            # интерактивно：выбор MySQL / PostgreSQL → подключение → запись backend/.env → генерация клиента → создание таблиц
# или неинтеракивно：pnpm setup --db postgres --host 127.0.0.1 --port 5432 --user app --password *** --database enterprise --yes
pnpm dev:api & pnpm dev:web
```

`pnpm setup` делает: ① записывает `DATABASE_URL` и `DB_PROVIDER` в `backend/.env`; ② для MySQL применяет историю миграций `prisma migrate deploy`, для PostgreSQL детерминированно выводит из `schema.prisma` файл `schema.postgres.prisma` и выполняет `prisma db push`; ③ генерирует Prisma Client под выбранный диалект.

> Client и таблицы Prisma генерируются под диалект: после смены БД заново выполните `pnpm setup` (или `pnpm --filter aiworkin-enterprise-api prisma:generate:pg`).

### Вариант B: ручная настройка

```bash
# 1) установить зависимости（запускается prisma generate）
pnpm install

# 2) настроить переменные окружения бэкенда
cp backend/.env.example backend/.env
#   правьте backend/.env：DATABASE_URL（MySQL или PostgreSQL）、DB_PROVIDER、JWT_SECRET、EXTERNAL_CRED_KEY
#   （JWT_SECRET / EXTERNAL_CRED_KEY — локальные случайные строки；без них бэкенд отказывается стартовать）

# 3) настроить переменные окружения фронтенда
cp frontend/.env.example frontend/.env.local

# 4) инициализировать базу（миграции/db push + генерация клиента）
#   MySQL：
pnpm --filter aiworkin-enterprise-api prisma:migrate:deploy
pnpm --filter aiworkin-enterprise-api prisma:generate
#   PostgreSQL（используется производная схема）：
pnpm --filter aiworkin-enterprise-api db:push:pg

# 4b)（опционано）залить демонстрационные данные：профили предприятий / справочники поставщиков / юристы·ИС·гибкая занятость / поставки-сбыт, маркетинг и т. д.
#     только для показа справочников и деталей；демо-роли — не входные аккаунты，после входа используйте локальный аккаунт из шага 5.
pnpm --filter aiworkin-enterprise-api prisma:seed

# 5) запустить бэкенд (по умолчанию 1690) и фронтенд (по умолчанию 15890)
pnpm dev:api
pnpm dev:web
```

Откройте в браузере `http://127.0.0.1:15890`, зарегистрируйте локальный аккаунт — и сразу доступны соцсеть и площадка спроса / предложения.
Фронтенд проксирует `/api/backend/*` на бэкенд через серверную часть Next.js, браузерная сторона остаётся того же источника.

### Создание администратора платформы (обязательно при первом развёртывании)

Администратор платформы **не создаётся** автоматически при установке / запуске — его явно создаёт `backend/scripts/seed-admin.ts` (идемпотентно, `--reset` сбрасывает пароль):

```bash
# 1) задайте в backend/.env ADMIN_USERNAME / ADMIN_PASSWORD
# 2) выполните（первое создание；при существующем аккаунте с таким именем — пропуск）
pnpm --filter aiworkin-enterprise-api exec tsx scripts/seed-admin.ts
```

После создания войдите под этим аккаунтом — в сайдбаре появится вход в панель платформы; без него можно зарегистрировать только обычного пользователя, в панель платформы вход закрыт.

### Ключевые переменные окружения

| Переменная | Описание |
|---|---|
| `DATABASE_URL` | Строка подключения к БД: MySQL `mysql://user:pass@127.0.0.1:3306/enterprise` или PostgreSQL `postgresql://user:pass@127.0.0.1:5432/enterprise?schema=public` |
| `DB_PROVIDER` | `mysql` / `postgres`: основа ветвления нативного SQL по диалекту (автоинкремент номеров документов, извлечение значений JSON-колонок); при отсутствии выводится из протокола `DATABASE_URL` |
| `PORT` | Порт прослушивания бэкенда, по умолчанию `1690` |
| `JWT_SECRET` / `JWT_ISSUER` | Ключ подписи локальных сессий, в продакшене обязательно заменить на случайное значение |
| `EXTERNAL_CRED_KEY` | Ключ производной AES-256-GCM шифрации ключей AIPDD / внешних учётных данных, настраивается отдельно и не откатывается к JWT_SECRET |
| `AIPDD_PLATFORM_KEY` | Резерв платформенного AIPDD APIKey на уровне развёртывания (канал базовых данных); после сохранения в панели «Системная конфигурация → Платформенный ключ AIPDD» действует шифротекст из базы |
| `AIWORKIN_BASE_URL` / `AIWORKIN_ENABLED` | Адрес и тумблер upstream-рынка (при выключении доступен только локальный замкнутый контур) |
| `CORS_ORIGIN_PATTERNS` | Разрешённые кросс-доменные источники (через запятую) |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD` | Логин и пароль, читаемые скриптом `seed-admin` при создании администратора платформы (при запуске не создаётся) |

> Все ключи хранятся только в локальном `.env` (уже в `.gitignore`); ни один интерфейс никогда не возвращает текст AIPDD-ключа.

### Совместимость баз данных (MySQL / PostgreSQL)

Система выбирает одну из двух при установке, во время работы ориентир — `DB_PROVIDER` (при отсутствии выводится из протокола `DATABASE_URL`), бизнес эквивалентно работает на обеих СУБД. Для сглаживания диалектных различий сделано следующее:

- **Единый источник истины схемы**: базовый `prisma/schema.prisma` (MySQL); при установке PostgreSQL детерминированно выводится `schema.postgres.prisma` через `scripts/gen-prisma-schema.mjs` (`provider=postgresql`, `@db.TinyInt→@db.SmallInt`, `@db.DateTime→@db.Timestamp`). MySQL строит таблицы по истории миграций, PostgreSQL — через `prisma db push`.
- **Автоинкремент номеров документов**: `document-number.ts` ветвится по диалекту — MySQL через `INSERT IGNORE` + `LAST_INSERT_ID`, PostgreSQL через `ON CONFLICT DO NOTHING` + `UPDATE … RETURNING`.
- **Извлечение значений JSON-колонок**: `jsonText()` в `common/sql-json.ts` генерирует путь `->>` по диалекту (PostgreSQL `col->>'key'` / MySQL `col->>'$.key'`) — для выбораки больших данных и кросс-запросной дедупликации лидокопания.
- **Вопросы к данным и графики BI**: `internalScope()` в `bi/bi.internal.ts` выдаёт плейсхолдеры по диалекту (PostgreSQL `$1` / `ANY($2::text[])`, MySQL `?`); ссылающиеся идентификаторы графиков в `bi.query.service.ts` выбираются под целевую базу (двойные кавычки PG / обратные кавычки MySQL для прикладной базы или внешнего источника данных).
- **Генерация клиента**: `postinstall` идёт через `scripts/prisma-generate-auto.mjs`, который по `DB_PROVIDER` / `DATABASE_URL` автоматически выбирает базовую или производную схему и генерирует клиент, чтобы при переустановке зависимостей PG-клиент не перезаписывался MySQL-версией.
- **Регистр имён пользователей**: вход и уникальные ограничения сведены к **нормализации в нижний регистр** (MySQL по умолчанию регистронезависим, PostgreSQL — зависим), email тоже хранится в нижнем регистре — поведение входа / проверки дублей в обеих базах согласовано; аккаунты со смешанным регистром, созданные до изменения, на MySQL продолжают входить нормально (CI попадает), для существующих баз доступна разовая дозаполровка `pnpm --filter aiworkin-enterprise-api db:normalize-usernames` (идемпотентна, работает на обеих СУБД, при коллизии имени позиция пропускается и выводится списком).

> Известное различие: свободный поиск по тексту (ключевые слова `contains`) регистронезависим в MySQL и зависим от регистра в PostgreSQL — Prisma-опция `mode:'insensitive'` не поддерживается коннектором MySQL, поэтому все поисковые операторы принудительно не унифицируются. Основной контент на китайском и т. п. не имеет регистра и не затронут; если нужно единообразие и для латиницы, на стороне PostgreSQL создавайте базу с регистронезависимым ICU-collation либо нормализуйте соответствующие поля в нижний регистр перед поиском.

## 🌐 Домен сайта (внешний адрес доступа)

Нигде не зашит локальный адрес: абсолютные адреса — эндпоинты подключения MCP / API, коллбэки IM и ссылок «перейти к обработке» карточек,
скрипт встраивания онлайн-поддержки, входы живых кодов, приглашательские ссылки, рекомендуемые адреса платёжных коллбэков и т. п. — собираются по приоритету:

1. значение, введённое в «Панель управления платформой → Настройки сайта → Домен сайта» (принимаются только http/https, можно с портом; запись в базу сразу действует, без перезапуска)
2. переменная окружения бэкенда `SITE_URL`
3. текущий адрес гостя (`window.location.origin`, при развёртывании на одном домене настройка не нужна вовсе)

При локальной разработке не нужно ничего заполнять: в dev-режиме Next проксирует `/api/*`, в продакшене Nginx сначала забирает `/api/*`,
поэтому эндпоинты вида `https://ваш-домен/api/v1/mcp` работают в обоих режимах.
После смены домена в панели этот домен автоматически добавляется в allowlist CORS / проверки источника; само изменение переменной `SITE_URL` всё ещё требует перезапуска.

## 🔑 Привязка AIPDD API Key и upstream-каналы

- Пользователь привязывает API Key (sk-), выданный платформой AIPDD, в блоке «Привязка AIPDD API Key» страницы «Модельные сервисы → Управление API-ключами»;
  несколько пользователей могут привязать один ключ (N:1, сводка по отпечатку), шифротекст ложится в базу через AES-256-GCM.
  Прежняя отдельная страница «Привязка AIPDD Key» (`/developer/aipdd`) объединена с управлением API-ключами, старый адрес редиректит на `/developer/keys`.
  Эти две страницы (управление API-ключами / настройки моделей) — самообслуживание на уровне аккаунта, **под идентичностью платформенного администратора в сайдбаре не показываются**; для настройки переключитесь на идентичность предприятия / частного лица (платформенный ключ — в «Системная конфигурация → Платформенный ключ AIPDD»), прямые ссылки продолжают работать.
- Тот же блок ведёт регистрацию: после того как администратор впишет в «Настройках сайта» рекомендованный код AIPDD, новый пользователь по подсказке регистрируется на www.aipdd.work и указывает этот код,
  получая бонусные вычислительные мощности (пригласительная комиссия уходит администратору); по умолчанию код задаётся переменной `AIPDD_REFERRAL_CODE`, адрес регистрации переопределяется `AIPDD_REGISTER_URL` (принимаются только http/https).
- `backend/src/common/upstream-token.ts` — **единственный вход учётных данных** к upstream: бизнес-код больше не использует локальную сессионную подпись как upstream-учётные данные,
  а подставляет привязанный ключ пользователя; при попытке upstream-действия без привязки возвращается содержательный `403` (локальная публикация не затронута).
- **Базовые данные идут через платформенный ключ, а не через ключ пользователя**: словари провинций / городов и платформенные словари не зависят от идентичности пользователя — администратор задаёт один платформенный ключ в
  «Панель управления платформой → Системная конфигурация → Платформенный ключ AIPDD» (та же проверка формата `sk-` и онлайн-верификация,
  AES-256-GCM шифротекст ложится в `system_settings.aipdd_platform_key`, наружу отдаётся только маска, приоритет выше, чем у переменной `AIPDD_PLATFORM_KEY`,
  и изолировано от чтения / записи общего интерфейса системных параметров). Цепочка резолва: платформенный ключ → привязанный ключ пользователя → при отсутствии обоих регионы откатываются к локальному встроенному словарю провинций / городов
  (`backend/src/shared/region-dictionary.ts`, источник данных `GEO_CENTERS`) — формы не блокируются даже без платформенного ключа,
  но платформенные словарьные позиции всё же требуют ключ.
- **Действия пользователя** — публикация запросов, синхронизация upstream, ресурсы для аутрича и т. п. — **продолжают использовать каждый свой привязанный ключ** и от платформенного ключа не зависят.
- При `AIPDD_KEY_VERIFY=off` привязка не проходит онлайн-верификацию (удобно для офлайн-демо); в онлайн-режиме вызывается проверка upstream.

## 🧪 Сборка, тестирование и CI

Модульные тесты бэкенда идут под `backend/test/jest-unit.json` (ts-jest), компонентные тесты фронтенда — Vitest + Testing Library (jsdom), отдельно CI проверяет шаблоны окружений, снимок OpenAPI, загрузку и миграции:

```bash
pnpm --filter aiworkin-enterprise-api test          # модульные тесты бэкенда（102 набора / 862 теста прошли，15 пропускаются по окружению）
pnpm --filter aiworkin-enterprise-web test          # компонентные тесты фронтенда（целевое задание / AI-разложение / клиент 360 / проект 360）
pnpm test:uploads                                   # проверка загрузки вложений и изображений счетов-фактур
pnpm test:environment                               # подходы шаблонов развёртывания и переменных окружения
pnpm api:docs:check                                 # совпадает ли снимок OpenAPI с контрактным слоем
pnpm lint                                           # линт кода + prettier，жёсткие гейты CI
pnpm build                                          # contracts → tsc бэкенда → next build фронтенда
```

- **Лимит кучи сборки фронтенда**: `build`, `typecheck` и `lint` идут единообразно через `frontend/scripts/with-heap.mjs` с
  `--max-old-space-size=10240` (обычные ~4 ГБ кучи не хватает при компиляции 55 страниц холодным стартом или при линте с анализом типов — OOM, код выхода 134);
  переопределяется переменной `NODE_HEAP_MB`, при явной конфигурации пробрасывается как есть.
- **CI (GitHub Actions)**: установка зависимостей → сборка contracts → архитектура и базовые маршруты (`check-architecture`, включая проверку прямых входов AI-гейта) → шаблоны окружений →
  снимок OpenAPI → typecheck → **жёсткий гейт линта (`pnpm lint`, включая prettier)** → модульные тесты бэкенда → компонентные тесты фронтенда → проверка загрузок →
  **`prisma migrate deploy` на пустой MySQL 8 (0001→0052)** → сборка фронтенда и бэкенда.
- **Бюджет типовых исключений**: `pnpm audit:escapes` генерирует `docs/escape-report.md` / `docs/escape-report.json`;
  `pnpm check:escape-budget` следит по `.escape-budget.json` (общее число и категории — только вниз) и `.escape-allowlist.json`
  (смещение строк зарегистрированной позиции — провал), CI подключён (после самопроверки измерителя, перед остальными гейтами).
- **Подход к концам строк**: в `backend/.prettierrc` стоит `endOfLine: "auto"` — проверка по фактическим концам каждого файла; на Windows
  `core.autocrlf=true` выдает CRLF, а индекс репозитория и CI — LF, ложных срабатываний ни там ни там. Остальные параметры форматирования — правила prettier по умолчанию.
- **Интеграционные скрипты, зависимые от базы**: `pnpm test:regression` / `test:query-plans` / `test:performance` / `test:geo-recovery`
  рассчитаны на одноразовую пустую базу локального PostgreSQL (`createdb` + `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`),
  с диалектом MySQL по умолчанию несовместимы, оставлены для запуска локально по необходимости.
- **Смоук-скрипты** (PowerShell, чистый ASCII, случайные имена пользователей гарантируют идемпотентность):

```powershell
pwsh scripts/smoke-m5.ps1   # замкнутый контур социального блока（контакты/лента/группы/личные сообщения/резюме/наследование блокировки）
pwsh scripts/smoke-m6.ps1   # площадка спроса/предложения：локальная публикация без ключа + 403 при синхронизации upstream без привязки
pwsh scripts/smoke-site-url.ps1            # нормализация домена сайта / CORS / публичный возврат + страница 200
```

## 🧹 Сокращения относительно upstream-коммерческой версии

Эта открытая версия — результат «объединения + обезличивания + локализации», она явно **не включает**:

- исходный NestJS-бэкенд SNS и сине-белую визуальную схему aiworkin.com (информационная архитектура сохранена, стили полностью переписаны на AntD);
- связанные с криптовалютой направления awcoin — бонусы / расчёты и прочее (площадка спроса / предложения только зеркалит статусы upstream, без криптовалют; AWcoin в центре баллов отображается только для чтения);
- механизмы вроде прокси-запроса / прокси-заявки `sk-` Key платформой и мгновенного выпуска `DEV_AUTO_LOGIN` (демонстрационные данные предоставляются `prisma:seed`,
  но демо-роли нельзя запустить в один клик — требуется обычная локальная регистрация);
- каталожный сервис upstream на Java: источник данных заменён локальной таблицей `users`.
