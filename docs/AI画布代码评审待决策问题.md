## 1. 用户取消时上游费用由谁承担

**现状**
- 取消 = 先把任务置 `CANCELED` 并 abort 本站等待（`content-job.service.ts` `cancel()`），`cancelReason` 固定写「已停止本站等待；上游已产生的算力费用不退回」。
- 站内**没有**画布/工作台的额度记账：`meterChat()` 只在调用方传 `meta` 时记 token 用量，画布与三个工作台的媒体生成路径都没有传，任务表也没有费用/用量字段。

**风险**
- 用户看到的是一句「不退回」，但实际发生了什么（上游是否已扣费、扣了多少）系统里查不到；客服无法回答「我取消了为什么还被扣」。
- 如果后续接入了站内额度（点数/余额），「取消不退款」会变成直接的资金争议点。

**可选方案**
1. **（推荐）只记录不退款**：在任务行上补「上游受理时间 / 子任务 id」字段，取消时把上游单据落库；不引入站内额度，用量口径固定为「提交即计费」。
2. 引入「取消退款窗口」：上游尚未受理（提交前取消）可退，已受理不退——需要上游提供「受理确认」，当前多数网关不给。
3. 站内先预扣、取消按实际退：改动最大，需要额度系统与上游对账一起做。

**影响面**：`content_generation_jobs` 增列 + 取消链路 + 任务界面文案；方案 3 还要改 `model-setting`/计费模块。

## 2. 画布任务的算力额度闸门

**现状**
- 画布/工作台与内容小工具共用 `ContentModelSettingService.resolveTarget()`，内部只有 `assertAiAllowed()`（安全三件套里的主开关与限流）。
- 没有按「画布」单独统计或限额。

**风险**
- 画布可以一次性连很多生成节点 + 生图批量 4 张，单次会话的提交量远高于小工具；若后续要做成本控制，「按功能限额」会缺一个维度。

**可选方案**
1. **（推荐）与内容小工具完全同口径**：不区分来源，靠渠道自身的限额与安全三件套兜底；只在 `/jobs` 列表按 `source` 过滤。
2. 画布单次提交上限（如一次 ≤ 12 条任务）：实现简单，但会打断「一张画布排一整套镜头」的正常用法。
3. 画布专属日额度：需要先有额度系统（见第 1 项方案 3）。

**影响面**：方案 2/3 需要改 `enqueue` 与契约。

## 3. 画布单人私有还是团队协作

**现状**
- `content_canvas_projects.user_id` 是作者，所有查询 `where: { userId }`；没有成员表、没有分享、没有 `isStanding` 复权。
- 生成的产物会进数字资产（可按既有规则共享），但**画布本身**不能共享。

**风险**
- 若产品预期是「设计 + 运营协作一张画布」，当前模型要重做（成员表、权限、离职撤权、冲突合并）。
- 若预期就是个人工作台，则当前实现没问题，但**界面文案不应暗示可协作**。

**可选方案**
1. **（推荐）单人私有**：保持现状，文档与界面明确「画布仅本人可见」；协作另立项。
2. 企业内共享只读：加 `visibility` 列，读走企业范围，写仍限作者——中等改动。
3. 成员协作编辑：成员表 + 乐观锁按人 + 离职复权，工作量大。

**影响面**：方案 2/3 需要迁移、契约、前端成员管理界面，并与「离职实时撤权收口」对齐。

## 4. 生成产物的副本策略

**现状**
- `source = canvas | studio` 的任务成功后：`client.download(直链)` → `digitalAssets.registerDeliverable()` 存本站 OSS，`assetUrl` 改写为本站地址，同时保留上游直链于 `output`。
- 老工具（`source = tool`）仍走上游平台登记（`tryRegister`），两套并存。

**风险**
- 每次成功都下载一份字节：视频动辄几十 MB，存储与出网带宽成本需要评估。
- 若下载失败，`store()` 只告警，任务仍成功，`assetUrl` 退回上游直链——此时产物不进本站资产，资产页看不到。

**可选方案**
1. **（推荐）全量落本站 OSS**：可用性与后续分享/删除都以本站为准；上游直链只作追溯。
2. 只登记直链、不下载字节：省存储，但上游链接过期/失效后资产不可用，且「删除数字资产」无法真正回收。
3. 按媒体类型分流（图片落 OSS，视频只登记直链）。

**影响面**：方案 2/3 要改 `store()` 与资产页的下载/删除语义。

## 5. 素材节点的引用方式

**现状**
- 素材节点保存的是 `{ assetId, name, media, url, previewUrl }` 的**快照**；提交时用的是节点里存的 `url`。
- 资产被删除或地址变更后，画布里的素材节点仍指向旧地址，但画布本身不感知。

**风险**
- 断链：素材在数字资产里删掉后，画布仍能提交，但上游拉不到图，用户只会看到「模型通道拒绝了这次生成」。
- 共享资产的地址可能随分享关系撤销而失效。

**可选方案**
1. **（推荐）资产 ID 为准，取用时解析**：`planNodeRun` 前按 `assetId` 反查最新可用地址（含共享范围校验），断链时明确报「素材已删除或无权访问」。
2. 保持 URL 快照，只在保存时校验可达性（成本高，且异步可达性不代表上游能拉取）。
3. 画布内冗余存一份副本（存储膨胀）。

**影响面**：方案 1 要改 `planNodeRun` 为异步（或在其前面加一层解析），并接资产服务的权限口径。

## 6. 保存冲突的交互

**现状**
- 保存带 `version` 乐观锁，不一致返回 409「画布已在别处更新，请刷新后再保存」；前端自动保存 2.5 秒防抖，失败置 `dirty` 并弹错。
- 单人使用时冲突只可能来自「同一账号两个标签页」。

**风险**
- 自动保存撞上后台结果回写（`rememberCanvasResult` 也会递增 version）时，用户会看到莫名的「已在别处更新」。

**本轮已做的处理**
- 任务收口后前端只合并 `results/lastRunId` 并同步 `version`（`refreshDoc()`），不再整页重载，避免把用户未保存的改动冲掉。
- 本地有未保存改动时跳过合并（保存会整张写回，合并来的结果会随保存一起丢掉）。

**待决策**
1. **（推荐）保持乐观锁**，冲突时提示「刷新后重新编辑」，不做自动合并。
2. 冲突时做「字段级合并」（节点按 id 合并、连线取并集）：需要额外的三向合并规则，风险在删除节点。
3. 引入实时协作（CRDT/OT）：工作量大，且与第 3 项强耦合。

**影响面**：方案 2/3 需要改保存链路与前端交互。

## 7. `image-edit` 多图与批量张数

**现状**
- 画布上连多张图到生图节点 → `image-edit`，`imageUrls` 最多 6 张，一次请求里用 `image[]` 多份上传。
- 张数 `count` 1–4 → 入队时建 4 条独立任务（每条各自一次上游请求），同 `runId`。

**风险**
- 「多图参考」与「多张结果」是两种不同语义，界面上都叫「参考图 + 张数」，用户容易以为"6 张参考图 × 4 张 = 24 种组合"。
- 批量 4 条任务意味着 4 次计费，取消/重试都按单条处理，和用户心智里的"一次生成"不一致。

**可选方案**
1. **（推荐）保持现状**，在面板上把「参考图（同一请求）」与「张数（分 N 次提交）」分开说明。
2. 改成上游 `n` 参数一次请求多张（不是所有网关支持，且失败时整批失败）。
3. 批量任务聚合成一条父任务，界面只显示父任务：需要父子任务表。

**影响面**：方案 2 改执行器；方案 3 改任务表与全部任务界面。

## 8. 渠道与模型的优先级呈现

**现状**
- 优先级：面板这一轮的选择 > 连进来的配置节点 > 生成节点自己存的。规则写在面板底部说明里。
- 若连了配置节点，面板上仍然能改渠道/模型，但改了不会生效（被配置节点覆盖），界面没有显式提示。

**风险**
- 用户改了模型、点生成，实际用的是配置节点的模型——「改了没反应」类投诉。

**可选方案**
1. **（推荐）保持优先级，但界面显式**：连了配置节点时，面板的渠道/模型置为只读并标注「由配置节点决定」。
2. 反过来：面板永远优先，配置节点只作默认值——与设计文档相反。
3. 两者都写进任务行（「请求模型 / 实际模型」），事后可查。

**影响面**：方案 1 只改前端；方案 3 要加任务字段。

## 9. 画布节点上限与拆分布局

**现状**
- 单画布 200 节点，保存时超限直接报「请拆分画布」。
- 没有多画布分组、没有跨画布引用。

**风险**
- 长视频分镜/多镜头项目很容易超过 200；届时用户只能手工拆，节点无法跨画布复用。

**可选方案**
1. **（推荐）保持 200 + 明确提示**，同时允许「复制节点到另一张画布」作为过渡能力。
2. 提高上限（如 500）并观察 JSON 读写耗时。
3. 引入「画布分组/子画布」：需要新表与前端导航。

## 10. 画布封面取哪张图

**现状**
- `derive()` 里 `coverUrl = 第一个图片素材的 previewUrl || 第一个生成结果`。素材节点通常先建，所以封面多半是素材而不是成品。

**风险**
- 列表页看起来像「素材库」，不像作品的成品封面。

**可选方案**
1. **（推荐）生成结果优先**：`results[0]`（最近产物）在前，素材图兜底。
2. 由用户手动选封面。
