# 企业系统整体升级与工作流底座设计方案

> 版本：v1.0（方案稿）  
> 日期：2026-11-10  
> 范围：系统整体性、数据权限、跨模块业务闭环、工作流编排、统一任务、服务商分级派单、平台统一 Chrome 插件与顶部下载入口、存量浏览器能力收敛、账号找回密码与登录方式统一、AI 赋能、平台默认模型与充值用户继承  
> 说明：本文为代码静态复核后的整体设计方案，不代表已完成全系统安全审计；未通过真实业务数据验证越权，也未在本次进行代码实施。

---

## 一、总体目标与核心判断

### 1.1 目标

将当前“功能丰富的模块集合”，升级为：

> **以账号和组织权限为边界、以业务闭环为主线、以工作流为统一编排底座、以 AI 和浏览器插件为执行能力的企业工作系统。**

核心不是继续增加模块，而是让已有模块：

1. 数据归属一致；
2. 权限口径一致；
3. 业务对象能够互相引用；
4. 跨模块流程能够自动推进；
5. 任务能够找到正确的人或服务商；
6. AI 和自动化在授权边界内运行；
7. 模型费用可解释、可控制、可对账。

### 1.2 当前主要矛盾

| 问题 | 企业侧表现 | 改造方向 |
|---|---|---|
| 数据归属与组织上下文不完全统一 | 切换组织后，不同模块看到的数据范围不一致 | 统一组织上下文与授权规则（已修复：CRM / BI / OA 默认主体收敛到统一租户解析服务） |
| 业务已有局部关联，但闭环不完整 | 签单后仍需手工建项目、任务、回款计划和成本归集 | 补齐跨模块业务链 |
| 联动可靠性不足 | 重复建单、任务状态不同步、通知或流程漏推进 | 事务、幂等、重试、对账 |
| AI 配置和执行边界分散 | 用户不会配模型；AI 能看什么、能做什么不清晰 | 默认模型继承、权限感知、统一计费与执行控制 |
| 任务、工作流、插件各自发展 | 同一件事出现多份待办或多套状态 | 统一编排、统一派单、统一回执 |

### 1.3 实施顺序原则

> **先保证“看得对、改得对、账算得对”，再扩大共享，最后开放 AI 与浏览器自动执行。**

不能先让 AI 或工作流获得更广的数据访问和自动写入能力，再回头补权限。

## 二、必须复用的现有底座

以下能力已经存在，不建议重复建设：

| 底座 | 现有能力 | 复用方式 |
|---|---|---|
| 账号与身份 | 个人账号、企业/服务商身份、组织成员、平台管理员 | 统一作为授权主体来源 |
| 组织租户 | 已有统一租户解析服务，按组织键解析当前组织 | 作为组织上下文收敛基础，不另建第四套 scope |
| 业务主体 | 已覆盖客户、供应商、合作伙伴等外部主体 | 作为客户/供应商 360 与合同、项目、ERP 的共享主数据 |
| 工作流 | 手动、定时、领域事件、任务变化触发；动作、AI、人工、Webhook 节点 | 升级为跨模块统一编排底座 |
| 我的任务 | 多业务待办投影、按幂等键写入、通知、关闭与回源 | 升级为统一办理入口，不复制业务状态机 |
| 通知与微信 | 站内通知、微信服务号模板消息、H5 办理入口 | 作为流程触达渠道，不单独形成任务权威状态 |
| 事件与规则 | 事件日志、规则执行、Webhook Outbox | 补齐可靠投递、重试、死信和消费幂等 |
| 数字资产与知识库 | 资产理解、标签、检索、审核、知识空间 | 作为 AI 资料来源和营销产物归档 |
| 模型广场与网关 | 模型目录、LocalAPI 通道、统一模型解析、用量记录、积分扣费 | 默认模型继承和统一计费的载体 |
| 积分 | 充值、赠送、消费、退款流水、余额与欠费 | 作为 AI 与增值服务统一计费账户 |
| Agent / MCP / 连接器 | 工具目录、业务动作、定时任务、连接器 | 与工作流共用业务动作，不另写工具实现 |
| 低代码与 BI | 表单、审批、数据集、行列权限配置 | 作为灵活业务补充，不替代核心业务流程 |
| Chrome 插件 | 多平台内容发布已实际使用该组件；另有获客采集与触达、执行回执 | 升级为平台统一浏览器组件，同类业务全部收敛到同一插件 |

## 三、统一账号、组织与数据权限

### 3.1 四类数据空间

| 空间 | 典型数据 | 默认边界 |
|---|---|---|
| 个人空间 | 私人邮箱、个人草稿、个人模型配置、个人资料 | 仅本人；分享需显式授权 |
| 组织空间 | 企业客户、项目、采购、库存、组织知识库 | 有效组织成员，再按业务权限判断 |
| 外部协作空间 | 与客户、服务商、供应商协作的指定项目或交付物 | 仅获邀人员及获授权对象 |
| 公开空间 | 明确发布的文章、服务、公开资料 | 按发布范围开放，不带内部敏感字段 |

**减少数据孤岛 ≠ 把私人数据变成企业共享数据，也不等于把同一客户在不同企业中的记录自动合并。**

### 3.2 数据归属字段必须区分语义

必须明确区分：

- **所属组织**：这条业务数据属于哪家企业或服务商；
- **创建人**：谁录入了数据；
- **负责人**：谁负责推进业务；
- **参与人**：哪些人被授权协作；
- **业务主体**：客户、供应商、合作伙伴是谁；
- **费用承担者**：本次 AI 或服务消耗由谁付款。

不能继续让一个 `userId`、`ownerId` 或 `createdBy` 同时承担全部含义。

### 3.3 六层授权判断

> **账号有效 → 组织关系有效 → 允许该动作 → 允许访问该记录 → 允许读取/修改这些字段 → 满足业务状态约束。**

建议支持的数据范围：

- 本人；
- 本部门；
- 指定部门；
- 全组织；
- 明确参与或被分享的对象。

规则要求：

1. 用户输入的筛选条件只能缩小授权范围，不能覆盖授权条件。
2. 缺少部门信息时不能退化成全组织可见。
3. 组织主账号、平台管理员身份不能自动替代目标记录的组织校验。
4. 业务对象引用不自动授予目标资源权限，打开目标对象仍需鉴权。
5. 已生成的导出文件、报表、AI 会话结果、分享链接，也必须持续受权限约束。

### 3.4 角色建议

| 角色 | 建议权限 |
|---|---|
| 平台管理员 | 平台设置、模型渠道、运营与运行管理；不因平台身份默认获得全部企业业务正文 |
| 组织负责人/组织管理员 | 组织成员、角色配置、组织设置；敏感数据访问需明确规则 |
| 部门负责人 | 授权部门内业务数据，不自动包含薪酬和财务秘密 |
| 销售 | 授权客户、商机、合同与跟进记录 |
| 财务 | 授权应收应付、收付款、报销、财务报表 |
| HR | 人事资料及获授权的薪酬成本信息 |
| 普通职员 | 本人事项、参与项目、组织公开信息 |
| 外部协作者 | 指定对象和指定动作，不能浏览内部完整台账 |

平台支持人员查看企业业务数据，应采用**企业授权、限时访问、全程审计**，而不是默认全库可读。

### 3.5 权限覆盖的访问入口

权限不能只控制页面按钮，至少覆盖：

- 列表、详情、搜索、统计；
- 导出、附件下载；
- 客户 360、项目总览等聚合页面；
- AI 检索、Agent、MCP、工作流；
- 定时任务、消息推送、公开分享；
- 已生成的报表、导出文件、AI 会话结果；
- 工作流派发的任务及其办理入口；
- Chrome 插件执行任务和回传结果。

人员离职或角色变化后，后续访问必须立即重新鉴权；不能只靠异步清理项目成员或缓存。定时任务执行时也要重新确认账号、组织资格及授权。

### 3.6 统一组织上下文（已收敛）

**问题**：切换组织后，不同模块看到的数据范围不一致。根因是各模块各写一套「我是谁的企业/服务商」——顶部「主体切换器」写入的组织选择只被部分模块采用，CRM / BI / OA 忽略了它，切换后静默无效。

**口径**：组织上下文只走统一租户解析服务 `backend/src/tenant/tenant-scope.service.ts`，不另建第四套 scope。取组织优先级（`TenantScopeService` 类注释）：

1. 主体切换器选过且关系仍在册 → 用它；
2. 自己名下的企业组织 → 用它；
3. 自己在册的 ACTIVE 成员组织 → 用它；
4. 旧 provider_staff 挂靠 → 用它；
5. 都没有 → 个人自组织（ENTERPRISE + 自己）。

**实现**：新增 `TenantScopeService.preferred(userId)`（读 `user_org_context` 并复核关系是否仍有效，返回 `{ orgType, orgUserId, … }` 或 `null`），`resolve()` 亦先行复用它；OKR / Party 已走本服务。本次把此前**忽略主体切换器**的三处收敛到同一入口：CRM `CrmScopeService.ownerOf` 与 BI `BiScopeService.ownerOf` 优先 `preferred`；OA `OaScopeService.resolve` 在**未显式指定组织**时优先切换器选择的组织，显式传参仍以传参为准（且目标必须是本人可选组织）。DI 处把 `TenantScopeService` 构造提前并注入这三个 scope（`backend/src/http/services.ts`）。HRM `HrmScopeService.resolve` 等既有模块已有与 `preferred` 等价的切换器优先逻辑，本次不改动其内部实现（行为一致，避免无谓回归）。

**边界**：知识空间 / 低代码项目等按「显式所属组织或组织键」鉴权的模块不设隐式默认组织，保持原状——低代码项目的组织成员资格由 `HrmScopeService` 冗余复核，不涉及默认主体选择。

### 3.7 回归测试

`backend/src/tenant/org-context-convergence.spec.ts` 覆盖：切换器命中 / 关系失效回退 / 未切换，以及 CRM / BI / OA 在切换器指向服务商组织时的归属与角色取值、OA 显式参数优先于切换器。

## 五、减少数据孤岛：统一业务对象与跨模块闭环

### 5.1 继续复用现有业务主体

现有业务主体已经承载客户、供应商、合作伙伴等能力，应补齐：

- CRM 客户与主体关联；
- ERP 供应商与主体关联；
- 合同、项目、往来记录与主体关联；
- 重复主体识别、人工合并、引用迁移；
- 删除前检查全部关联业务，避免悬空引用。

明确每类字段的权威来源，避免联系人、电话、税号在多个模块互相覆盖。

### 5.2 标准业务对象引用

跨模块关联应包含：

> **组织 + 对象类型 + 对象 ID + 关联关系。**

不能仅用一个数字 `contractId` 泛指所有合同，因为系统存在不同合同业务域。

在此基础上提供统一的“关联业务”组件，展示上下游记录、附件、评论、任务和时间线。

### 5.3 优先补齐六条业务闭环

| 闭环 | 已有基础 | 建议补齐 |
|---|---|---|
| 线索→客户→合同→项目→回款 | CRM、合同、订单转项目、应收已有 | 签约时生成履约计划、回款计划；项目与回款状态联动 |
| 项目→工时→采购/报销→成本→利润 | 项目、工时、采购、报销、合作成本已有 | 统一项目成本归集，明确预算、已发生、已支付、已确认口径 |
| 采购申请→审批→采购→入库→付款 | OA、采购、库存、应付已有 | 来源单关联、重复入库防护、付款审批与采购对账 |
| 招聘→录用→入职→岗位权限→目标→离职 | 招聘、成员、HRM、OKR 已有 | 入离职清单、权限交接、客户和项目负责人移交 |
| 客户沟通→客服工单→任务→交付→知识沉淀 | 邮件、客服、任务、知识库已有 | 经授权将沟通归档到业务对象，解决方案审核后进入知识库 |
| 经营异常→责任人→整改→复核 | BI、规则、任务、通知已有 | 异常生成可处理任务，关闭时回查业务指标而非仅点“完成” |

尤其应区分：

- 合同签约完成；
- 服务已经交付；
- 客户验收通过；
- 财务结算完成。

这四个状态不能互相替代。

## 六、统一执行底座总体架构

### 6.1 架构分层

```text
业务事件 / 定时计划 / 用户操作
              ↓
         工作流编排服务
              ↓
    业务动作 + 统一派单服务
              ↓
      ┌───────┼────────┐
   个人办理   服务商承接   自动执行
      ↓          ↓          ↓
   我的任务   服务商工作池   API / AI / Chrome
                 ↓
            指定或自动分配
                 ↓
             执行人待办
      └──────────┼──────────┘
                 ↓
        结果、证据、业务状态回写
                 ↓
        验收 / 后续流程 / 通知
```

### 6.2 四个必须明确的边界

1. **工作流是编排者，不是所有业务数据的所有者。**  
   合同仍由合同模块管理，库存仍由库存模块管理，扣费仍由积分服务管理。

2. **我的任务是办理入口，不是第二个业务状态机。**  
   审批是否通过、交付是否验收，必须由原业务服务确认。

3. **浏览器执行任务与人的待办不是同一种对象。**  
   浏览器离线、等待登录、已填充等属于执行状态，不能直接等同于业务完成。

4. **服务商承接方与实际执行人必须分开。**  
   更换执行人不改变服务商履约责任；更换服务商则需要重新处理授权和交接。

### 6.3 职责划分表

| 工作流负责 | 业务模块负责 |
|---|---|
| 触发、分支、顺序、并行、等待 | 单据合法性和业务规则 |
| 分派、提醒、升级、超时处理 | 对象权限和字段权限 |
| 调用 AI、插件、连接器 | 库存、资金等事务一致性 |
| 汇集结果、推进下一步 | 正式审批、付款、验收、结算状态 |
| 记录跨模块执行过程 | 原业务数据与审计事实 |

OA 审批不必立即被重写为通用工作流。更合理的是由工作流“发起审批并等待审批结果”，审批模块继续负责会签、驳回等规则。

## 七、工作流引擎作为通用底层服务

### 7.1 当前能力

工作流已有：

- 手动触发；
- 定时触发；
- 领域事件触发；
- 任务变化触发（创建/关闭/逾期）；
- 业务动作节点；
- AI 大模型、知识库检索、Agent/子工作流节点；
- 人工分配任务、等待任务、表单填写节点；
- Webhook 集成节点；
- 运行和步骤持久化；
- 与“我的任务”的派发及回源唤醒。

工作流分配个人任务，见 `backend/src/workflow/workflow-engine.ts:616`。

### 7.2 业务动作层

系统已有契约动作目录，但普通企业不应面对大量底层接口自行拼装。

建议增加经过审查的业务动作：

- 创建履约计划；
- 请求客户补充资料；
- 分配给服务商；
- 分配或认领执行人；
- 创建浏览器执行任务；
- 等待发布结果；
- 提交交付；
- 发起验收；
- 逾期升级；
- 将审核通过的内容归档到知识库。

每个动作声明输入、输出、权限、是否收费、是否可重试、如何判定完成。工作流、Agent、MCP 共用这些动作，避免分别实现。

### 7.3 必须增强的引擎能力

1. **持久等待**  
   支持等待几小时、几天及指定日期，不依赖进程内延时。

2. **结构化人工任务**  
   真正提交表单、附件、选择结果，并由服务端验证；不能只把关闭备注当业务数据。

3. **明确结果分支**  
   成功、拒绝、取消、过期、返工分别路由。

4. **可靠恢复与幂等**  
   服务重启可恢复；已执行但未收到响应的动作先核查，避免重复发布、建单或扣费。

5. **执行身份与组织固定**  
   长流程不能因发起人后来切换组织而改变数据归属；每次恢复仍需检查当前授权。

6. **流程版本与变更控制**  
   正在运行的实例固定版本；新版本默认只影响新实例。

7. **并行分支与汇合规则**  
   明确等待全部、任一成功、失败中止等语义，不能只在画布上画出并行。

8. **运营与故障处理**  
   能看到卡在哪一步、等待谁、为什么失败、如何安全重试或终止。

9. **费用和执行预算**  
   限制单次流程的 AI 费用、循环次数、工具调用数量及浏览器动作数量。

10. **避免双重自动化**  
    某业务若已有内置自动联动，接入工作流时必须确定唯一执行入口，不能两边同时创建任务或单据。

### 7.4 工作流触发与任务的边界

- 已有业务待办（OA 审批、客服工单等）应投影到我的任务，不再造一份同义任务。
- 跨模块协同事项（补资料、内容审核、服务商接单、发布确认）适合由工作流创建。
- 任务完成必须回到业务流程判断，不能只改任务状态。
- 业务重开时，任务与流程要有对应恢复规则。

## 八、我的任务（统一任务中心）

### 8.1 定位

**“我的任务”是统一办理入口和聚合视图，不是第二个权威业务状态机。**

原则：

- 业务状态以原模块为准；
- 中心展示待办并跳转或调用原业务操作；
- 区分业务完成、个人归档、消息已读；
- 不能因本次分页未取到某任务，就把它标记为完成；
- 指派对象必须区分“用户”和“外部主体”，不能只比较 ID；
- 流程任务应支持明确的完成、撤回、驳回和重新打开规则。

### 8.2 建议提供的视图

在权限控制下提供：

- 我的待办；
- 我发起的；
- 我负责分派的；
- 组织待认领；
- 服务商待承接/待分派；
- 待验收；
- 异常与超时。

### 8.3 任务卡片信息

每个任务应展示：

> **来源业务、流程节点、承接方、执行人、截止时间、操作入口、提交要求、验收人。**

办理按钮根据任务类型变化，例如“提交资料”“去发布”“接单”“转派”“提交交付”“验收”，而不是所有任务都只有一个“完成”。

### 8.4 优先落地的任务清单

| 触发条件 | 生成或关联的任务 | 分配对象 | 完成依据 |
|---|---|---|---|
| 营销内容生成完成 | 内容审核 | 品牌负责人/审核岗位 | 审核结果及内容版本 |

## 九、服务商分级派单

### 9.1 现状

系统已有：

- 按企业指定主办职员；
- 部分业务创建时自动继承承办人；
- 客服按在线状态、并发容量和负载自动分配；
- 项目需求采纳后形成外部合作记录，并可把任务指派给外部主体。

代表性依据：

- 服务商指定企业主办职员：`backend/src/identity/identity.service.ts:2198`
- 客服负载分配：`backend/src/service-desk/service-desk.service.ts:2582`
- 项目外部合作及任务指派：`backend/src/project/project-demand.service.ts:340`
- 项目任务指派类型：`backend/src/project/project-task.service.ts:60`

但当前自动分配主要是局部实现，尚缺统一的逐任务派单、接单、转派、负载分配和验收闭环。

### 9.2 推荐流程

```text
企业发起服务任务
    ↓
进入指定服务商工作池
    ↓
服务商接单，或按已授权规则自动接单
    ↓
服务商指定人员 / 自动分配 / 合格人员认领
    ↓
执行人办理并提交交付
    ↓
服务商内部复核（按业务需要）
    ↓
企业验收
    ↓
业务完成；满足条件后再进入结算
```

拒单、退回补资料、取消、超时、返工应有独立分支，不能全部视为“任务结束，流程继续”。

### 9.3 三种分配方式

| 方式 | 适用情况 |
|---|---|
| 指定执行人 | 重点客户、专业要求高、客户明确指定 |
| 自动分配 | 标准化、资格规则明确、任务量较大 |
| 工作池认领 | 合格人员较多，需要灵活接单 |

**待分派任务应归属服务商组织，不应简单挂到服务商主账号个人名下。**

主账号或调度员收到分派提醒；任务本身仍是一条组织级待办，避免给每名员工复制一份造成重复办理。

### 9.4 自动分配规则

先做硬条件筛选，再排序。

**硬条件**

- 属于该服务商且在职；
- 具有该业务办理权限和必要资质；
- 可以接单、未超过容量；
- 能访问这笔任务授权的数据；
- 不存在需要回避的利益冲突。

**排序因素**

1. 当前客户已有主办人，优先保持连续性；
2. 专业能力及服务类型匹配；
3. 待办负载与预计工时；
4. 截止时间、可用时段；
5. 轮询或其他公平规则。

无人符合条件时，留在待分派队列并通知调度员，不能随便指定一个账号。

客服现有负载分配逻辑可以提供参考，但财税、法务、营销不能直接共用一套无差别规则。

### 9.5 长期主办关系与单次任务指派

当前“企业主办职员”属于长期关系，而且改派可能同步调整多类在办单据。

因此新增功能必须明确：

- **更换客户主办人**：客户级操作，可影响后续任务，并明确处理在办事项；
- **转派这一笔任务**：仅影响指定任务；
- **临时代办**：限定时间和动作，不转移全部客户权限。

不能为了改派一项营销任务，就顺带改变这个客户所有财税业务的承办人。

### 9.6 跨组织授权

- 企业保留原始客户、合同和项目数据归属；
- 服务商只获得该服务任务所需的数据和操作授权；
- 服务商员工的权限不能超过服务商获得的授权；
- 员工离职、改派或服务终止后，原执行权限应失效；
- 外部主体档案不等于真实服务商账号授权，需要明确绑定和接受关系；
- 默认不允许服务商再转包给其他服务商；确需转包应由委托方授权。

客户看到履约进度和必要交付信息，服务商内部的人事资料、成本信息不因此公开。

### 9.7 统一派单生命周期

建议统一为：

> **待分派 → 待接单 → 已接单 → 已指定执行人 → 办理中 → 待复核 → 待验收 → 已完成**

异常分支：

- 拒单；
- 退回补资料；
- 超时升级；
- 取消；
- 返工。

每次状态变化记录操作者、组织、原因和业务证据。

## 十、Chrome 插件作为平台统一浏览器组件

### 10.1 原则

> **有稳定且获授权的官方 API，优先 API；必须依赖用户登录网页时用 Chrome；涉及确认、验证码或高影响操作时交给人。**

### 10.2 现有能力

插件已有：

- 多平台内容分发；
- 获客采集与触达；
- 页面与插件通信桥；
- 分发结果回执；
- 获客任务的短期令牌、拉取与回报；
- 人工确认与失败保留页面。

依据：

- 分发任务接单与回执：`extensions/aipdd-enterprise/background.js:167`
- 获客令牌桥：`backend/src/acquisition/plugin-bridge.service.ts:47`
- 发布结果回写：`backend/src/distribution/distribution.service.ts:246`

当前插件与工作流尚无直接集成，分发与获客两套链路也尚未完全统一。

### 10.3 建议升级方向

- 服务器创建执行任务，插件认领，而不是只靠页面临时发消息；
- 任务绑定组织、业务来源、平台、目标账号、执行人和授权设备；
- 插件只支持已登记动作，不接收任意脚本执行指令；
- 使用认领租约和执行版本，防止多浏览器重复执行；
- 页面关闭后，结果仍可持久回传；插件或服务重启后可以恢复；
- 登录失效、验证码、平台页面变化时进入人工处理，不强行绕过；
- 任务取消、改派、授权撤销后，旧执行凭证不能继续推进业务。

当前分发结果通过来源标签页回送，再由页面落库。因此需要重点解决“页面关闭后如何收回执”的问题。

**当前实现（2026-11-11，P3-4）**：平台统一浏览器任务服务 `BrowserTaskService` 落地上述队列语义，分发链路已接入（页面无需改动）：

- 持久队列：`browser_tasks` 表（迁移 `0070_browser_task`）记录能力、动作、组织/主体、平台、业务来源、参数与全生命周期状态；同一来源（`distribution:#<内容 id>`）同时只允许一条未终结任务，重复分发把旧任务按 `EXPIRED` 收尾。
- 认领租约：派发即以 15 分钟租约认领（`lease_owner` / `lease_expires_at`），回执终结时释放；队列 TTL 24 小时，`sweep()` 惰性回收过期租约与超期未认领任务，无需额外定时器。
- 版本门槛：派发前调用能力目录 `assertDispatchable`（下线/停止派发/灰度/最低版本），与后台维护共用同一份生效口径。
- 结果回执：逐平台结果回写即任务回执，`SUCCESS → SUBMITTED`（已提交未核实）、`FILLED → FILLED`、其余 `FAILED`，同步落结果链接证据；已终结任务重复回执幂等不覆盖。内容删除按来源取消在办任务，旧回执挂不回已删内容。
- 获客链路沿用既有令牌桥 `AcquisitionPluginBridgeService`，按本文“逐步收敛”原则后续统一接入同一服务，不新写队列。

### 10.4 统一执行状态

建议至少区分：

> **待执行 → 已认领 → 执行中 → 待登录/待人工确认 → 已填充 → 已提交 → 已核实发布结果。**

并保留失败、取消和结果未知状态。

特别要求：

- 已填充，不等于已发布；
- 已提交，不等于平台审核通过；
- 用户手工补记，应标注为人工确认，不能冒充平台核验结果；
- 发布结果未知时先核查，不直接重新发布。

**定时流程可以准时创建浏览器任务，但普通 Chrome 插件不能保证用户关机时仍准时执行。** 对严格定时发布的需求，应优先使用平台正式接口。

### 10.5 营销工具与插件分工矩阵

| 营销场景 | 后端、AI 负责什么 | Chrome 适合负责什么 | 人工确认点 |
|---|---|---|---|
| 多平台内容分发 | 内容生成、渠道适配、审核、排期 | 在授权账号的发布页面填充内容、上传素材、辅助发布 | 账号确认、最终发布、平台验证 |
| 商品页优化 | 分析商品资料、生成标题卖点、图片和详情草稿 | 用户授权下读取当前商品页、辅助填入编辑页面 | 覆盖线上内容、价格和商品状态变更 |
| SEO/GEO 内容优化 | 检测、选题、内容优化、效果分析 | 获取当前页面渲染信息；无适用 API 时辅助填入 CMS | 正式发布、站点结构变更 |
| 合规线索采集 | 去重、分类、质量判断、归档 | 在允许访问和采集的页面提取用户选定资料 | 采集范围、个人信息与入库审核 |
| 客户沟通辅助 | 根据授权上下文生成回复草稿 | 在允许的平台页面辅助填入回复 | 对外发送；不做无授权批量触达 |
| 发布效果回收 | 指标汇总、渠道归因、经营分析 | 无可用 API 时，由授权人员辅助读取后台指标 | 数据范围和指标口径确认 |
| 活动报名处理 | 表单、线索分配、跟进任务 | 仅在外部网页缺少集成接口时补充办理 | 需要修改外部系统数据时确认 |
| 图片、视频、文案生成 | 模型调用、积分计费、资产入库 | **生成过程不需要插件**，投放时再使用 | 内容审核 |

商品页编辑、CMS 填充等应作为**新增平台适配需求**，不能因为已有分发插件就认为自动支持所有网站。

### 10.6 产品入口：顶部导航的插件图标

建议在系统顶部右上角导航增加一个**统一 Chrome 插件入口图标**，与通知、微信服务号等入口并列：

```text
顶部右侧：  搜索   消息   微信服务号    [Chrome 插件]   帮助   账号
```

入口定位不是营销功能专属按钮，而是**平台级客户端的下载、安装和能力入口**。

#### 展示规则

- 所有已登录用户均可看到；
- 平台未发布插件包或全局关闭该入口时，图标不显示，避免给出无法完成的引导；
- 移动端 H5 不展示安装入口，或展示“请在桌面版 Chrome/Edge 中使用”；
- 图标不依赖任何单一业务开关，营销、获客、商品页、SEO 等业务共用；
- 如果用户已安装但版本过低，图标带提示标记。

#### 点击后的抽屉内容

建议使用右侧抽屉或弹层，分为四个页签：

| 页签 | 内容 |
|---|---|
| 下载与安装 | 当前版本、支持浏览器、下载包、校验值、安装步骤、商店链接 |
| 使用说明 | 如何连接平台、各业务能力入口、常见问题 |
| 更新记录 | 版本号、更新内容、最低兼容版本 |

不要为每个业务模块单独做“安装插件”弹窗，所有业务统一跳转到同一个入口。

#### 安装状态与交互

- 打开抽屉时自动检测插件是否已安装、是否启用、版本是否满足当前业务要求；
- 安装后自动重新检测，不设置手动刷新按钮；
- 检测不到时给出明确的安装步骤，而不是只提示“未安装”；
- 已安装但版本过低时，提供更新说明和下载入口；
- 浏览器不支持时说明支持范围；
- 检测能力受浏览器限制时，允许用户手动确认“我已安装”，但业务执行前仍需真实验证。

#### 下载方式

| 方式 | 适用场景 | 建议 |
|---|---|---|
| Chrome Web Store | 公网用户、自动更新 | 首选，更新体验最好 |
| Edge Add-ons | Edge 用户 | 作为补充渠道 |
| 企业策略部署 | 企业统一管理 | 支持管理员批量部署 |
| 平台托管 ZIP/CRX | 私有化、OEM、内网 | 提供校验值和版本说明；注意 Chrome 对自托管 CRX 的限制 |

下载页必须来自平台自身的站点域名配置，禁止硬编码本机地址或单一客户域名。对 OEM 场景，插件不能为每个客户单独打包域名：应在首次连接时让用户填写或选择平台地址，并由服务端校验。

#### 实现落点（已落地）

| 环节 | 实现位置 | 说明 |
|---|---|---|
| 入口图标 | `frontend/src/components/extension-entry.tsx` + `frontend/src/components/pro/pro-layout.tsx` | 顶栏图标与微信服务号、通知等并列；未登录、平台未发布插件包或管理员关闭总开关时整枚图标不渲染 |
| 入口信息 | `GET /api/backend/enterprise/extension/info`（`backend/src/platform/extension-entry.service.ts`） | 登录用户可读；版本 / 能力 / 安装步骤 / 更新记录与营销分发页同源（`backend/src/distribution/extension-release.ts`） |
| 下载地址 | 同一服务内 `resolveSiteUrl` + `joinSiteUrl` | 站点设置里填了域名就用它，没填回落访客当前访问来源；不硬编码任何客户域名 |
| 总开关 | 后台「平台管理 → 站点设置 → 顶部浏览器插件入口」 | 落 `site_settings.extensionEntryEnabled`，与营销、获客等业务开关解耦 |
| 安装检测 | `frontend/src/lib/extension-bridge.ts` 的 `pingExtension` | 打开抽屉即自动握手（不设手动刷新）；版本低于 `minVersion` 时图标带提示点并给出更新说明 |
| 手动确认 | 抽屉「下载与安装 → 我已安装」 | 仅记录「用户自述已装」，业务执行前仍走真实握手验证，不因手动确认放行任务 |
| 安装包 | `frontend/public/downloads/aipdd-enterprise-v<version>.zip` | 由 `node scripts/pack-extension.mjs` 生成，版本号与 `EXTENSION_RELEASE` 对齐；`scripts/verify-distribution.mjs` 断言下载路径存在 |

移动端 H5 顶栏不渲染该图标（入口只在桌面工作台布局出现）；「支持浏览器」一栏明确写出 Chrome/Edge 109+ 与不支持移动端浏览器。

### 10.7 平台统一插件架构

**原则：平台只维护一个 Chrome 插件、一个扩展 ID、一套通信协议；新增业务只增加能力模块，不新增第二个插件。**

#### 分层结构

```text
业务页面 / 工作流 / Agent
          ↓
   统一前端桥接 SDK
          ↓
   平台浏览器任务服务
          ↓
   统一 Chrome 插件（单一扩展）
     ├─ 内容分发模块
     ├─ 获客采集模块
     ├─ 商品页/SEO 模块
     ├─ 未来的新业务模块
     └─ 公共能力：认证、站点授权、日志、回执
```

#### 能力目录

服务端维护统一能力目录，每个能力至少声明：

- 能力标识与版本；
- 适用业务模块；
- 支持平台与站点；
- 动作清单和输入/输出结构；
- 所需站点权限；
- 是否需要人工确认；
- 完成判定和证据要求；
- 失败重试与取消规则；
- 数据最小化要求；
- 最低插件版本。

插件启动或连接时上报自身版本和支持的能力。服务端按以下规则控制：

1. 插件版本低于某能力的最低版本时，不派发该能力任务；
2. 业务页面提示升级，而不是执行到一半失败；
3. 平台可灰度开启新能力，不影响旧版本已有功能；
4. 新版本发布保留一段兼容窗口，明确强制升级时间；
5. 能力下线前先停止派发，再清理入口。

#### 统一通信协议

所有业务共用同一套协议和桥接 SDK：

- 页面只发送“能力标识 + 参数”，不直接发送任意脚本；
- 插件只执行已登记动作，拒绝未知能力；
- 任务包含组织、用户、业务来源、目标平台、授权站点和执行凭证；
- 回执包含状态、结果、证据、错误码和版本；
- 禁止每个业务自行定义一套 postMessage 消息名和回执格式。

现有分发和获客链路应逐步收敛到这套协议，而不是长期保留两套并行机制。

> **实现状态（P3 阶段）**：统一协议已落地——契约 `packages/contracts/src/browser-task.ts`（任务/回执信封、
> 逐条结果口径 `FILLED/SUBMITTED/VERIFIED/FAILED/SKIPPED`、统一错误码）、页面侧 SDK
> `frontend/src/lib/extension-bridge.ts`（`pingExtension` 协商 `protocolVersion`、`sendBrowserTask`、
> `onBrowserReceipt`）、插件 `extensions/aipdd-enterprise/bridge.js`（`ping` 上报协议版本、
> `type: 'task'` 路由到已登记能力/动作、终态回统一 `type: 'receipt'`）。存量消息名作为过渡适配层保留：
> 统一通道与旧消息名同源同一条后台链路，页面按握手协议版本选择通道，业务侧逐步迁移。

#### 安全与隐私

- 不读取、保存或上传用户密码、Cookie、支付信息；
- 只在用户明确授权的站点和动作范围内运行；
- 使用可选站点权限，按业务需要申请，避免首次安装索取全部站点权限；
- 不加载远程可执行代码，更新必须通过正式发布包；
- 执行令牌绑定用户、组织、任务和有效期；
- 撤销授权、离职或服务终止后，旧令牌立即失效；
- 插件日志不记录页面正文、聊天内容等敏感数据。

### 10.8 迭代与发布规范

插件作为平台统一组件，需要按产品级组件管理：

1. **版本号**：语义化版本，能力变更明确标注兼容性；
2. **发布说明**：顶部入口的“更新记录”与业务侧升级提示同源；
3. **灰度发布**：先小范围组织启用，再全量；
4. **强制升级阈值**：旧版本无法安全执行某能力时，服务端拒绝派发；
5. **回滚**：保留上一稳定版本，出现严重问题时停止派发并回滚；
6. **兼容测试**：Chrome、Edge、不同操作系统、不同站点改版；
7. **站点适配监控**：平台页面结构变化导致失败时，能按平台统计失败率并快速修复；
8. **变更审计**：记录谁发布了哪个版本、影响了哪些能力。

### 10.9 新业务接入清单

后续任何业务需要浏览器能力时，必须按以下清单接入，而不是另起插件：

- [ ] 在统一能力目录登记能力、版本和支持平台；
- [ ] 明确哪些步骤必须浏览器执行、哪些应走 API；
- [ ] 定义人工确认点和完成证据；
- [ ] 声明站点权限和数据最小化范围；
- [ ] 接入统一任务服务和回执协议；
- [ ] 定义失败、取消、超时、重试和版本不兼容处理；
- [ ] 在工作流中增加“浏览器任务”节点或复用统一动作；
- [ ] 在顶部插件入口更新“支持能力”说明；
- [ ] 完成跨浏览器、跨站点改版的回归测试；
- [ ] 提供组织级开关和审计记录。

满足以上条件后，新业务只发布插件的新能力模块和对应服务端能力，不改变用户安装方式。

### 10.10 存量案例统一：以多平台发布为基准

当前营销工具中的**多平台发布**已经在使用该 Chrome 组件，这是平台统一插件的第一存量案例，应作为后续所有浏览器能力的参考实现，而不是与统一插件并列的另一套能力。

#### 统一原则

1. **不新建第二个浏览器插件。**  
   多平台发布、获客采集与触达、商品页辅助编辑、SEO/CMS 填充等，都属于同一插件的不同能力模块。

2. **不保留多套页面通信协议。**  
   存量业务逐步收敛到统一的能力标识、任务结构、执行状态和回执格式；过渡期内由适配层兼容，但不能长期并行。

3. **不重复建设任务与台账。**  
   浏览器任务统一进入平台任务服务，业务侧只保留自己的业务台账和结果关联，不各自维护一套队列、重试和回执。

4. **不按业务复制安装入口。**  
   所有业务统一使用顶部右上角的插件入口和同一份安装说明；业务页面只提示“需要安装/升级插件”，并跳转到统一下载页。

5. **统一版本与权限门槛。**  
   多平台发布支持哪些平台、需要什么站点权限、最低插件版本，都登记在同一能力目录中；新业务不能自行放宽权限。

#### 存量收敛步骤

| 步骤 | 内容 |
|---|---|
| 1 | 盘点当前已使用 Chrome 的业务入口，形成“业务—能力—平台—权限—回执”清单 |
| 2 | 把多平台发布登记为第一个标准能力，确定任务结构、状态和完成证据 |
| 3 | 将获客采集、触达等已有链路映射到同一协议，保留必要适配层 |
| 4 | 新业务一律按统一清单接入，不再新增独立插件或独立桥接 |
| 5 | 存量旧入口在能力目录中标记“已统一/待迁移”，给出迁移时间点 |
| 6 | 迁移完成后下线重复入口、重复协议和重复任务表 |

#### 判断是否属于“同类案例”

满足以下任一条件，应优先纳入统一插件：

- 需要用户已登录的浏览器会话；
- 目标平台没有稳定、可用的官方 API；
- 需要在网页上填充、上传、采集或读取渲染结果；
- 需要人工确认发布、提交或验证码处理；
- 已存在独立插件、脚本或页面桥接在完成类似动作。

如果目标平台有合规官方 API，仍应优先 API，不因统一插件而把服务端能力退化为浏览器执行。

#### 多平台发布的基准要求

作为参考实现，多平台发布应满足：

- 任务绑定组织、用户、业务来源和目标平台；
- 每个平台独立执行、独立回执，单平台失败不掩盖其他平台结果；
- 明确区分“已填充”“已提交”“已核实发布结果”；
- 页面关闭、浏览器重启后任务可恢复或可查询；
- 重复回执不重复写台账，旧执行凭证不能覆盖新结果；
- 平台页面结构变化可监控、可快速修复；
- 顶部插件入口展示当前版本和支持的平台能力；
- 业务侧不复制插件执行逻辑，只消费统一任务和回执。

后续商品页优化、SEO/CMS 辅助、其他平台运营等，均以这套基准接入。

## 十一、AI 赋能

### 11.1 原则

AI 应围绕业务闭环，而不是增加更多聊天框。

### 11.2 场景清单

| 场景 | AI 具体能力 | 形成的业务结果 | 人工边界 |
|---|---|---|---|
| 企业知识助手 | 按权限检索制度、客户、项目资料，附来源 | 回答可追溯、可打开原始记录 | 不检索无权访问的资料 |
| 经营异常助手 | 发现逾期回款、库存异常、项目超支 | 生成原因分析与责任任务草稿 | 指标口径由系统确定，不能由模型编造 |
| 销售助手 | 总结授权沟通记录、提取需求、建议下一步 | 跟进记录与行动计划 | 对外发送前确认 |
| 合同履约助手 | 提取期限、金额、交付和付款条件 | 履约节点、回款计划草稿 | 合同结论及正式入账需审核 |
| 会议/邮件助手 | 提取行动项、责任人、截止时间 | 待确认任务与业务归档 | 私人邮件只处理用户选定或授权范围 |
| 项目助手 | 综合任务、工时、变更识别风险 | 周报、风险清单、复盘草稿 | 不自动修改预算或承诺交期 |
| 财务助手 | 票据提取、重复识别、对账差异解释 | 报销草稿、异常清单 | 不自动付款、核销或改银行信息 |
| 采购库存助手 | 分析库存和需求，建议补货及供应商 | 采购申请草稿 | 下单和付款仍走授权审批 |
| HR/招聘助手 | 增强已有匹配、入职问答和培训建议 | 面试提纲、培训计划 | 不独立作出录用、薪酬或淘汰决定 |
| 客服知识助手 | 总结已解决问题，生成 FAQ | 待审核知识条目 | 不把客户私密内容直接发布 |
| 营销助手 | 复用获授权资产、生成内容、分析反馈 | 生产—审核—发布—反馈闭环 | 发布确认、素材权限和个人信息检查 |

### 11.3 AI 执行分级

1. **只读分析**：在权限范围内自动执行；
2. **生成草稿**：生成任务、表单、回复草稿，等待确认；
3. **实际执行**：必须有明确动作授权；付款、权限变更、敏感导出等仍需审批。

知识内容、邮件和网页中的文字不能成为系统指令；工具执行层必须真正限制可写动作，不能只在提示词里要求“不要越权”。

### 11.4 与工作流的关系

- 工作流可调用 AI 节点，但 AI 不直接修改业务敏感状态；
- AI 生成的待办、表单、采购申请等以草稿或待确认任务进入流程；
- AI 读取的数据范围不超过流程发起人和任务执行人的授权；
- AI 费用纳入流程预算。

### 11.5 本次落地（P4-8，2026-11-11）

| 缺口 | 落点 | 口径 |
|---|---|---|
| 工作流 AI 成本不可见 | `workflow-engine` 的 `ai.llm` / `ai.agent` 节点把 `usage` 随步骤落库（`output.__usage`），并经 `recordAiUsage` 写一条 `module=workflow` 的用量事实 | 与网关调用落在同一张 `usage_events`，运行详情与成本报表读同一处；无用量不补记空账 |
| 内置写/付费工具绕开 `allowWrite` | `BusinessTool` 增 `paid` 标记，`chrome_start_session` / `chrome_resume_session` 受 `allowWrite` 把关；`generate_image` / `generate_video` / `publish_to_library` 同样拦截 | 只读回合（定时任务未授权、副驾未开写开关）一律不发起点；提示用户到页面操作或打开「允许执行动作」 |
| 合同履约助手只停在聚合事实 | 新增 `Growth_fulfillmentAdvice`（GET）与 `Growth_dispatchFulfillment`（POST），增长驾驶舱「合同履约四态」下新增「合同履约助手」面板 | 只读四态事实 → 卡点 + 下一步动作（`module=growth`、`operation=fulfillment_advice`）；模型不可用或 JSON 不合规时退回规则式建议（`source=RULE`），结论同样可用；派单走任务中心 `assign`，幂等锚为合同主键，已闭环合同直接跳过 |
| 场景助手缺位（§11.2） | 页面助手升级为「路由→场景」：销售 / 合同履约 / 财务 / 采购库存 / HR·招聘 / 客服知识 / 营销 / 会议·邮件 八个场景各有定位、能力清单与人工边界，写进提示词；会议/邮件助手新增行动项提取（`Assistant_extractActions`），把责任人、截止时间抽成「待确认」任务进任务中心 | 场景未命中时仍是通用页面助手；文本只处理用户粘贴/选定的内容，模型不可用或 JSON 不合规时按行首「待办/TODO/行动项」规则式兜底；AI 不直接改业务状态 |
| 费用与执行预算（§7.3-9）未落地 | 工作流新增 `budgets` 配置（`maxNodes` / `maxAiCalls` / `maxTokens` / `maxToolCalls` / `maxBrowserActions`，0＝不限），运行创建时快照到 `workflow_runs.budgets`；引擎按波开计量器：数量类在开跑前**预占**（AI 调用 / 工具调用 / 浏览器动作 / 节点次数），token 因只有事后才知用量按波结算 | 触顶即停在节点边界、运行记 `budget_stop`（`NONE`/`AI_CALLS`/`TOKENS`/`TOOL_CALLS`/`BROWSER_ACTIONS`/`LOOP_LIMIT`）与 `usage`；改预算不影响在途运行。编辑器工具栏「执行预算」配置，运行记录与试跑面板展示用量与「超预算」标记 |

助手不写业务状态：卡点判定仍以四态只读聚合为准（`growth-cockpit.service#fulfillment`），模型只负责把原因和动作说具体，金额、客户名、卡点都由系统事实给出。

## 十二、平台默认模型与充值用户继承

### 12.1 产品规则

> **用户完成真实充值且积分结算成功后，如果没有配置对应能力的个人模型，可以自动使用平台管理员设置的默认模型，并从自己的积分账户扣费。**

规则建议：

1. 不额外增加充值金额或次数门槛；
2. 注册赠送、邀请奖励、管理员调账，不单独构成“完成充值”资格；
3. 获得资格后，仍需余额充足、账号正常、模型可用；
4. 按能力分别继承：配了文本模型，仍可继承图片或语音模型；
5. 不要求用户另外绑定自己的上游 API Key；
6. 充值资格只授予模型使用能力，不扩大业务数据权限；
7. 充值退款或撤销支付时重新计算资格；存在其他有效充值时，不直接取消全部资格。

### 12.2 管理后台

建议在**模型广场管理中增加“默认模型配置”页签**，包含：

- 平台默认模型总开关；
- 各能力的默认模型；
- 模型当前可用状态与调用价格；
- 单次用量限制、账号日/月消费限额；
- 配置变更记录与生效时间。

候选模型只来自模型广场已启用、通道可用且能力匹配的模型：

| 能力 | 典型用途 |
|---|---|
| 文本 | 问答、总结、结构化提取、业务文案 |
| 视觉 | 图片理解、票据和截图分析 |
| 图片 | 营销配图、内容创作 |
| 视频 | 视频生成 |
| 语音识别 | 音频转文字 |
| 语音合成 | 文字转语音 |
| 向量 | 知识检索与相似匹配 |

具体开放哪些类型，以现有适配器和模型实际能力为准，不用一个普通文本模型代替所有能力。

### 12.3 模型选择顺序

**本次明确选择 → 已明确绑定的模块模型 → 个人该类型模型 → 平台该类型默认模型。**

并要求：

- 历史有效配置先纳入统一解析，不随意覆盖；
- 个人模型已配置但调用失败，不自动切换成收费的平台模型；
- 用户清空个人该类型配置后，可恢复继承；
- 自动后台任务只有在用户启用该任务并授权消费预算后，才能使用平台默认模型；
- 继承实时解析，不批量复制为用户个人配置。

### 12.4 技术落点

现有 LocalAPI 通道已经支持无需用户 Key、按调用用户身份使用模型广场，见 `backend/src/ai/ai-channels.ts:43`。

建议：

- 平台保存各能力对应的模型目录引用；
- 统一模型解析返回“配置来源：个人/模块/平台”；
- AI 网关与内容创作的多媒体解析入口共用这套规则；
- 调用走模型广场的服务器端通道；
- 上游凭据不发送到前端，也不复制到用户账户。

### 12.5 积分计费

必须保证：

> **同一笔模型用量只扣一次模型费用。**

要求：

- 模型费用由统一的模型计费链结算，价格复用模型广场；
- 若某业务另有服务费，应单独展示科目，不能隐藏成第二笔模型费；
- 默认扣调用用户的积分，不扣平台管理员的个人钱包；
- 企业代付作为后续能力，需明确付款主体、成员授权和额度；
- 请求、用量、积分流水、异步任务使用可关联的幂等标识；
- 调用前检查预算并预占，调用后按实际用量结算；
- 未产生应计用量的失败释放预占；部分完成按明确的计费规则结算；
- 上游结果未知时进入对账，不能盲目重试并重复扣费。

当前模型广场主要是调用前检查余额、调用后扣费，见 `backend/src/model-plaza/usage.service.ts:73`。开放默认继承前，应补足并发消费和长任务的费用控制。

### 12.6 充值一致性

当前充值结算先写订单 `PAID`，再分别增加本金和赠送积分，见 `backend/src/points/recharge.service.ts:155`。

建议将以下事项作为一个可恢复、可对账的结算过程：

- 支付确认；
- 本金入账；
- 赠送入账；
- 充值资格生效。

不能仅见到 `PAID` 就认定所有步骤完成，否则中断时可能出现“显示充值成功，但积分未完整到账”。

### 12.7 用户体验

用户侧不再提示「平台默认模型」：继承来的默认模型对用户透明，`/model-settings` 只呈现用户自己的渠道与默认模型配置。

未充值、余额不足、模型不可用时，在调用侧给出对应提示，而不是统一提示“请配置 API Key”。

### 12.8 本次实现（2026-11-10）

- **管理端**：后台「计费与商品 → 模型广场」新增「默认模型」页签——总开关、按能力选择目录模型（只列已上架且能力匹配的候选，附折后价与不可用原因）、单次 / 日 / 月积分限额、变更记录；配置存 `system_setting.model_platform_defaults`，变更写审计。
- **资格判定**：只统计 `RechargeOrder.status = PAID` 的充值单，注册赠送、邀请奖励、管理员调账均不构成资格；退款或撤销支付后按剩余有效充值重新计算。
- **解析阶梯**：显式选择 → 模块绑定 → 个人该类型模型 → 历史 RPA / Workbuddy 配置 → 平台该类型默认模型。个人或历史配置已存在但调用失败时直接返回“无可用模型”，不自动切到收费的平台模型。
- **能力口径**：文本、视觉、图片、视频、语音识别、语音合成、向量；能力由模型声明的端点与输入模态推导，不用普通文本模型顶替。图片 / 视频 / 语音等媒体任务走内容创作同一条解析入口。
- **计费与限额**：站内调用走模型广场 LocalAPI 通道（`channelId = -1`），按目录折后价扣调用者积分；调用前校验日 / 月额度与预估费用，单次扣分按「单次限额」封顶，失败不计费，同一用量只结算一次。
- **用户侧**（2026-11-11 调整）：`/model-settings` 不再展示「平台默认模型」——面板、继承说明、未启用原因与充值入口均已移除，用户侧只保留自己的渠道与默认模型配置；继承情况仅管理端可见。
- **接口**：`GET /enterprise/model-plaza/platform-status`、`GET|PUT /enterprise/admin/model-plaza/platform-defaults`。

## 十三、完整业务示例：每周内容代运营

1. 企业启用“每周内容运营”模板，选择品牌、渠道、服务商和预算。
2. 工作流按计划获取**获授权**的产品资料和素材。
3. AI 生成选题、文案与图片，产物进入相应资产空间。
4. 企业负责人收到审核任务。
5. 审核通过后，任务进入代运营服务商工作池。
6. 服务商按客户主办关系和人员负载分配运营人员。
7. 运营人员在授权浏览器中认领发布任务。
8. 插件辅助填充；需要人工确认的渠道等待确认。
9. 各渠道结果分别回传；失败只处理失败渠道。
10. 服务商提交交付清单，企业按发布链接等证据验收。
11. 到期后通过 API 或授权浏览器辅助收集效果数据。
12. AI 生成复盘，形成下周优化建议。

这个闭环同时复用了：

> **数字资产、模型广场、默认模型、积分、工作流、任务中心、服务商成员、Chrome 插件、通知、验收和经营分析。**

与平台默认模型的关系：

- 哪个账号获得使用资格；
- 谁批准这条流程自动消费；
- 费用由企业发起人、服务商，还是另行授权的企业预算承担；
- 服务商接单不代表可以任意扣客户积分；
- 没有明确预算授权时，应暂停等待确认，而不是自动收费。

费用授权与数据授权仍然是两回事。

## 十四、事件、通知与任务可靠性

### 14.1 事件与通知

建议采用：

- 业务变更与待发送事件在同一事务提交；
- 每个消费者独立记录处理状态；
- 每个动作有幂等键，重复投递不重复建单或扣费；
- 自动重试、失败队列、人工重放与运行监控；
- 多实例调度通过原子抢占避免重复执行；
- 区分业务成功、通知成功、外部系统同步成功。

### 14.2 任务对账

- 业务状态以原模块为准；
- 任务中心是聚合/投影，不是第二个权威状态机；
- 不能把单次分页未返回当作已办结；
- 外部主体 ID 与用户 ID 必须区分类型；
- 任务关闭、重开、取消、超时有明确规则；
- 工作流任务源是推送型，应避免被普通对账误关。

### 14.3 通知渠道

- 站内通知是基础事实；
- 微信服务号、H5 是触达和办理入口；
- 敏感通知默认只推摘要，详情登录后查看；
- 通知发送成功不等于业务完成；
- 去重、重试和失败监控纳入统一投递。

## 十五、账号找回密码与登录方式统一

### 15.1 现状结论

当前系统**后端已经实现找回密码接口**，但产品入口和策略统一还不完整。

| 能力 | 当前状态 | 结论 |
|---|---|---|
| 邮箱验证码找回密码 | 后端支持 | 已有基础，可复用 |
| 手机验证码找回密码 | 后端支持 | 已有基础，可复用 |
| 登录页“忘记密码”入口 | 未发现前端页面或入口 | 缺失 |
| 邮箱重置链接 | 配了链接前缀会发 `/reset-password?token=`，但前端无该路由，后端 reset 接口只接受邮箱+验证码 | 链路不完整，暂不应启用 |
| 找回渠道与管理员登录方式统一 | 找回接口未按 `loginMethods` 开关判断 | 缺失，需要统一 |
| 手机验证码登录后设置新密码 | 已登录修改密码仍要求输入旧密码 | 缺失 |
| 重置后会话失效 | 重置密码会递增 tokenVersion | 已有基础 |

代码依据：

- 发送找回验证码：`backend/src/account/account.service.ts:724`
- 校验并重置密码：`backend/src/account/account.service.ts:746`
- 已登录修改密码仍要求旧密码：`backend/src/account/account.service.ts:792`
- 找回路由：`backend/src/account/account.routes.ts:438`、`backend/src/account/account.routes.ts:450`
- 登录方式与可用性：`backend/src/account/account-settings.service.ts:94`、`backend/src/account/account-settings.service.ts:112`
- 重置链接分支：`backend/src/account/notify-channel.service.ts:45`
- 登录页未发现找回入口：`frontend/src/app/login/page.tsx`

### 15.2 产品目标

> **登录方式、找回密码方式、已登录后的密码设置方式，必须来自平台管理员同一份账号策略，不能各自判断。**

统一后的能力包括：

1. 未登录时，用邮箱验证码找回密码；
2. 未登录时，用手机验证码找回密码；
3. 已用手机验证码登录后，无旧密码也能用手机验证码设置新密码；
4. 已用邮箱验证码登录后，在满足条件时可用邮箱验证码设置新密码；
5. 管理员关闭某种登录方式后，对应找回方式同步关闭；
6. 管理员未配置 SMTP 或短信通道时，对应找回入口不展示，后端也拒绝；
7. 至少保留一种登录方式；找回方式可以少于登录方式，但不能反过来出现“登录没开、找回却能走”的旁路。

### 15.3 统一策略模型

平台管理员的账号登录设置应形成一份统一矩阵：

| 登录方式 | 是否开启 | 依赖配置 | 可用于登录 | 可用于找回密码 | 可用于已登录设置密码 |
|---|---|---|---|---|---|
| 账号密码 `PASSWORD` | 管理员控制 | 无 | 是 | 不适用 | 需旧密码，或走验证码方式 |
| 邮箱验证码 `EMAIL_CODE` | 管理员控制 | SMTP | 是 | 是 | 是（邮箱已验证） |
| 手机验证码 `SMS_CODE` | 管理员控制 | 阿里云短信 | 是 | 是 | 是（手机已验证） |
| 微信登录 `WECHAT` | 管理员控制 | 微信参数 | 是 | 否 | 否 |

规则：

- `EMAIL_CODE` 开启且 SMTP 已配置 → 登录页显示邮箱验证码登录，同时显示邮箱找回密码；
- `SMS_CODE` 开启且短信已配置 → 登录页显示手机验证码登录，同时显示手机找回密码；
- 两种验证码方式都不可用 → 登录页不显示“忘记密码”入口；
- 密码登录关闭时，不展示“找回密码”，避免出现“能重置但无法用密码登录”的无效入口；
- 管理员修改登录方式后，登录页和找回页都实时读取同一配置，不缓存旧能力；
- 找回接口必须在服务端再次校验，不能只靠前端隐藏入口。

### 15.4 未登录找回密码流程

```text
登录页点击“忘记密码”
        ↓
选择邮箱或手机号（只展示管理员已开启且通道可用的方式）
        ↓
输入邮箱/手机号并获取验证码
        ↓
输入验证码 + 新密码
        ↓
服务端校验策略、验证码、密码强度
        ↓
更新密码、递增 tokenVersion、记录审计
        ↓
提示“密码已重置，请重新登录”
```

要求：

- 邮箱和手机号输入格式分别校验；
- 账号不存在时与存在时返回同样的“已发送”提示，避免探测账号；
- 验证码 5 分钟有效、一次性使用、错误次数受限；
- 同一 IP、同一目标、同一账号分别限流；
- 新密码遵循统一密码策略；
- 重置成功后所有旧会话失效，未登录流程要求重新登录；
- 不自动登录，避免验证码被撞库后直接获得会话。

### 15.5 已登录后设置/重置密码

用于以下场景：

- 用户通过手机验证码登录，从未设置过密码；
- 用户忘记旧密码，但当前仍保持登录；
- 用户需要主动更换密码。

建议入口放在“账号安全 / 登录与安全”设置中，提供两种方式：

1. **知道旧密码**：输入旧密码 + 新密码；
2. **不知道旧密码**：通过已验证的手机号或邮箱验证码设置新密码。

规则：

- 验证码方式必须证明当前账号绑定的手机号/邮箱，不能给任意号码发码；
- 手机验证码登录后，优先允许手机验证码设置密码；
- 邮箱验证码方式仅在邮箱已验证且管理员开启 `EMAIL_CODE` 时可用；
- 已登录场景使用独立的 `SET_PASSWORD` 验证码场景，不与未登录 `RESET_PASSWORD` 混用，避免跨场景重放；
- 设置成功后递增 tokenVersion，当前设备换发新会话，其他设备退出登录；
- 若账号没有绑定手机或邮箱，提示先完成绑定，或由管理员重置；
- 管理员批量重置密码仍保留在后台，但应审计并标记 `mustChangePassword`。

### 15.6 接口与页面改造建议

#### 后端

- `requestPasswordReset` 增加：
  - `loginMethods()` 校验；
  - SMTP/短信通道可用性校验；
  - 按 IP、目标、账号的限流；
  - 统一脱敏应答。
- `resetPassword` 增加：
  - 同样的策略校验；
  - 密码策略统一；
  - 重置后会话失效；
  - 审计记录。
- 新增已登录验证码设置密码接口，例如：
  - `POST /enterprise/account/password/code`：向当前账号已绑定的手机/邮箱发送设置密码验证码；
  - `POST /enterprise/account/password/set-by-code`：校验验证码并设置新密码。
- 如果保留邮箱链接找回：
  - 增加可访问的 `/reset-password` 页面；
  - 链接必须携带可解析的目标或一次性票据；
  - 后端增加 token 校验接口；
  - 未完成前不要仅靠 `resetLinkBase` 就发链接邮件。

#### 前端

- 登录页增加“忘记密码”入口，条件由账号配置决定；
- 新增找回密码页面，支持邮箱/手机两种方式；
- 账号安全设置增加“设置密码/修改密码”，支持旧密码和验证码两种路径；
- 管理后台账号登录面板显示：
  - 登录方式开关；
  - 对应通道是否配置；
  - 找回密码是否可用；
  - 关闭某方式后对找回的影响提示。

### 15.7 安全要求

- 防止账号枚举：账号不存在时也返回已发送；
- 防止验证码爆破：错误次数上限、有效期、一次性消费；
- 防止短信轰炸：目标、IP、账号、日限额多维限流；
- 防止跨场景重放：登录、注册、找回、换绑、设置密码使用不同 scene；
- 防止会话残留：重置后递增 tokenVersion；
- 防止弱密码：统一长度、字符类型和常见密码校验；
- 防止越权：已登录设置密码只能操作当前账号；
- 全流程审计：谁、何时、通过哪种渠道重置或设置密码。

### 15.8 验收标准

| 场景 | 预期 |
|---|---|
| 管理员开启邮箱验证码且 SMTP 正常 | 登录页显示邮箱验证码登录和邮箱找回；可完成找回 |
| 管理员开启手机验证码且短信正常 | 登录页显示手机验证码登录和手机找回；可完成找回 |
| 管理员关闭邮箱验证码 | 邮箱找回入口隐藏；直接调用接口被拒绝 |
| 管理员关闭手机验证码 | 手机找回入口隐藏；直接调用接口被拒绝 |
| SMTP/短信未配置 | 对应入口不显示；接口返回可操作的管理员配置提示 |
| 两种验证码方式都不可用 | 不显示“忘记密码”入口 |
| 账号不存在 | 与存在账号返回一致，不泄露注册信息 |
| 验证码过期/重复/错误多次 | 均被拒绝，且需要重新获取 |
| 手机验证码登录后无旧密码 | 可通过手机验证码设置新密码 |
| 邮箱链接找回 | 要么完整可用，要么不发送链接，不能出现死链 |
| 重置成功 | 旧会话失效，新密码可登录，审计有记录 |
| 管理员修改登录方式 | 登录页与找回页同步变化，无需重新发布前端 |

### 15.9 实施优先级

建议列为 **P1：账号安全与登录体验**，与平台默认模型、统一组织上下文同期推进。

优先级高于新增业务功能，因为它同时影响：

- 新用户首次使用；
- 手机验证码登录用户的密码可用性；
- 账号安全与客服成本；
- 平台管理员对登录策略的统一控制。

## 十六、实施路线

### 第一阶段：权限与资金安全底线

- 修复已确认的对象授权、筛选覆盖、来源资产授权问题；
- 明确组织归属与敏感字段规则；
- 修复充值结算一致性，确定模型计费唯一入口；
- 建立跨账号、跨组织、跨角色回归测试；
- 修复工作流等待恢复和任务对账问题。

### 第二阶段：统一上下文与默认模型

- 收敛组织选择和数据范围；
- 推出平台默认模型配置、充值资格及用户继承；
- 覆盖文本、多媒体、知识处理、Agent、工作流等实际调用入口；
- 完善离职撤权、导出与附件权限；
- 统一登录方式、找回密码与已登录设置密码策略；
- 上线顶部 Chrome 插件入口，提供统一下载、安装说明、版本状态和能力介绍。

### 第三阶段：统一编排与派单

1. 营销内容生成 → 审核 → Chrome 分发 → 结果回收；
2. 企业服务任务 → 服务商接单 → 内部分派 → 交付验收；
3. 业务到期事件 → 自动待办 → 超时升级 → 原业务办结。

同时完善：

- 工作流持久等待、结构化人工任务、业务结果分支、并行汇合和运营故障处理；
- 统一插件能力目录、单一扩展和统一通信协议；
- 浏览器任务服务、持久队列、认领租约、版本门槛和结果回执；
- 分发、获客及新业务能力逐步收敛到同一个插件。

### 第四阶段：业务闭环与 AI

- 销售—合同—项目—回款；
- 项目—工时—采购报销—成本；
- 入职—岗位授权—离职交接；
- 权限感知 AI 问答、总结和草稿；
- 经过验证的业务执行与跨模块 Agent；
- 经营异常自动化；
- 合同履约四态聚合视图与履约助手（卡点 → 下一步动作 → 派履约任务）。

### 迁移原则

- 不凭“第一条成员关系”猜测历史数据归属；
- 无法确定归属的数据进入待确认清单；
- 新增归属字段先回填、验证，再收紧约束；
- 保留来源记录、审计信息和回滚路径；
- 同时验证 MySQL、PostgreSQL 的迁移及约束行为；
- 不在整合过程中重置用户已有模型配置；
- 现有业务自动联动与工作流接入必须确定唯一执行入口。

## 十七、验收标准

| 类别 | 验收要求 |
|---|---|
| 租户隔离 | A 组织账号不能通过 ID、筛选、导出、AI 或附件入口读取/修改 B 组织数据 |
| 敏感字段 | 普通成员不能获得未授权的人事成本、财务或管理备注 |
| 撤权 | 离职后，直接访问、旧分享、导出下载和后台任务均重新校验 |
| 模型继承 | 已充值且未配置对应模型的用户可以直接使用；个人配置不被覆盖 |
| 计费 | 一次用量只结算一次；并发、重试、流式中断、异步查询不重复扣费 |
| 充值 | 重复回调或中断恢复后，订单、本金、赠送和资格保持一致 |
| 业务联动 | 同一来源重复触发不重复建项目、任务、应收或采购单 |
| 任务可靠性 | 分页、同步失败、业务重开不会造成误完成或永久丢失 |
| 工作流 | 服务重启可恢复；等待、取消、拒绝、超时、返工分支正确 |
| 派单 | 无合格执行人时进入待分派，不越权兜底；转派后旧执行人不能继续办理 |
| 服务商隔离 | 服务商只看到授权任务，员工只看到自己获授权的内容 |
| 插件执行 | 离线、页面关闭、登录失效时任务不丢、不误报成功 |
| 插件结果 | 已填充、已提交、已核实发布结果严格区分 |
| 插件入口 | 顶部入口与微信等图标并列；无插件包或全局关闭时不显示；移动端不误导 |
| 插件版本 | 未安装、已安装、版本过低可识别；打开入口自动检测，安装后自动更新状态 |
| 插件统一 | 多平台发布作为基准能力；同类浏览器业务不新增独立插件或第二套协议 |
| 存量收敛 | 已知同类入口登记在能力目录，明确已统一/待迁移；迁移完成后重复入口下线 |
| 插件权限 | 仅申请业务所需站点权限；不读取密码、Cookie；撤销授权后旧任务不能继续执行 |
| 登录策略 | 登录方式、找回方式和已登录设置密码共用平台管理员配置，关闭后无旁路 |
| 找回密码 | 邮箱/手机验证码找回可用；入口按策略显隐；防枚举、防爆破、重置后旧会话失效 |
| AI 权限 | AI 可读范围不超过调用者，写操作必须通过业务授权和确认 |
| 可追溯性 | 每次自动执行能查到操作者、组织、业务来源、模型、费用与结果 |

## 十九、结论

下一阶段不应继续横向增加独立功能入口，而应优先完成六件事：

1. **统一组织与数据权限**，让所有模块、导出、AI 和插件遵循同一授权边界；
2. **打通核心业务闭环**，让客户、合同、项目、任务、交付、回款和成本互相关联；
3. **把工作流、任务、派单和浏览器执行做成共享底座**，由业务模块定义规则，底座负责何时办、谁来办、如何执行和如何回流；
4. **只维护一个平台级 Chrome 插件**，通过顶部统一下载入口触达用户，多平台发布等存量能力作为基准案例，同类业务全部收敛到同一插件能力目录；
5. **统一账号登录与找回密码策略**，让密码、邮箱验证码、手机验证码和微信登录及其找回方式都由平台管理员同一份配置控制；
6. **让 AI 与默认模型在可控预算和授权范围内使用**，通过充值资格降低使用门槛，同时保证一笔用量只计费一次。

这样既能减少数据孤岛，也能让服务商、员工、AI 和浏览器执行能力真正协同起来，而不是形成更多新的孤岛。
