# 工作流编排与任务派单升级设计方案

> 状态：**已确认，实施中**。日期：2026-11-10。决策：**D1=A、D2=C、D3=A、D4=A、D5=A、D6=A、D7=B、D8=A**（详见第十二节）。
> D2=C 的执行口径：**不开放任何外部 Webhook 触发**。`trigger.webhook` 节点、`Workflow_hookToken / Workflow_hookReset` 契约、`WorkflowHookToken` 表、`hooks/:token` 路由全部不落地；B1 只做「调度器 + 领域事件桥 + 任务事件桥 + 内部 invoke」。出站方向的 Webhook 订阅（机制服务 Outbox）与 `integration.webhook` 动作节点不受影响，仍照旧。
> 范围：在已交付的「我的任务（统一任务中心）」「工作流」「AIPDD Enterprise 浏览器插件」三项底座之上，回答五件事：
> ① 全局还有哪些需求可优化；② 营销工具里哪些真的需要插件；③ 哪些任务应由工作流生成与分配；④ 服务商 → 业务执行人的派单怎么落；⑤ 工作流引擎能否作为底层服务。
> 本文件只做设计与判定，**不含任何代码改动**；第十二节的 D1–D8 需要你按编号拍板后才进入实施。

## 〇、结论先行

1. **三项底座已经具备"承重"的形状，缺的是"接线"**：任务中心已有统一写入/聚合/关闭/对账（`backend/src/task-center/`），工作流已有节点目录自动派生、DAG 编译、版本冻结、运行步骤、Agent 工具（`backend/src/workflow/`），插件已同时承担分发与获客。但三者之间只有一条线（`workflow` 任务源），其余全是断点。
2. **21 个营销工具里，只有 2 个必须用插件**：AI 获客、多平台内容分发。其余 19 个走服务端 API 或本系统内部服务，**不应为了"统一"而迁到插件**。
3. **工作流当前只有「手动 / Agent」两个真触发**：`trigger.schedule / event / webhook / task` 只是画布上的标记节点，运行时直接返回 `DONE`，没有调度器、没有事件订阅、没有入口路由。这是"工作流当底层服务"的第一块短板。
4. **任务中心只有「派给某个账号」一种派单语义**：`MyTask.assigneeUserId` 是单账号；没有组织收件箱、没有服务商 → 执行人的转派、没有按规则/负载自动分派。各板块现有的"指派承办人"是**企业级默认值**（`ProviderAssignment`）或**少数单据级**（`supply.assignOrder`），不是统一原语。
5. **推荐的目标架构是四层而不是一个大引擎**：编排层 = 工作流；派单层 = 任务中心（新增 `TaskRouter`）；执行层 = 站内服务 + 插件；事件层 = 机制服务（`MechanismEventService`）。工作流不吞并派单，派单不反向依赖工作流，二者通过事件与内部 API 对接。
6. **一次交付的边界建议**：D1–D8 确认后，按第九节 B1–B7 连续做完，不分期；其中 B1（真触发）与 B2（派单原语）是其余所有能力的前置。

### 1.2 已确认的断点（逐条给证据）

| # | 断点 | 证据 |
|---|---|---|
| 1 | 定时/事件/Webhook/任务变化四类触发不生效 | `workflow-engine.ts` 的 `runNode` 对 `trigger.schedule / event / webhook / task` 统一走 `return { status:'DONE', output:{trigger:…} }`；无 `WorkflowScheduler`、无 `MechanismEventService.on(...)` 订阅、无 `hooks/:token` 路由 |

| 6 | 无重试/超时/取消 | `runStep.attempts` 只在重入时 +1；没有失败重试策略、没有节点超时、运行没有取消接口 |

| 12 | 工作流没有运行历史页 | 只有编辑器 Playground 的单次运行；`Workflow_runDetail` 无列表接口 |

### P0 — 不做则"底层服务"名不副实

| 编号 | 问题 | 影响 | 建议 |
|---|---|---|---|
| P0-1 | 四类触发是空壳 | 用户配了「每周一 9 点」不会跑，属**承诺未兑现** | 补调度器 + 领域事件桥 + 任务事件桥（B1）；`trigger.webhook` 按 D2=C 直接下架，不再为"不开放"的能力留空壳节点 |

## 三、承重设计：四层 + 四个统一

```
┌──────────────────────────────────────────────────────────────┐
│ 编排层  Workflow（图 / 版本 / 运行 / 人工节点 / 试跑）          │
├──────────────────────────────────────────────────────────────┤
│ 派单层  Task Center（工作项 + TaskRouter + 组织收件箱 + 摘要）   │
├──────────────────────────────────────────────────────────────┤
│ 执行层  站内服务（contracts endpoints） │ AIPDD 插件（浏览器动作）│
├──────────────────────────────────────────────────────────────┤
│ 事件层  MechanismEventService（领域事件 / 规则 / Webhook Outbox）│
└──────────────────────────────────────────────────────────────┘
```

### 3.1 四个「统一」

| 统一 | 含义 | 落点 |
|---|---|---|
| **统一触发源** | 手动、定时、领域事件、任务变化、Agent/MCP 五类触发都落到 `WorkflowService.invoke({workflowId|businessKey, trigger, input, actor, sourceRef, dedupeKey})` 一个入口（外部 Webhook 按 D2=C 不开放） | B1 |
| **统一工作项** | 任何需要人做的事（审批、回复、填报、线下办理、插件补发）都写 `MyTask`；业务状态仍在源模块 | 已有，补 `assigneeType` |
| **统一派单原语** | 派给谁只由 `TaskRouter.resolve()` 决定：显式账号 / 组织队列 / 规则 / 轮询 / 负载 | B2 |
| **统一动作目录** | 工作流节点、规则动作、Agent 工具三者共用 `endpoints` + `AGENT_TOOL_MANIFEST` 一份目录 | 已有，补规则动作 |

### 3.2 层间只允许单向依赖

```
Workflow ──派单──▶ TaskCenter ──事件──▶ MechanismEvent ──触发──▶ Workflow
     └──────────调用（运行发起人身份）──────────▶ 业务服务
TaskCenter ──关闭回调──▶ 源模块 / Workflow（按 source）
```

- **TaskCenter 不认识 Workflow 的内部结构**，只通过 `TaskSource.onClosed` 回调；
- **Workflow 不认识业务表**，只通过契约动作节点调用；
- **业务模块不上报"待办"给驾驶舱**，只实现 TaskSource 或发 draft。

## 四、工作流作为底层服务（能否、怎么落）

**结论：能，但必须先补三块地基（触发、内部调用契约、事件回流），否则只是"一个可视化页面"。**

### 4.1 内部调用 API（给其它模块用）

```ts
// WorkflowService 新增（非 HTTP，进程内调用）
invoke(input: {
  workflowId?: number;
  /** 稳定别名：发布时生成，模块可写死 businessKey 而不依赖自增 id */
  businessKey?: string;
  trigger: WorkflowTrigger;
  actor: CurrentUser;
  input?: Record<string, unknown>;
  /** 业务关联：单据类型 + 主键，用于"由哪个工作流驱动"反查 */
  sourceRef?: { type: string; id: string | number };
  /** 幂等键：同一业务事件重复投递只起一次 */
  dedupeKey?: string;
}): Promise<{ runId: number }>;
```

- 同步/异步两种：`invoke` 立即返回 `runId`（异步，默认）；需要结果时用 `Workflow_runDetail` 或 SSE 订阅。
- 权限：以 `actor` 身份跑，动作节点继续走 `runtime.runOperation`，**不新增绕过模块校验的通道**；跨组织调用由 `orgKeys` 判定。
- `businessKey` 的作用：让业务代码写 `invoke({businessKey:'acquisition.followup'})`，管理员在 UI 里换绑实现而不改代码。

### 4.2 真触发（B1）

| 触发 | 实现 | 幂等/防重 |
|---|---|---|
| `trigger.manual` | 已有 | — |
| `trigger.schedule` | 新增 `WorkflowScheduler`（进程内 60s tick；与 GEO/BI 的既有调度同风格），扫 `PUBLISHED` 且图中含 `trigger.schedule` 的工作流；cron 只支持 5 段标准表达式 | 每个 `(workflowId, 计划时间点)` 唯一，落 `workflowRun.dedupeKey` |
| `trigger.event` | 在 `MechanismEventService.dispatch` 的 listener 链上注册桥接：`event` 名匹配 → `invoke` | `eventLog.id` 作幂等键 |
| `trigger.webhook` | **不实施（D2=C）**：不开放外部触发入口，画布目录里也不提供该节点 | — |
| `trigger.task` | `TaskCenterService` 在 `assign`（created）/ `close`（closed）/ 逾期扫描（overdue）后发事件 | `myTask.id + 事件类型` |
| `trigger.agent` / `mcp` | 已有（`wf__<id>`） | 调用方 requestId |

> 口径说明：本方案不新增任何免登录的公开触发面（D2=C）。所有触发都在进程内以 `actor` 身份发起，动作节点继续走 `runtime.runOperation`，权限与审计由业务模块自己把关。

### 4.3 事件与规则（B3）

```ts
// 规则动作新增（mechanism-event.service.ts runAction）
| { type: 'run_workflow'; target: string /* workflowId 或 businessKey */; payload?: Row }
| { type: 'assign_task'; target: string /* userId 或 ORG:providerUserId */; payload: Row }
```

- `run_workflow`：复用 4.1 的 `invoke`，`trigger:'EVENT'`，`dedupeKey = ruleId:eventLogId`；
- `assign_task`：直接写任务中心（`source:'rule'`，`sourceId = ruleId:eventLogId`），支持组织收件箱（见第五节）；
- 两个动作都进 `ruleExecution` 审计，失败不阻断其它动作。

### 4.4 表单节点结构化（B4）

| 层 | 落地 |
|---|---|
| 存储 | `my_tasks` 增 `form_schema` / `form_data` 两列（JSON，迁移 `0061_my_task_form`）；普通任务保持 `NULL` |
| 定义 | `human.form` 的 `fields` 收敛为 `[{ key, label, required }]`；`WorkflowEngine.runForm` 校验字段并把定义写入任务的 `formSchema`，无字段直接节点失败 |
| 契约 | 新增 `MyTask_submitForm`（`POST /enterprise/my-tasks/:id/form`，body `{ values, note? }`）；`myTaskSchema` 增 `formSchema / formData` |
| 提交 | `TaskCenterService.submitForm` 按定义校验必填 → 写 `formData` → 复用 `finish`（终态 + `closed` 事件 + 源模块 `onClosed`）；已关闭任务、非表单任务拒绝提交 |
| 回写 | `WorkflowEngine.resumeFromTask` 把 `task.formData` 写进等待步骤产出 `form`，下游可用 `{{nodes.<id>.form.<key>}}`；未填的可选字段不出现在产出里 |
| 前端 | `/tasks` 对表单任务显示「填写」入口，弹窗按字段定义渲染；必填前端先拦、后端再校验；已提交字段值在任务行内回显 |

- 表单提交与「本人关闭」共用同一条办结路径，因此 `closed` 事件、工作流唤醒、源模块回调的行为完全一致，不存在第二套关闭状态机。
- 字段值只收字符串并截断到 2000 字；未在定义里的键一律丢弃，避免把任意表单内容写进 JSON 列。

### 4.5 引擎补强（B5）

| 项 | 设计 |
|---|---|
| 真并行 | `logic.parallel` 出边目标按 `Promise.allSettled` 并发执行（单次运行并发上限默认 4，可配）；节点间仍按各自入度就绪，`context.nodes` 用不可变快照避免竞态 |
| 重试 | 节点 `config.retry = { times: 0..5, backoffMs: 0..30s }`；只对可重试节点生效：人工节点、写动作（`operation.method !== 'get'`）、未知 Agent 工具一律不自动重试（D6），步骤记实际尝试次数 |
| 超时 | 节点 `config.timeoutMs`（钳制 ≤600s），缺省按动作 60s / AI 180s / Webhook 30s；超时只约束外层等待，在途请求不中断，步骤记 `TIMEOUT`、运行记 `FAILED` |
| 取消 | `Workflow_runCancel`：`RUNNING` 在下一次波次边界停；`WAITING` 直接把等待步骤记 `CANCELED` 并结束运行；终态幂等返回，发起人 / 工作流创建人 / 管理员可取消 |
| 关联业务 | `workflowRun` 增 `sourceType / sourceId`，列表与单据页可反查 |
| 运行列表 | `Workflow_runList`（按 `workflowId / status / sourceType / sourceId` + 分页，可见范围与工作流一致），供 `/workflow` 运行记录页签与运维排查；行内可展开看每步状态 / 尝试 / 耗时 / 错误 |

### 4.6 工作流与业务模块的"增强"范式（不推翻业务代码）

1. **不改业务服务**：工作流通过契约动作节点调用同一个端点，权限/校验/审计由模块自己把关；
2. **在业务侧只加一行**：需要"单据状态变化即触发"的模块，在状态流转成功后调 `workflow.invoke({ businessKey, sourceRef, dedupeKey })`；
3. **需要"流程驱动单据"**：单据表增 `workflowRunId`（可空），由工作流动作节点回写；
4. **需要"人工卡点"**：一律用 `human.assign_task / human.form`，不新增第二套待办。

## 五、服务商 → 业务执行人派单（B2）

### 5.1 现状与差距

- `ProviderAssignment(providerUserId, enterpriseId, staffUserId)` = **企业级默认承办人**；建单时 `assignedStaffFor()` 取默认值。
- `ProviderStaff` = 服务商与职员的绑定（`status ACTIVE`），服务商可邀请、职员确认。
- `shared/visibility.ts`：服务商账号可见 `staffUserId = 本人` 或**未指派**的单据；指派给他人后服务商账号即不可见。
- **差距**：没有"派给服务商 → 服务商决定给谁"的任务级流转；没有按业务线/地域/负载的自动分配；任务中心看不到机构队列。

### 5.2 目标语义

```
业务事件/工作流
      │
      ▼
TaskRouter.resolve()
      │  DIRECT       → assigneeUserId = 指定账号
      │  ORG_QUEUE    → assigneeType = ORG，机构待接（assigneeUserId 为空）
      │  BY_RULE      → assignments 规则表命中（板块 + 类目 + 地域 + 优先级）
      │  ROUND_ROBIN  → 该服务商在职职员里轮转（按 roles 过滤）
      │  LOAD         → 未办任务最少的在职职员
      ▼
MyTask（orgType=PROVIDER, orgUserId=服务商账号）
      │
      ├─ 机构负责人在「我的任务 · 机构待派」改派给某个职员（DIRECT）
      └─ 到期未派 → 自动按 ROUND_ROBIN/LOAD 落实，并通知负责人
```

### 5.5 与既有可见性的冲突（必须决策）

任务派给服务商 ≠ 业务单据对服务商可见。`visibility.ts` 目前要求 `staffUserId` 命中。两种做法：

- **方案 A（推荐）**：派单与业务单据**同事务**写 `staffUserId`；任务与单据永远一致，服务商负责人转派时同步改单据。需要各板块暴露一个内部"改承办人"方法（供销已有 `assignOrder` 可参照）。
- **方案 B**：任务只在任务中心流转，单据仍由企业/平台指派；服务商能看到任务却点进去 403，**不可接受**。

⇒ **D3 请确认走 A**。走 A 时，转派动作要串行：`MyTask` 更新 → 业务单据 `staffUserId` 更新 → `TaskAssignmentLog` 落库，任一步失败整体回滚。

### 5.6 实施落地（B2，已交付）

**代码位置**：`backend/src/task-center/` 下 `task-router.service.ts`（派单原语）、`task-document.binding.ts`（任务↔单据绑定）、`task-assignment.service.ts`（规则维护）、`task-assignment.scheduler.ts`（D4 超时落实）。迁移 `0060_task_assignment` 已应用。

**实际语义**：

- `resolve()` 只看 `orgType=PROVIDER` 的启用规则，按 `priority desc, id asc` 取第一条命中的（`source/category` 支持 `*`，`region` 留空为不限）；命中但目标池里没有在职职员时回落 `ORG_QUEUE`，不会派给离职账号。
- 规则优先于板块默认承办人（`ProviderAssignment`）；都没有就进机构队列。板块只需把建单输入交给 `TaskRouter.dispatch()`，不直接写 `my_tasks`。
- 改派/接单/板块指派三处统一走 `commitAssign`/`assignDocument`：`MyTask` → 单据 `staffUserId` → 留痕，同一 `$transaction`，单据不存在即抛错整体回滚（D3=A）。首批登记的单据绑定为供销订货单（`supply` / `so-*`）与服务预约（`supply-booking` / `sb-*`）。
- 机构队列的幂等锚是 `source:sourceId:org:<orgUserId>`：改派后源的下次刷新只更新业务字段，不会把承办人弹回。
- D4 落实：`TaskAssignmentScheduler` 默认每 10 分钟扫一次（`TASK_ASSIGN_SWEEP_MS` 可调、`TASK_ASSIGN_SCHEDULER_DISABLED=1` 关闭），只处理 `assigneeType=ORG` 且 `assignedAt` 超过 24 小时的任务；能解析出职员才自动改派，解析不出就提醒机构负责人并把计时推到当轮，避免重复轰炸。
- 规则写入只有服务商负责人本人（且须 `SERVICE_PROVIDER` 已审核）；平台管理员只有 `audit` 只读分页，没有任何平台侧写入路径（D5=A）。`DIRECT` 规则必须且只能有 1 个目标职员，目标必须是本机构 `ACTIVE` 职员。

### 8.4 共享按具体主体拆分（已落地）

**问题**：清单原来只有「公司共享 / 服务商共享」两个笼统分组，把本人所属的多个公司、多个服务商的工作流混在同一张表里。每条工作流能支持的数据域跟着主体走，混在一起就等于让用户在 A 公司的流程里挑 B 公司的流程。

**口径**：一个主体一个数据域，一个数据域一个页签，用户点页签即完成选择。

| 层 | 落地 |
|---|---|
| 契约 | `workflowOrgSchema = { orgType, orgUserId, name, current }`；`Workflow_list.query` 增 `orgUserId`，响应增 `orgs: WorkflowOrg[]` 与 `counts: Record<string, number>`；`Workflow_create / Workflow_save` 请求体增 `orgUserId` |
| 后端 | `orgKeys()` 复用 `OrgContextService.contexts()` 顺带产出 `options`（主体名 + 当前标记），不额外查库；`shareOrgId(group, requested, orgs)` **恒只返回一个主体**：请求指定且确属本人 → 当前主体（同类型）→ 该类型第一个 → `''`（落 `__none__` 哨兵查空，绝不退化成「全部」）；`counts` 键为 `mine` / `org:<主体>` / `provider:<主体>`，与前端页签一一对应，一次 `Promise.all` 取齐 |
| 写入 | `orgForScope(scope, orgs, requested)`：共享到非本人所属主体 → 403「你不属于该公司主体 / 该服务商机构，不能共享到它」；该类型一个主体都没有 → 403「你不属于任何…，不能设为…共享」。`save` 只传 `orgUserId` 也生效（可见性沿用原值），不做静默空操作 |
| 前端 | `PillTabs`：`我的` + `${主体名} · 公司共享/服务商共享`，长名 `maxWidth 240` 单行截断 + `title` 悬停看全名；统计卡按主体求和，单主体时 hint 直接写主体名；表格「可见性」列在徽标下补一行主体名；新建弹窗「可见性」下拉列出具体主体，从哪个主体页签进来就默认共享到哪个主体 |
| 切页签不弹回 | `useBusinessQuery` 无 `placeholderData`，换 queryKey 后 `data` 短暂为 `undefined`；页签失效判定与归位 effect 都以 `orgsReady = data !== undefined` 为前提，只有主体关系真的变了（离职 / 切身份）才回到「我的」 |

**不做**：不给 `WorkflowRow` 加 `orgName` 列（前端从同一份 `orgs` 解析）；不改 `toolSpecs()` 的跨主体目录口径（Agent/MCP 的 `wf__` 目录本就按「本人全部所属主体」取已发布已共享流程，与清单分组是两件事）。

**用例**：`backend/src/workflow/workflow.service.spec.ts` 覆盖单主体过滤、非本人主体回落、哨兵查空、按主体计数、写入 403、只传 `orgUserId` 改主体，以及 B1 的 invoke 幂等与三类进程内触发。

### 8.5 内置配方模板与 `{{actor.*}}`（B7 已落地）

**模板承载方式**：5 个配方是前端常量（`frontend/src/app/workflow/workflow-templates.ts`），新建时随 `Workflow_create.graph` 一并落草稿，**不新增接口 / 契约 / 表**；用户进画布后照常改参数、保存、发布。

**为什么新增 `{{actor.*}}`**：模板要「复制即跑」，但「分配任务」节点必须有收件人。原来缓存里只有 `input / vars / nodes` 三个命名空间，模板只能写死 userId（换个人就失效）或要求先填入参（留空就报错）。现在 `RunContext` 增加**发起人**命名空间，模板收件人写 `{{actor.userId}}`，谁运行就派给谁：

| 层 | 变更 |
|---|---|
| `workflow.types.ts` | `RunContext` 增 `actor: { userId, username }` |
| `workflow-engine.ts` | `start()` 构造上下文时写入 `actor`；逐波推进时 `snapshot` 一并带上（并行分支看到同一发起人） |
| `workflow-graph.ts` | `RunContextLike.actor` 可选（图编译器与既有单测的上下文字面量不必补字段）；`readPath` 增 `actor` 分支，`{{actor.userId}}` / `{{actor.username}}` 可解析 |
| 模板约定 | 触发节点只能有一个（`trigger.event` 的事件名必须是真实领域事件）；条件分支的 `value` 是字面量；出边用 `sourceHandle` 标 `true` / `false` |

**兜底口径**：入参留空也不报错——标题都带固定前缀（如「跟进获客线索 #」），条件取值缺失时 `toNumber(undefined)=0` 走 false 分支，节点按 DAG 正常推进；「表单填写」模板按设计停在 `WAITING` 等本人提交。

**用例**：`backend/test/workflow-templates.spec.ts` 直接 import 前端模板，用后端 `compileGraph` + `validateTriggers` 逐个校验（无环、恰一个触发、cron / 事件名合法），并断言示例入参覆盖模板里所有 `{{input.*}}` 引用。

## 十、验收（可复现，不靠"看起来对"）

1. **触发**：建一个「定时每分钟 → 分配任务给我」的工作流，观察 3 个运行记录，间隔 ≤ 70s；同一领域事件（同一 `eventLogId`）重复投递 3 次只产生 1 个运行；同一分钟重复 tick 不产生第二个运行。
2. **派单**：以服务商账号接一条 `ORG_QUEUE` 任务 → `/tasks` 机构待派可见；改派给职员 A → 服务商账号不可见、A 可见；单据 `staffUserId` 同步为 A。
3. **规则**：配置「`crm.lead.created` → run_workflow」→ 新建线索后产生运行；`ruleExecution` 状态 `DONE`（失败为 `FAILED` 并带错误文案）。
4. **表单**：表单节点填 2 个必填字段，只填 1 个时任务侧不能提交；提交后工作流继续且 `nodes.<id>.form` 有值。
5. **并行**：两个各耗时 5s 的分支并行，总耗时 < 8s；汇合节点拿到两份结果。
6. **插件**：关掉工具页 2 分钟后重新打开，分发回执能补传且不重复入库。
7. **一致性**：驾驶舱「我的任务」= `/tasks` 未办数 = 菜单角标；`bySource` 各源计数之和 = 未办数。

## 十一、风险与边界

| 风险 | 说明 | 缓解 |
|---|---|---|
| 工作流变成"影子权限" | 动作节点以发起人身份跑真实接口，可能绕过页面级限制 | 继续走 `runOperation` 同一路由与校验；`forbiddenReasonOf` 红线保持；写动作节点默认不自动重试 |
| 组织收件箱与单据可见性错位 | 任务可见但单据 403 | 强制 D3 方案 A：任务与单据同事务写 `staffUserId` |
| 触发入口被滥用 | 无登录入口可触发写动作 | **D2=C：不开放任何外部触发入口**；`invoke` 只在登录态路由与进程内桥调用，发起人＝工作流创建人（账号被禁用即不触发） |
| 并行带来重复写 | 两个分支同时改同一单据 | 节点级并发上限；写动作互斥键（`sourceRef` + operationId） |
| 插件风控 | 高频操作触发平台验证码 | 维持串行 + 随机间隔 + `CAPTCHA/NEED_LOGIN` 即停；不新增绕过能力 |
| 口径反复 | 驾驶舱、任务中心、各板块各算一套 | 驾驶舱已统一到 `bySource`；「我的待办」板块卡中财税 / 物流 / 营销三张已改读 `bySource`（见下） |

**本轮口径说明（已落地）**：驾驶舱「待我处理」**只读任务中心 `bySource`**，并移除了驾驶舱自己再拉 CRM/OKR 的重复请求。板块卡口径分两类：

- **已收敛（B7）**：财税申报、物流、营销三张卡在 `frontend/src/lib/dashboard-scope.ts` 的 `CONVERGED_STATISTICS` 中被移出「板块统计」请求，改为读 `taskSummaryQuery.bySource`（`taskSourceCount`），与 `/tasks`、菜单角标同一份数字。这三个源（`tax` / `logistics` / `marketing` 适配器）都复用各板块自己的 `listScope`，摘要里的 `bySource` 就是板块可见范围内的未办件数。
- **未收敛**：其余板块（供销、数字资产、法务、知识产权、灵活用工、入职、智能硬件等）尚无 TaskSource，仍按板块统计计算，**本轮保留原实现**，避免把已有能力改丢；接入 TaskSource 后逐卡替换即可，收敛点集中在 `dashboard-scope.ts` 一处。
