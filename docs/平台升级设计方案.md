# 平台升级与一键还原设计方案

> 状态：已实施（2026-11-10）。入口：平台管理后台 → 系统与内容 → **平台升级**（`/admin/upgrade`）。

## 一、背景与目标

开源版部署在客户自己的服务器上，升级长期依赖人工：拉包、停服、覆盖代码、装依赖、跑迁移、重启，任何一步出错都可能把库和代码留在中间状态。本功能把这条链路收进平台后台，由平台自己的 Agent 先分析差异再执行，并在执行前强制备份、执行中自动维护模式、失败自动回滚、事后可一键还原。

目标：

1. 一个页面完成「取包 → 分析 → 确认 → 执行 → 还原」全流程。
2. 执行前**强制备份数据库**，代码备份默认勾选；备份保留时间不限制。
3. 升级期间自动进入维护模式，写请求返回 503，避免半升级状态写入脏数据。
4. 执行失败可按建议自动回滚；任何时候都能从备份台账一键还原（整库 + 代码，或仅数据库）。
5. 全程可审计：包、任务、步骤、日志、备份与操作人全部落库。

## 二、已确认口径

1. **重复确认、一键执行**：执行前必须手动输入目标版本号；还原必须输入 `RESTORE` / `RESTORE-DB`。
2. **拉取与上传都支持**：优先 GitHub Release 资产，也可下载指定 tag 的源码包；同时支持管理员手动上传 zip 到 `update/`。
3. **固定本仓库、不需要 Token**：`liujh0729-jpg/AI-enterprise-OEM` 为公开仓库；仅当 GitHub 限流时才建议配置可选的 `UPGRADE_GITHUB_TOKEN`。
4. **Agent 分析用平台自己的渠道**：读取「平台管理后台 → 系统设置 → 模型设置」的文本模型槽位，不在升级模块另配 Key；模型不可用或返回不合法 JSON 时退回规则分析，不阻断流程。
5. **备份位置固定、保留不限期**：全部落在 `update/backups/`，后台可查大小、SHA-256 与校验状态，可手动删除（正在被任务引用的除外）。
6. **接受短暂停服**：升级与还原都会重启 API / Web；升级开始前自动打开维护模式，任务结束（成功、失败或回滚）后自动关闭。
7. **分析完成后由管理员决定**：Agent 只给风险、阻断项、冲突文件、迁移与依赖变更、执行策略与前后置检查，不自动执行。
8. **强制备份**：`backupDatabase` 在契约层与执行层双重校验，必须为 `true`。

## 三、总体流程

```
① 取包            ② 分析                     ③ 确认执行                  ④ 执行 / 还原
GitHub Release ─┐   Agent 读取平台文本模型      勾选备份（数据库强制）      独立 runner（脱离 API 进程）
指定 tag 源码包 ─┼─→ 对比版本/迁移/依赖/环境变量 → 输入目标版本号确认 ─────→ 维护模式 → 备份 → 覆盖代码
手动上传 zip   ─┘   输出建议（或规则兜底）      冲突覆盖/中止、自动回滚      → 装依赖 → 构建 → 迁移 → 重启
                                                                          → 健康检查 → 关维护模式
```

### 1. 取包

- `AdminUpgrade_check` 读取 GitHub 最新 Release，返回版本、资产名、大小、下载地址与 release notes。
- `AdminUpgrade_download` 支持 `release`（优先 `.zip` 资产）与 `source`（tag 源码 zip）。
- `POST /enterprise/admin/upgrade/upload` 接收 multipart（字段 `file` / `version`），单包上限 512MB，body 上限单独放宽到 512MB。
- 包统一落到 `update/packages/`，解压到 `update/sources/<id>/`。解压前后做安全检查：
  - 条目数 ≤ 200k，单包 ≤ 512MB，解压后 ≤ 2GB；
  - 拒绝绝对路径、盘符路径、`..` 穿越、超长路径与符号链接；
  - 校验根目录必须包含 `package.json`、`pnpm-workspace.yaml`、`backend/package.json`、`frontend/package.json`、`packages/contracts/package.json`、`backend/prisma/schema.prisma`。
- 校验通过记为 `EXTRACTED` 并记录候选目录、版本、SHA-256；不合规记为 `INVALID` 并写明原因。

### 2. Agent 分析

- 以任务形式后台执行，单任务步骤：`collect` → `agent` → `save`。
- 采集事实：当前版本 / commit、包版本、文件差异概览、是否包含新迁移、依赖清单变化、`.env.example` 新增键、工作区未提交改动（可能被覆盖）、磁盘空间与必需工具。
- 建议结构：`risk`（LOW/MEDIUM/HIGH）、`summary`、`blockers`、`warnings`、`conflicts`、`migrations`、`dependencies`、`envChanges`、`strategy`、`prechecks`、`postchecks`、`rollback`、`source`（`agent` / `rules`）。
- 模型调用复用内容模块的模型解析与统一传输层（OpenAI `/chat/completions`、Anthropic `/messages`），提示词要求只输出 JSON；解析失败或渠道不可用时使用规则建议。

### 3. 确认执行

- 必须选择已解压的升级包，执行选项：数据库备份（固定勾选且不可取消）、代码备份（默认开）、自动回滚（默认开）、冲突策略（覆盖 / 中止）。
- Docker 部署不在容器内自我重启：页面直接给出宿主机命令（`docker compose down && docker compose up -d --build`），由管理员在宿主机执行。
- 前置校验：无进行中的任务、包可用、目标版本高于当前版本、备份工具可用、磁盘余量足够、确认文本等于目标版本。

### 4. 执行器（脱离 API 进程）

API 无法重启自己，因此执行交给独立 Node 进程 `scripts/upgrade-runner.mjs`：

- API 写 `update/jobs/<id>/job.json`（600 权限）、初始化 `state.json` 与 `job.log`，以 detached 方式拉起 runner 后立即返回。
- runner 每完成一步回写 `state.json`（当前步骤、进度、错误、各步骤状态），API 在查询任务时同步进数据库；进程被杀也能从文件恢复最后状态。
- 步骤：预检 → 停服 → 备份数据库 → 备份代码 → 覆盖代码 → 安装依赖 → 构建 → 执行迁移 → 重启 → 健康检查。
- 覆盖代码为**增量覆盖**：排除 `.env*`、`node_modules`、`.git`、`update`、`.next`、`dist`、日志；不会主动删除新版本已移除的旧文件（方案限制，见 §七）。
- 健康检查按 `UPGRADE_HEALTH_URL` 轮询（默认 `http://127.0.0.1:1690/health/ready`），超时判定失败；开启自动回滚时按备份恢复数据库与代码并重启。
- 支持取消：写 `cancel` 文件，runner 在步骤边界中止并标记 `CANCELLED`。

### 5. 维护模式

- 系统设置键 `platform_maintenance` 存 `{ on, reason, jobId, startedAt }`。
- 升级/还原启动前由 API 写入；任务进入终态时由同步逻辑清除。
- 中间件对非 `GET/HEAD/OPTIONS` 请求返回 503；白名单：升级接口本身、会话 / 身份 / 账号接口与健康检查，保证管理员仍能登录、查看进度与取消任务。

### 6. 页面引导

- 每一步都给出下一步说明：未选包时提示「先下载或上传并在表格中选用」；已选包时说明下一步会对比代码并给出建议；分析被阻断时说明原因并提供「返回第一步：更换升级包」。
- 执行确认与备份台账页在缺少 `mysqldump` / `pg_dump` / `tar` 时直接禁用执行按钮，并展示安装指引：
  - 按后端归档工具路径判断服务器系统（Windows / Linux），给出对应的安装方式；
  - MySQL：Linux 使用 `mysql-client`，Windows 使用 MySQL Installer 勾选 Client 组件；
  - PostgreSQL：Linux 使用 `postgresql-client`，Windows 使用官方安装包并加入 PATH；
  - `tar`：Linux 使用系统包管理器，Windows 使用系统自带 `System32\tar.exe` 或可选功能安装；
  - 命令可一键复制；安装后重启后端，重新进入本页会自动重新检测，下载与分析不受影响。
- 后端预检与 runner 的错误信息会列出实际缺失的工具，并指向本页安装指引。
- 任务成功后提示按「升级后确认」检查并提供备份清理入口；自动回滚后提示排查日志并提供手动还原入口。

## 四、数据模型

| 表 | 用途 |
|---|---|
| `platform_upgrade_packages` | 升级包台账：来源、状态、版本、tag、文件路径、SHA-256、解压目录、校验原因 |
| `platform_upgrade_jobs` | 任务：ANALYSIS / UPGRADE / RESTORE，状态、前后版本、当前步骤、进度、选项、建议快照、操作人、任务目录 |
| `platform_upgrade_steps` | 任务步骤：步骤键、名称、状态、消息、起止时间 |
| `platform_backups` | 备份：DATABASE / CODE、版本、方言、归档路径、manifest 路径、大小、SHA-256、校验与锁定标记 |

迁移：`backend/prisma/migrations/0057_platform_upgrade/`（MySQL 源）；PostgreSQL schema 由 `scripts/gen-prisma-schema.mjs` 派生，统一 `migrate deploy`。

## 六、安全与可靠性

- **权限**：所有操作 `requireAdmin`，仅平台管理员可调用；前端深链同样按身份收口。
- **命令执行**：数据库导出 / 恢复、`tar`、解压、依赖安装、构建与重启全部使用参数数组调用，不拼 shell 字符串；确认文本在服务端校验。
- **网络边界**：GitHub 与下载统一走 `httpRequest` / `streamRequest`，继承超时、并发限流、请求 ID 与隔离测试禁网。
- **Zip 安全**：路径穿越、绝对路径、符号链接、压缩炸弹（条目数 / 解压体积）全部拒绝。
- **备份完整性**：manifest 记录绝对路径、字节数与 SHA-256，文件权限 600；还原前重新校验，校验失败拒绝执行。
- **强制备份**：契约 `refine` + 服务层检查双保险；代码备份默认开启。
- **单任务**：同一时间只允许一个 ANALYSIS / UPGRADE / RESTORE 任务，避免并发覆盖。
- **维护模式**：任何执行前先落维护标记，终态同步时清除；API 重启后从 `state.json` 恢复任务状态。
- **还原口径**：FULL 需要同一任务产生的数据库与代码两份备份；DATABASE 只回滚数据。两者都会先进入维护模式并再次强制备份当前状态。

## 七、已知限制

1. 代码覆盖不删除新版本已移除的文件；跨大版本若存在删除型变更，建议先看 Agent 提示的冲突文件并选择「中止」策略人工处理。
2. Docker 部署需在宿主机执行重启命令，容器内不自动重启。
3. 备份保留不限期，需要管理员在台账中手动清理；磁盘余量不足会阻断升级。
4. Agent 建议依赖平台已配置的文本模型；未配置时降级为规则分析，结论粒度较粗。

| 变量 | 默认 | 说明 |
|---|---|---|
| `UPGRADE_INSTALL_DIR` | 仓库根目录 | 部署目录（`update/` 默认建在其下） |

| `UPGRADE_GITHUB_TOKEN` | 空 | 可选，仅 GitHub 限流时使用 |
| `UPGRADE_GITHUB_REPO` | `liujh0729-jpg/AI-enterprise-OEM` | 固定仓库，一般不改 |
