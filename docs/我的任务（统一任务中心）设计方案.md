## 二、核心抽象：任务源适配器（TaskSource）

整个设计的抽象点只有一个——**任何板块只要实现一个 `TaskSource`，它的待办就会自动出现在「我的任务」里**。

```ts
/** backend/src/task-center/task-source.ts */
export interface TaskDraft {
  assigneeUserId: string;      // 被 @ 到该账号
  source: string;              // 源 key：oa | okr | pj | crm | desk | contract | admin ...
  sourceId: string;            // 业务对象主键（去重锚点）
  title: string;               // 任务介绍（标题）
  description?: string;        // 任务介绍（正文/摘要）
  link: string;                // 点击去处理的 URL
  category: string;            // 分组：approval | report | task | matter | audit
  priority?: 'LOW'|'NORMAL'|'HIGH'|'URGENT';
  dueAt?: string | Date;
  createdBy?: string;
  sourceStatus?: string;        // 业务方状态
  sourceStatusLabel?: string;
  terminal?: boolean;           // 业务是否已终态（终态即视为完成）
}

export interface TaskSource {
  key: string;                 // oa / okr / pj / ...
  label: string;               // 中文名，如「OA 审批」
  category: string;            // 默认分组
  /** 拉取：该账号在此源下所有"待处理"任务（对存量模块零侵入接入） */
  collect(user: CurrentUser): Promise<TaskDraft[]>;
  /** 单条刷新：打开任务/定时刷新时向源要最新业务状态；返回 null 表示已不存在 */
  resolve?(draft: TaskDraft): Promise<Partial<TaskDraft> | null>;
  /** 本人关闭后回调源模块（可选：让业务方感知"用户已阅/已收起"） */
  onClosed?(draft: TaskDraft, note: string): Promise<void>;
}
```

- 源适配器注册进 `TaskSourceRegistry`（DI 单例，和 §5.8 机制同风格）。
- **两条写入通道**同时支持，这是"足够抽象、支持所有板块发起"的关键：

| 通道 | 谁用 | 机制 | 特点 |
| --- | --- | --- | --- |
| **Push（事件驱动）** | 新模块 / 明确知道"派给谁"的场景（如"任务分配给我"、"要我签署"） | 业务方调 `TaskCenterService.assign(draft)`，或发 `TASK_ASSIGNED` 事件被中心 listener 落库 | 精确、可回写、跨角色无差别 |
| **Pull（适配器聚合）** | 存量模块（已有自己的"待办"口径） | 中心遍历 `registry.collect(user)`，按 `dedupKey` upsert / 动态合并 | 零侵入、一次接入历史模块 |

## 三、数据模型：`my_tasks`（统一任务表）

```prisma
/// 统一任务中心：任意板块 @ 到某账号的一件待办。写入口收口在 TaskCenterService。
model MyTask {
  id                Int       @id @default(autoincrement())
  assigneeUserId    String    @map("assignee_user_id") @db.VarChar(64)   // 账号级，跨角色
  source            String    @db.VarChar(32)                            // oa|okr|pj|crm|desk|...
  sourceId          String    @default("") @map("source_id") @db.VarChar(64)
  /// 去重锚：source + source_id + assignee，防重复派发
  dedupKey          String    @unique @map("dedup_key") @db.VarChar(191)
  category          String    @default("matter") @db.VarChar(16)         // approval|report|task|matter|audit
  title             String    @db.VarChar(200)
  description       String    @default("") @db.Text
  link              String    @default("") @db.VarChar(500)              // 去处理的 URL
  priority          String    @default("NORMAL") @db.VarChar(16)
  /// 中心状态机：OPEN → DOING → DONE / CANCELED / EXPIRED
  status            String    @default("OPEN") @db.VarChar(16)
  /// 业务方权威状态（只展示、由源回写）：如 APPROVING / PENDING / SUBMITTED
  sourceStatus      String    @default("") @map("source_status") @db.VarChar(32)
  sourceStatusLabel String    @default("") @map("source_status_label") @db.VarChar(40)
  /// 上下文主体（可选）：该任务归属的组织/企业；空表示纯账号级任务
  orgType           String    @default("") @map("org_type") @db.VarChar(16)
  orgUserId         String    @default("") @map("org_user_id") @db.VarChar(64)
  createdBy         String    @default("") @map("created_by") @db.VarChar(64)
  dueAt             DateTime? @map("due_at")
  closedAt          DateTime? @map("closed_at")
  closedBy          String    @default("") @map("closed_by") @db.VarChar(64)
  closeNote         String    @default("") @map("close_note") @db.VarChar(500)
  lastSyncedAt      DateTime? @map("last_synced_at")
  createdAt         DateTime  @default(now()) @map("created_at")
  updatedAt         DateTime  @updatedAt @map("updated_at")

  @@index([assigneeUserId, status, createdAt])
  @@index([assigneeUserId, category, status])
  @@index([assigneeUserId, source, status])
  @@map("my_tasks")
}
```

> 另有可选 `TaskSourceState`（记录每个源的 `lastPullAt`/`cursor`）用于增量拉取，非首批必需。

**幂等**：`dedupKey = ${source}:${sourceId}:${assigneeUserId}`（无 sourceId 的纯手工任务用随机段）。同一件业务再派发只更新描述/链接，不产生重复行。

## 四、状态模型：两个维度，不要混为一谈

用户要"有任务状态"+"业务方也能回写状态"+"自己能关闭"——这是**两个正交维度**：

| 维度 | 归属 | 取值 | 谁能改 |
| --- | --- | --- | --- |
| **中心状态 `status`** | 任务中心 | `OPEN` → `DOING` → `DONE` / `CANCELED` / `EXPIRED` | 用户（关闭/完成）、系统（源终态自动 EXPIRED/DONE） |
| **业务状态 `sourceStatus`** | 源模块（权威） | 各模块自己的枚举（如 `APPROVING`/`PENDING`） | 只有源模块，经 `TaskCenterService.syncStatus()` 或事件回写 |

规则：

1. **本人关闭**：`OPEN/DOING → DONE`，写 `closedAt/closedBy/closeNote`；随后回调源模块的 `onClosed`，并发通知给发起人/相关方（复用 `NotificationService`）。
2. **只关"我这边的待办"**：中心关闭表达的是"这条我不再挂在待办里"，**不代表业务终态**（审批的终态仍以源模块为准）。所以关闭是**幂等且可被源终态覆盖**，`sourceStatus` 照常展示。
3. **源终态 → 中心自动完成**：`collect/resolve` 返回 `terminal=true`，或源发 `TASK_DONE` 事件 → 中心置 `DONE`（保留 N 天后归档）。
4. **已办保留**：默认保留 180 天（对齐 `NotificationService.prune` 口径），可配置。

**⑤ 持久化（账号级，跨设备）**

## 十一、工作流（Workflow）：可视化编排 + 可被 Agent 调用

> 参考：[langflow-ai/langflow](https://github.com/langflow-ai/langflow)。按其核心抽象（**Flow 流程图 / Component 节点 / Edge 连线 / Playground 步进试跑 / 可发布为 API 或 MCP server**）落地，节点复用本系统现有的统一能力注册表，不另造一套清单与权限。

### 11.1 定位与边界（避免与既有自动化重复）

| 现有 | 做什么 | 与工作流的关系 |
| --- | --- | --- |
| **RPA 自动化**（[rpa/](file:///E:/wwwroot/oem-enterprise/backend/src/rpa)） | 浏览器/设备端在**外部网站**上的自动操作 | 工作流把 RPA 作为**一种节点**（"跑 RPA 任务"），不重写 |
| **规则引擎**（[mechanism-rule.service.ts](file:///E:/wwwroot/oem-enterprise/backend/src/mechanisms/mechanism-rule.service.ts)） | **单事件 → 条件 → 若干动作**，轻量声明式 | 复杂多步/分支/人工/审批场景交给工作流；规则可"触发一条工作流" |
| **站内 Agent**（[agent-engine.ts:560](file:///E:/wwwroot/oem-enterprise/backend/src/content/agent-engine.ts#L560)） | LLM 自主选工具完成任务 | **双向**：工作流可被 Agent 当工具调用；工作流内可用「Agent 节点」 |
| **工作流** | **可视化多步图编排**：分支/并行/等待/人工任务/审批/AI，可被 Agent 与外部调用 | 统一编排层 |

### 11.2 核心抽象（对齐 Langflow）

| Langflow 概念 | 本系统实现 |
| --- | --- |
| **Flow** | `Workflow`：一张有向图（节点 + 连线）+ 输入/输出契约；有版本 |
| **Component / Node** | `WorkflowNode`：带类型的节点，声明 `inputs/outputs` |
| **Edge** | 连线：上游节点输出 → 下游节点输入（参数映射） |
| **Playground** | 编辑器内步进试跑：逐步高亮、看每步输入/输出/耗时/错误 |
| **Component Registry** | **从系统能力注册表派生**（见 11.3），不写第二份 |
| **Deploy as API / MCP** | 发布后：`POST /workflows/:id/run` + 自动进入 MCP 工具列表 |
| **Flow JSON 导出** | `graph` 以 JSON 存储，可导出/导入、可版本快照 |

### 11.3 节点体系：「系统功能皆节点」怎么落地

**唯一口径**：节点目录从既有注册表派生，**不新建清单**——
- **系统动作节点** ← `endpoints`（[packages/contracts](file:///E:/wwwroot/oem-enterprise/packages/contracts/src) 的契约注册表，MCP 清单正是"从它派生、不写第二份"，见 [mcp-catalog.ts:9](file:///E:/wwwroot/oem-enterprise/backend/src/mcp/mcp-catalog.ts#L9)）。参数表单由对应 Zod schema 自动生成。
- **工具型节点** ← `AGENT_TOOL_MANIFEST`（[agent-tool-manifest.ts](file:///E:/wwwroot/oem-enterprise/backend/src/content/agent-tool-manifest.ts)）的六类：内置 / 业务 / 连接器 / 硬件 / 技能 / 插件。

六类节点：

| 类别 | 节点 | 说明 |
| --- | --- | --- |
| **触发** | 手动 / 定时 / 领域事件 / Webhook / **我的任务状态变化** | 事件触发作为 §5.8 `MechanismEventService.on(event,…)` 的 listener；定时复用现有 scheduler 模式 |
| **系统动作** | 任意 `operationId`（含**任务分配** `MyTask.assign`、发审批、发通知、建线索、表格写行、签约…） | 运行期以**运行人身份**进真实业务服务，组织隔离/校验/审计沿用模块自身 |
| **AI / Agent** | LLM 调用 / 知识库检索（KbRetrieve）/ **Agent 节点**（跑另一个工作流或站内 Agent） | 复用统一 AI 网关与 `kb_retrieve` |
| **逻辑** | 条件分支 / 循环 / 并行 / 等待 / 合并 / 变量 | 图遍历编译期做环检测 |
| **人工** | OA 审批 / **人工任务（写入「我的任务」并等待）** / 表单填写 | 见 11.4 |
| **集成** | MCP 连接器工具 / Webhook / 硬件工具 | 复用连接器与硬件 MCP |

> 新增任何模块只要进了 `endpoints` 契约，就**自动**成为可选节点——工作流代码不用改。这是"系统中的这些功能都可以成为工作流节点"的实现方式。

### 11.4 与「我的任务」联动（任务分配成为节点）

- **「分配任务」系统动作节点**：运行时写 `my_tasks`（`source = workflow`，`sourceId = runId:nodeId`，`link` 指回工作流/业务页）。任务的标题、介绍、链接由节点配置与前序节点输出渲染。
- **「等待任务完成」人工节点**：工作流在此暂停，直到该 `MyTask` 被本人关闭或业务终态；`MyTask` 的关闭回调（本方案 4 节的 `onClosed`）回流事件唤醒工作流继续。
- **触发节点**可监听「我的任务被创建 / 被关闭 / 逾期」，实现"任务驱动"的自动化。
- 这样工作流与「我的任务」共用同一份任务实体，不产生两套待办。

### 11.5 可见性与共享（私有 / 公司 / 服务商）

| `scope` | 谁能看/运行 | 谁能编辑 |
| --- | --- | --- |
| `PRIVATE` | 仅创建人 | 创建人 |
| `ORG` | 当前主体内部（按 `orgType + orgUserId`） | 创建人（可加协作者） |
| `PROVIDER` | 服务商机构内部（按服务商组织关系） | 创建人（可加协作者） |

- **任何登录账号都可创建工作流**（默认私有）；开放到公司/服务商需具备相应组织关系（复用既有 org 隔离口径）。
- 共享 = **只读可用**（可运行、可被引用/复制），编辑权归创建人；发布为 Agent/MCP 工具要求 `scope ≥ ORG` 且已发布。
- 复制共享工作流 = 另存为自己名下的私有副本。

### 11.7 执行引擎

- **图遍历**：DAG 编译与校验（环、悬空连线、必填输入）在保存/发布时拦截；支持条件分支、并行、等待、合并。
- **身份与审计**：每步以**运行发起人**身份调真实模块服务（复用 `runBusinessTool` 同口径），组织隔离/必填/审计由模块自身保证——工作流不另写权限。
- **幂等**：`runId + nodeId` 为副作用步骤的幂等锚；外部写操作带幂等键。
- **失败策略**：每节点可配「重试 N 次 / 跳过 / 终止」；已成功步骤保留中间态，可从失败步重跑。
- **暂停/恢复**：人工任务与审批节点置 `WAITING`，由 `MyTask` 关闭 / OA 审批完成事件唤醒。
- **流式**：步骤事件（SSE）推给 Playground 实时展示。
- **触发**：手动（编辑器/列表）、定时（scheduler）、领域事件（§5.8 event bus）、Webhook、Agent/MCP 调用。

### 11.10 边界、风险与验收

- **不重复造轮子**：节点目录派生自 `endpoints` + `AGENT_TOOL_MANIFEST`；执行复用模块服务与审计，权限不二次实现。
- **安全**：`scope` 越权校验；写操作红线沿用 `MCP_FORBIDDEN_ACTIONS`；Agent 调用走同一写门禁。
- **性能**：长流程异步执行 + 步骤日志分页；并行节点受并发上限约束。
- **可观测**：`WorkflowRun/Step` 是唯一运行台账，支持失败定位与重跑。
- **验收**：环检测、分支/并行、等待唤醒（任务关闭→继续）、越权分享被拒、幂等重放、流式步骤、Agent/MCP 调用连通；typecheck/lint/单测全绿；文档与 8 语言文案。

## 十二、第三方工作流引擎（Langflow）兼容性评估

> 结论先行：**Langflow 引擎不能直接复用（不可移植），只能做「概念移植」**。工作流的实现仍按第十一节在 TypeScript 侧自建。
> 证据来源：用户提供的 `langflow-main.zip`（v1.13.1，14,235 文件），抽取核对 `pyproject.toml` / `src/backend/base/pyproject.toml` / `src/backend/base/langflow/graph/__init__.py` / `services/database/models/flow/model.py` / `src/frontend/package.json`。

### 12.1 引擎实际构成（读到的客观事实）

| 维度 | Langflow 1.13.1 | 本项目 |
| --- | --- | --- |
| 语言/运行时 | **Python `>=3.10,<3.15`**；`langflow-base==1.13.1`（FastAPI + uvicorn/gunicorn） | **纯 TypeScript**：Node 24 + Hono 4（后端）、Next 16 App Router（前端） |
| 图引擎所在 | **仓库外**——`langflow/graph/__init__.py` 全部 re-export 自外部包 `lfx`（`lfx.graph` 的 `Graph/Edge/Vertex/CustomComponentVertex/InterfaceVertex/StateVertex`），base 依赖首项即 `lfx[sqlite]==1.13.1` | 无独立引擎包；节点＝`@enterprise/contracts` 的 `endpoints` operationId（HTTP + zod schema） |
| 节点语义 | **进程内 Python 类**，执行时直接 import 并调 LangChain / 各 provider SDK | 契约注册表里的操作；Agent 经 `executeTool()` 走同一份 manifest |
| ORM/迁移 | **SQLModel + SQLAlchemy 2.0 + Alembic**；`Flow` 用 UUID 主键 + `data: dict` JSON 列存整张图；`AccessTypeEnum{PRIVATE,PUBLIC}`、`FlowType{workflow,agent}` | **Prisma 5.22** + 自有迁移目录；无 SQLAlchemy/Alembic |
| 依赖体量 | base 单包 **~200 个直接依赖**（LangChain 1.3、langchain-community、OpenTelemetry 全家桶、kubernetes、litellm、transformers、onnxruntime、redis、scipy、pandas…）+ 数十个 `lfx-*` bundle 子发行版 | 现有 pnpm 工作区依赖，无 Python 运行时 |
| 前端画布 | Vite + React Router + **Chakra/Radix/Tailwind** + `@xyflow/react ^12.3.6` + `elkjs` + zustand + react-query | Next 16 + React 19 + **AntD 6** + ProLayout |
| 权限 | 自带 JWT + api_key + authz + 目录级 PRIVATE/PUBLIC | 企业/服务商/职员/管理员四身份 + 主体归属 + 备案审核 + MCP 红线 |

### 12.2 硬性不兼容点（逐条）

1. **运行时割裂**：引入 Langflow ＝ 在架构里再加一套 **Python 进程 + Python 3.10+ 环境 + 数百 pip 依赖**，还要额外跑它的独立前端。这与既有约束「**不给服务器装东西**／优先用模型或浏览器端」直接冲突。
2. **引擎根本不在仓库里**：DAG 引擎是外部包 `lfx` 1.13.1，不是这份代码；连"拷源码"都拿不到核心，只能在 Python 环境里 pip 安装。
3. **数据层无法共享**：Langflow 的表由 **Alembic** 建（UUID 主键 + `data: dict` JSON 列），我们的表由 **Prisma** 建。若塞进同一 MySQL/PG，两套迁移历史互相污染；只能**并列各存一份**，等于图数据双写。
4. **权限模型不兼容**：Langflow 只有 `PRIVATE/PUBLIC` + 自带 authz；我们的粒度是"企业/服务商/职员/管理员 + 主体 + 备案"。对接＝**权限二次实现**，违反"权限不二次实现"。
5. **节点无法自动生成**：Langflow 节点是 Python 类，要把本系统某个操作变成节点，就得**每个模块写一段 Python 适配**；而我们的目标是"任何模块进 `endpoints` 契约就自动成为节点"，两边机制相反。
6. **前端不可复用**：Langflow 前端是 Vite + Chakra/Radix/Tailwind + React Router，与 Next 16 + AntD 6 + ProLayout 技术栈不同，组件树/主题/路由无法搬。

### 12.3 可借鉴的部分（概念层，可直接落到我们的 TS 实现）

- **图数据模型**：一张图＝`{nodes, edges}` 一个 JSON（Langflow 的 `Flow.data`）→ 对应我们 §11.6 的 `Workflow.graph`。
- **概念一一映射**：Flow→Workflow、Component→节点、Edge→连线、Playground→步进试跑、Flow JSON 导入导出→工作流导入导出、`FlowVersion`→`WorkflowVersion`、`webhook/endpoint_name/mcp_enabled`→发布为 REST/MCP。§11.2 已按此映射。
- **画布技术选型（唯一可直接照搬的具体件）**：`@xyflow/react`（React Flow v12，MIT、纯 React、与 Next 16 兼容）做编辑器画布，`elkjs` 做自动布局。
- **触发面**：定时（Langflow 用 `croniter`）、Webhook（`endpoint_name`）、MCP 暴露——与我们 §11.7 的 `MANUAL/SCHEDULE/EVENT/WEBHOOK/AGENT/MCP` 完全同构。
- **执行语义**：DAG 校验/环检测、节点重试·跳过·中止、暂停·恢复、步骤事件流——照抄**设计**，不照抄代码。

### 12.4 两个可选路线与建议

- **路线 A（推荐，已定）**：**不引入 Langflow 运行时**，按第十一节在 TS 侧自建引擎——节点目录从 `endpoints` + `AGENT_TOOL_MANIFEST` 派生，画布用 `@xyflow/react` + `elkjs`，借鉴 Langflow 的概念与交互（§12.3）。贴合"系统功能皆节点 + 被站内 Agent 调用 + 权限不二次实现"三个硬目标。
- **路线 B（不推荐）**：把 Langflow 作为**独立旁路服务**部署，经 MCP/REST 暴露，我们的编辑器只做编排壳。代价：多一套 Python 运行时 + 第二前端 + 第二权限系统，且两套编排会长期重复——除非明确要**大量复用 Langflow 自带的 LangChain 组件生态**，否则不值。
- **判断依据一句话**：要"**现成 AI 组件库**"→ Langflow 有优势；要"**把本系统功能编排成工作流并接站内 Agent**"→ 自建更贴合，节点目录能自动从契约派生。

> 本节为分析结论，不改动 §十一 的技术方案；§十一 的引擎按路线 A 在 TS 侧实现。
