## 一、需求拆解（你的原话 → 目标态）

| # | 你的原话（要点） | 目标态 |
|---|---|---|
| 1 | 兑换码分两种：积分兑换码、日卡兑换码 | 一张码在创建时就定死「兑的是积分还是卡」；用户端**只有一个输入框**，不需要选类型 |
| 2 | 用户只需输入兑换码，自动识别是哪种 | 后端按码值查目录行，用行上的 `assetType` 分流：`POINTS` 走现有入账，`CARD` 走发卡；前端提示语随之变成「积分到账 / 日卡已激活」 |
| 3 | 日卡从兑换成功起算 24 小时 | 卡的 `activatedAt = 发卡成功那一刻`，`expiresAt = activatedAt + validDays×24h`，**精确到秒，不看自然日**；同时支持 30 天卡（同一张机制，`validDays = 30`） |
| 4 | 一张卡只能绑定一个模型 + 一个量（LLM=tokens，图=张数，视频=秒数） | 卡规格目录每行**必须且只能选一个模型**（`catalogId`），量纲由该模型的 `billingUnit` 派生：`token` / `image` / `second`，不允许「通用卡」 |
| 5 | 图片卡不限分辨率 | 图片卡消耗恒为 1 张 = 1 额度，**不查分辨率、不设倍率** |
| 6 | 视频卡不限分辨率，但按规格换算秒数（480p=1 秒 ⇒ 720p=2 秒），**倍率由管理员建卡时配置** | 卡规格上挂一张「规格倍率表」`specMultipliers`（`{ video_resolution: "720p", multiplier: 2 }`），结算时消耗 = 实际秒数 × 命中倍率；未命中档位回落基准倍率 1 |
| 7 | 管理员先配置卡规格，再由兑换码绑定卡；也支持积分直接兑换日卡 | 两段式：① 平台管理员维护「卡规格目录」（模型、额度、有效期、倍率、积分价、现金价）；② 兑换码/积分/现金三个入口都指向同一张规格 |
| 8 | 要有兑换订单区：日卡购买订单、日卡兑换订单、积分兑换订单，各自显示消耗进度 | 积分中心新增「**兑换订单**」页签，三类订单一屏列出，每条带**额度进度条 + 剩余量 + 剩余时长 + 状态** |
| 9 | 卡的量只能在绑定的模型上用，别处用不了 | 结算时先按 `provider + modelKey` 精确匹配可用卡；匹配不上就不扣卡（**不跨模型、不折算积分、不抵扣其它消费**） |
| 10 | 帮助中心要写清 Qoder、Codex 怎么配 API Key | 帮助中心新增「**在 Qoder / Codex 里配置 API Key**」主题（含 Base URL、Key、Model ID 三步），并在模型广场话题里补「卡额度在外部客户端同样生效」 |
| 11 | 加一个使用帮助说明，快速新开窗口打开帮助中心 | 模型广场「调用方式」抽屉、兑换码面板、兑换订单一处放「使用帮助」按钮，`window.open('/help?topic=…', '_blank')` |
| 12 | 模型广场把 Model ID 做得容易复制 | 模型卡片标识、调用方式抽屉的「模型标识」都加**一键复制**（现有 `copy()` 复用） |

## 四、核心机制

### 4.1 兑换码类型自动识别

用户侧仍然只有一个输入框、一个「兑换」按钮：

1. `redeem()` 沿用现有 `code.trim().toUpperCase()` 查 `point_promo_codes`（`promo.service.ts:162`）。
2. 命中后按行上的 `assetType` 分流：
   - `POINTS`：完全走现路径（校验 → 原子抢 `maxRedemptions` → `perUserLimit` → `points.credit('EARN')`）。
   - `CARD`：同样校验状态/时间窗/次数，**不产生积分**，改为在同一事务里 `point_promo_redemptions` 落一行（`points` 记 0、新增 `cardCode` 快照字段用 `refAmount` 存额度）+ `point_user_cards` 发卡 + `point_card_orders`（`kind=CARD_CODE`，`status=ISSUED`）。
3. 返回值在 `redeemPromoResultSchema` 上**加字段而不是改字段**（`points/balance/promoCode/promoName` 原样保留），新增 `assetType`、`card`（`{ name, modelName, unit, quota, validDays, expiresAt, cardId }`）。旧前端读到的仍是积分文案，新前端按 `assetType` 分支显示「日卡已激活：DeepSeek-V3 · 1000 万 tokens · 24 小时」。
4. 「码不存在 / 已停用 / 不在时间窗 / 已兑完 / 已达个人上限」沿用现有报错，不新增错误面。

> 为什么不用码前缀识别：前缀（如 `CARD-`）会限制发码格式、且改不了历史码。**以目录行为准的查表识别**更稳，也保证「一个框输入任意码」都能识别。

### 4.2 有效期语义

- `activatedAt` = 发卡那一刻（不是自然日 00:00）。
- `expiresAt = activatedAt + validDays × 24h`（日卡 1、30 天卡 30，字段可扩展）。
- 判定「可用」的谓词只有一处：`status = 'ACTIVE' AND expiresAt > NOW() AND quotaUsed < quotaTotal`，收口成 `CardService.findUsable(userId, provider, modelKey)`，扣减/闸门/列表都调它，避免多处口径漂移。
- 过期不打状态位也不重要（谓词已排除），但提供一个夜间批 `expireCards()` 把 `ACTIVE → EXPIRED` 刷出来，只为了让列表显示准确；挂在 `points-daily.scheduler.ts` 既有日批里，不新增调度器。
- **兑换/购买都不可叠加续期**：一次兑换=一张新卡。同一模型同时有多张有效卡时，按 `expiresAt` 升序（先到期先花）扣减，避免用户浪费临期卡。

### 4.3 绑定唯一模型 + 量纲

- 建卡时 `catalogId` 必填且只能一个，保存时从 `ModelCatalog` 抄 `provider/modelKey/billingUnit` 进规格行；`billingUnit='call'` 的模型**不允许建卡**（无「量」可表达），前端下拉只放 `token/image/second` 三类已上架模型。
- 匹配用 `provider + modelKey`（与 `@@unique([provider, modelKey])` 同键），不用 `catalogId`——因为同一 `modelKey` 允许后台改价/换上游，改行不改变用户手里那张卡的权利。
- 卡的额度**只能用于该模型**：不折算积分、不能抵扣其它模型、不能用来充值/存储/其它模块计费。这是「消耗进度」成立的前提。

### 4.4 视频秒数的规格倍率

- 管理员在卡规格上配 `specMultipliers`，写法与 `ModelCatalog.tiers` 一致：
  `[{ match: { video_resolution: "480p" }, multiplier: 1 }, { match: { video_resolution: "720p" }, multiplier: 2 }, { match: { video_resolution: "1080p" }, multiplier: 4 }]`
- 新增 `cardMultiplierOf(specMultipliers, tier)`，**命中规则完全复用 `matchTier`**（`model-plaza.pricing.ts:269`）：先精确匹配 `video_resolution`/`resolution`/`size`；未命中时取「不低于请求高度的最接近档位」；仍无 → 返回基准 1（不猜更高档，避免多扣）。
- 消耗量：`cardDeduct = quantityOf('second', 上游返回秒数) × multiplier`（`second` 保留 3 位小数，`pricing.ts:361`）。
- 图片卡恒为 1（用户明确「张数，不管分辨率」），token 卡恒为 1（token 没有分辨率维度）。

### 4.5 扣费顺序：卡 → 积分

新增 `CardService.settleBeforeCharge(user, row, cost, usage)`，插在 `plaza.usage.charge()` 之前（唯一一处，三个入口自动同源）：

1. `findUsable(userId, row.provider, row.modelKey)` 取临期优先的一张卡。
2. 需要扣量 = 按 `billingUnit` 折算本次用量：`token → promptTokens + completionTokens`（与 `computePlazaCost` 的 token 分支同口径，缓存读写不重复计进卡）；`image/call → quantityOf(...)`；`second → quantityOf(...) × cardMultiplierOf(...)`。
3. **原子扣卡**（复刻 `points.debit` 的范式，`points.service.ts:185`）：
   `updateMany({ where: { id: card.id, status:'ACTIVE', expiresAt:{gt:now}, quotaUsed:{lt:quotaTotal} , quotaUsed + need <= quotaTotal }, data: { quotaUsed:{ increment: need } } })`
   `count===0` 表示并发抢光或卡不够 → 本次不扣卡（够扣一部分见 D4）。
4. 本次 `need > 卡剩余额度` 时：**能扣多少扣多少**（卡内额度不浪费），差额继续走 `charge()` 扣积分；`charge()` 余额不足转欠费的既有行为不变。
5. 卡全额覆盖时**不调 `points.debit`**：`charge(userId, 0, meta)` 走的是 `usage.service.ts:94-97` 那条「amount≤0 只写 `usage_events(billed=0)`」的分支，天然不留假积分流水。
6. `model_usage_logs` 落 `userCardId` + `cardDeduct`，进度与对账同源。

### 4.6 前置闸门必须卡感知（关键，否则有钱买卡、零余额的人被拒）

- `assertCanCall()`（`usage.service.ts:74`）：现在「`ARREARS` 或 `balance<=0`」直接拒。改为**先查可用卡**：命中且剩余额度 > 0 → 放行（不看余额与欠费位，欠费只影响积分侧）。
- 对外预估闸（`model-plaza.public.ts:540-561`）：预计成本先减掉「本次可从卡扣的量」，**只对差额**判余额，报错文案要分别说清「卡额度不足」与「积分不足」。
- Key 级 `pointsQuota`（`public.ts:170-181`）：它是**积分预算**闸，因此只统计 `pointsCost`，卡内消耗**不计入**（见 D6）。
- 站内试用按钮、模型广场卡片：余额为 0 但有可用卡时不该灰掉，需要在 `/enterprise/model-plaza/*` 的会话视图里回一个 `usableCard: { modelKey, quotaRemaining, unit, expiresAt } | null`。

### 4.7 积分直接兑换日卡

- 规格行 `pointsPrice > 0` 才允许；入口放在「兑换订单」页签的「用积分换卡」动作里（不新开菜单，符合低频并入主栏目）。
- 流程（单事务）：建 `PointCardOrder(kind=CARD_POINTS, status=CREATED)` → `points.debit(userId,'SPEND',pointsPrice,{scene:'card_exchange', refType:'card_order', refId:orderNo, remark:'积分兑换〈卡名〉'})` → 发卡 → 订单 `ISSUED`。
- **积分不足直接拒**（`POINTS_INSUFFICIENT`），不做「部分用积分」；这与「卡额度不足才用积分补」是两个不同方向，别混。
- 失败回滚：发卡异常时同事务回滚，`points.refundTx` 只在跨事务场景才用；`debit` 与发卡在同一 `$transaction` 里，天然原子。

### 4.8 现金购买日卡

完全复刻 `recharge.service.ts` 的骨架，避免第二种支付实现：

- `createOrder()`：`allocateNo(prisma,'CD')` 单号；规格行 `cashCents > 0` 才可下单；调 `wechat-pay.client` 生成 `prepayId/codeUrl`（NATIVE 扫码 / H5）。
- `handleNotify()` + `settle()`：幂等键＝微信 `transaction_id`（唯一索引兜并发），已 `PAID` 直接返回；置 `PAID` 后**同事务发卡**并置 `ISSUED`。
- `query()/closeExpired()`：并入 `points-daily.scheduler.ts` 既有关单调度（`recharge.service.ts:406`），只多扫一张表。
- 支付通道未配置时：**购买入口不渲染**（按既有「通道未配则不可选」口径），不做假按钮。
- 退款：本期不做自动退款；`REFUNDED` 状态位保留但只有后台「撤销卡 + 手工补偿积分」路径写它（见 4.10）。

### 4.9 消耗进度怎么算

进度不落冗余列，实时算，避免与流水打架：

- 已用 = `quotaUsed`；剩余 = `quotaTotal - quotaUsed`；百分比 = 已用/总量。
- 单位展示：`token` → 「X 万 tokens」（后台配的是绝对个数）；`image` → 「X 张」；`second` → 「X 秒」，并在 tooltip 里说明「按卡规格倍率折算后的秒数」。
- 订单条目 = 关联卡的快照：`point_card_orders.userCardId → point_user_cards`。订单一旦 `ISSUED` 就不改，进度永远跟着卡走。
- 明细：`model_usage_logs where userCardId=? order by createdAt desc`，给「本次扣量 + 模型 + 来源（站内/API）+ 时间」，点开可核对。

### 4.10 撤销、异常与边界

| 场景 | 口径 |
|---|---|
| 后台撤销卡 | `status=REVOKED`，已消耗不退；**未用额度不退现金**，后台可一键「按剩余比例补偿积分」（走 `points.credit('EARN', {scene:'card_compensate'})`）——补偿动作需管理员密码确认，沿用既有敏感操作口径 |
| 兑换码发出去的卡作废 | 兑换记录保留（`point_promo_redemptions` 不删），卡 REVOKED 并在订单行显示「已撤销」 |
| 调用发生在过期前、结算落在过期后 | **正常扣卡**（授权已发生）；扣不到（已过期且谓词不过）则整笔转积分并在日志 `message` 注明「卡已过期，改按积分结算」 |
| 同一码被并发抢最后一份 | 沿用 `maxRedemptions` 原子抢量（`promo.service.ts:162` 之后那段条件更新），抢不到就报「已被兑完」 |
| 同一模型上多张卡 | 先到期先扣；额度进度分别显示，不合并 |
| 卡的模型被后台下架（`enabled=false`） | 卡仍可用来调用（走 `/v1` 时按 `enabled` 现状判定），因此明确：**下架即不可用**，界面对受影响用户提示「该卡绑定模型已下架，请联系客服/按剩余折算补偿积分」；这是必须写清的边界，避免用户以为被吞 |
| 管理员改了卡规格 | 规格行改动**不影响已发出的卡**（快照已落在 `point_user_cards`），这是发卡类资产的通用规则 |

### 4.11 每人持有上限（2026-11-11 追加）

兑换码自带的「每人上限」钉在**单张码**上，换一张码就能再兑一次，挡不住低价日卡被同一账号靠多张码囤积。因此把上限挪到卡规格上：

- 字段：`point_card_templates.per_user_limit`（迁移 `0078_point_card_per_user_limit`），`0=不限`，上限 100；后台「时长卡规格」弹窗新增「每人最多兑换（张，0＝不限）」，列表列显示「N 张 / 不限」。
- 归并口径：**按卡规格（`templateCode`）合计**，兑换码兑换、积分直兑、现金购买三入口共用 `CardService.assertHoldLimit`；计数取 `point_user_cards` 中该用户该规格下 `status != 'REVOKED'` 的卡数（被撤销的卡不占名额）。
- 拦截时机：
  - 兑换码：`redeemCard` → `issueForPromoCode` 发卡前校验，失败时整笔回滚并释放码名额；
  - 积分直兑：`exchangeByPoints` 在**扣积分之前**校验，避免扣了积分发不出卡；
  - 现金购买：`createCashOrder` 在**下单之前**校验，不产生待支付订单；支付回调 `settlePay` 时若名额已被其它入口占满，**照常发卡并记 `card_hold_limit_exceeded_after_payment` 告警**——钱已经收了，不能留一条「付了钱没卡」的订单。
- 只拦新兑换：调小上限不会撤销已发出的卡，已持有的卡照常使用到额度用尽或到期。
- 提示文案：`「卡名」每位用户最多兑换 N 张，你已持有 M 张；已持有的卡到期后或额度用尽即可再次兑换`。

## 九、决策点（推荐默认值，确认即可开工）

| # | 决策 | 选项 | **推荐** |
|---|---|---|---|
| D1 | 码类型识别方式 | A 查目录行分流 / B 码前缀约定 | **A**：不改码格式、历史码天然兼容 |
| D2 | 卡额度落在哪套模型 | A 新建 `point_user_cards` / B 塞进 `EntitlementUsage` | **A**：权益表是「组织×功能×自然月」，与「个人×模型×24h」维度不同，混用会污染两套口径 |
| D3 | 「积分兑换订单」指什么 | A 用**积分**兑换日卡的订单 / B 用兑换码兑**积分**的订单 | **A**（与「支持积分直接兑换日卡」直接对应）。兑积分的老码记录继续留在「兑换码 + 流水」，不塞进这个列表，避免一个列表混两种维度 |
| D4 | 卡额度不够本次调用时 | A 卡能扣多少扣多少，差额走积分 / B 卡不扣，整笔走积分 / C 直接拒绝 | **A**：用户额度不浪费，且积分侧已有欠费兜底 |
| D5 | LLM 卡的「量」口径 | A `prompt+completion` / B 含缓存读写折算 | **A**：简单且与积分计价的 token 分支对齐；缓存价只影响积分成本，不影响卡的 tokens 数 |
| D6 | 卡内消耗是否计入 API Key 的 `pointsQuota` | A 不计入 / B 按等值积分计入 | **A**：`pointsQuota` 是积分预算帽（`public.ts:170`），卡是另一份权利；否则买卡用户在 Qoder 里会被 Key 额度误杀 |
| D7 | 视频倍率未命中档位 | A 回落 1 倍 / B 取最高档 / C 拒单 | **A 回落基准 1 倍**，并在明细里标注命中来源（`精确/就近/回落`）。与 `matchTier` 的「不猜更高档」原则一致 |
| D8 | Codex 支持 | A 本期只做 Qoder，帮助中心如实说明 Codex 暂不支持 / B 同批补 `/v1/responses` 适配层 | **B**（工作量约一个批次的 1/4，做完 Codex 与 Qoder 一样可用）。若你想先上卡片能力，也可选 A，把 B 单独排到下一批 |

## 十、验收清单（联调时按此逐条实测，不看代码想当然）

1. 平台管理员建一张「DeepSeek-V3｜1000 万 tokens｜1 天」卡 → 建一个绑它的兑换码。
2. 用户输入该码 → 自动识别为卡 → 积分不变、卡到账、进度 0%、有效期 24 小时后（精确到分）。
3. 同一用户再输入一个积分码 → 自动识别为积分，现有文案与到账不变。
4. 用这张卡在模型广场站内试用 → 用量页出现 `cardDeduct`，积分流水**没有**新增扣分。
5. 拿 `ek_` Key 在 Qoder 里调同一模型 → 卡的额度继续下降；调**另一个**模型 → 卡的额度不动，走积分。
6. 卡额度扣到只剩 1 万 tokens 时调一次 3 万 tokens → 卡扣 1 万到 100%、差额走积分（D4）。
7. 余额 0 + 欠费状态 + 有效卡 → 调用放行（D4 前提，闸门卡感知）。
8. 视频卡配 `480p=1 / 720p=2`，出 5 秒 720p → 卡内扣 10 秒；出 5 秒 480p → 扣 5 秒；请求 1080p → 按就近/回落规则并在明细标注。
9. 图片卡出 3 张（任意分辨率）→ 扣 3 张。
10. 「兑换订单」页签三类订单各出现一次，进度条、剩余量、剩余时长、状态正确；点明细能逐条对上第 4-9 步的消耗。
11. Model ID 在卡片与抽屉各复制一次，粘贴板内容等于目录里的 `modelKey`。
12. 三处「使用帮助」新窗口打开对应话题，正文里的列表/加粗渲染正常、无原样 `**` 残留。
13. 后台撤销卡 → 卡立即不可用，未用额度显示「已撤销」，补偿积分动作留痕。
14. 每人上限（4.11）：规格设「每人最多兑换 2 张」，同一用户用**两个不同**兑换码兑同一规格 → 第 2 张成功后第 3 张被拒，提示「已持有 M 张」；换另一账号仍可兑 2 张。
15. 上限按三入口合计：兑换码兑 1 张 + 积分直兑 1 张已满 2 张 → 再点「购买」在下单前就被拒（不产生待支付订单）；积分直兑在**扣积分之前**被拒。
16. 规格「每人最多兑换」留 0 → 不限额，连兑 3 张以上不出错；把上限改小后已发出的卡照常可用到到期，不撤销。
17. 支付回调边界：下单时未满、支付完成时名额已被其它入口占满 → 照常发卡，日志出现 `card_hold_limit_exceeded_after_payment` 告警（不留「付了钱没卡」的订单）。

## 十一、风险与边界

- **不动用户可见的积分价与折扣口径**：卡只改「先扣什么」，不改 `computePlazaCost` 的价格计算，也不新增计费科目（`PLAZA_USAGE_CODE='model_plaza'` 保持唯一 AI 用量科目）。
- **不做通用卡**：一张卡绑一个模型是你明确定的规则，界面上不提供「多模型/全模型通用」入口，也不做「跨模型折算」。
- **不接现金退卡**：本期只留 `REFUNDED` 状态位与后台手工补偿，不接微信退款接口（那是另一条凭据链，需要单独设计）。
- **卡不是权益配额**：不与 `Entitlement*` 联动；组织套餐的「功能可用与否」仍然独立生效，卡只解决「模型用量从哪出」。
- **欠费语义只作用于积分侧**：欠费用户有可用卡时仍能用卡（这是 D4/4.6 的直接结果），需要在帮助中心写清，免得运营误解成「欠费也能白嫖」——卡是他自己已经付费/兑换到的额度。
- **迁移与并发**：发卡、扣额度全部走条件更新 + 唯一键幂等（`transactionId`、`orderNo`、`maxRedemptions` 抢量），不依赖应用层判重。
- **与 RPA 方案的关系**：本方案只动积分/模型广场链路；本地 Chrome 插件 RPA 方案（`docs/本地Chrome插件RPA控制方案.md`）独立成文、迁移号错开，两份互不阻塞。
- **每人上限是发卡动作的闸，不是资产回收**：上限只拦新兑换（4.11），调小或设为 0 都不撤销已发出的卡；已付现金的订单在回调时必发卡（只告警），这是「可用性优先于记账」的直接取舍。计数按 `templateCode` 且不含 `REVOKED`，所以后台撤销一张卡会释放一个名额——这是有意为之（撤销即视为未持有）。
