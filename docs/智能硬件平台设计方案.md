## 四、数据模型（新增 6 张表）

```
hw_models                 硬件型号（平台级目录，管理员维护）
  id, code(唯一，如 esp32-devkit), name, vendor, chip, category,
  summary, coverUrl, specJson(能力/接口/尺寸等结构化字段),
  featured, enabled, sortOrder, createdBy, createdAt, updatedAt

hw_dev_kits               开发包（型号 × 版本）
  id, modelId, version, channel(STABLE|BETA), fileName, fileSize, ossKey,
  sha256, changelog, docUrl, minFirmware,
  downloadCount, enabled, createdBy, createdAt, updatedAt
  unique(modelId, version)

hw_devices                用户接入的实体设备
  id, userId, modelId, name, serialNo,
  tokenHash(设备令牌 SHA-256), tokenPrefix(前 8 位，仅展示),
  status(ONLINE|OFFLINE|NEVER), lastSeenAt, lastIp, firmwareVersion,
  metaJson, enabled, createdAt, updatedAt
  index(userId, modelId), unique(tokenHash)

hw_device_events          设备事件流水（心跳 / 指令 / 状态变更，供排障）
  id, deviceId, kind(HEARTBEAT|COMMAND|RESULT|STATUS), direction(IN|OUT),
  commandCode, payloadJson, ok, latencyMs, message, createdAt
  index(deviceId, createdAt)

hw_tools                  工具定义（API 与 MCP 共用一张表，用 kind 区分）
  id, modelId, kind(API|MCP), scope(DEFAULT|USER), ownerUserId(用户自建时填),
  code(型号内唯一), name, description,
  transport(HTTP|DEVICE),          // HTTP＝平台代调设备 HTTP；DEVICE＝下发指令等设备回执
  method, path,                    // HTTP 用
  commandCode,                     // DEVICE 用
  paramsJson(参数 JSON Schema), responseJson, examplesJson,
  write, requiresGrant, enabled, sortOrder, createdBy, createdAt, updatedAt
  unique(modelId, kind, scope, ownerUserId, code)

hw_tool_grants            用户对「写类」工具的自动执行授权（对齐平台 MCP 的授权闸）
  id, userId, toolId, grantedAt
  unique(userId, toolId)
```

**为什么工具用一张表**：API 与 MCP 是同一份「设备能力」的两种出口，参数、写标记、授权口径完全一致，只是展示形态不同（REST 示例 vs MCP tool schema）。分两张表会出现同一能力改两遍、漂移。

**为什么 `transport` 分两种**：ESP32 这类 MCU 通常只能主动出网（NAT 后无法被访问），必须走「平台下发、设备拉取」；Jetson 这类能跑常驻服务的，可以直接暴露 HTTP 由平台代调。两种都要支持，否则 ESP32 接进来只能看心跳不能控制。

## 五、设备接入与心跳（「添加硬件」）

### 5.1 接入方式

| 方式 | 适用 | 用户操作 | 设备侧 |
| --- | --- | --- | --- |
| A. 令牌直连（推荐，两种硬件都支持） | ESP32 / Jetson | 页面「添加硬件」→ 选型号 → 填名称 → 生成令牌（只显示一次） | 把令牌写进固件配置，设备启动后定时上报 |
| B. 局域网代调 | Jetson 等常驻服务 | 添加时填设备内网/公网地址 + 端口 | 设备跑开发包里的 agent 进程，监听本地端口 |
| C. 扫码/序列号绑定（可选，后续） | 出厂预置 | 扫设备二维码 | 设备预置序列号，首次联网自动注册 |

**令牌设计**（对齐获客插件的「一次性令牌」与 IM 回调的「路径内嵌 token」两种既有做法）：
- 生成 32 位随机串，**只存 SHA-256**，明文只在生成那一刻显示一次，之后不可再取（和 `api_keys` 同口径）。
- 设备请求头 `x-device-token: hw_...`，与 `ek_` Key 完全分开——设备令牌**只能**走设备通道，**不能**调任何业务接口。

### 5.2 心跳协议（最小可用）

```
POST /api/public/hardware/heartbeat
x-device-token: hw_xxxxxxxx
{ "firmware": "1.2.0", "uptime": 3600, "metrics": { "cpu": 12, "mem": 41 } }
→ { "code": 0, "data": { "status": "ONLINE", "serverTime": "...", "pendingCommands": 2 } }
```

- 设备每 30~60 秒上报一次；服务端更新 `lastSeenAt`、`status=ONLINE`。
- 定时任务每 1 分钟扫一遍：`lastSeenAt` 超过 3 个心跳周期（默认 3 分钟）→ `OFFLINE`；从未上报过 → `NEVER`。
- 心跳响应里带 `pendingCommands`，设备可顺带拉取待执行指令（见 6.3 的 DEVICE 通道），省一次请求。

### 5.3 页面呈现

「添加硬件」列表列：设备名 / 型号 / 在线状态（绿点在线、灰点离线、空心未激活）/ 最后在线 / 固件版本 / 操作（详情、重置令牌、停用、删除）。详情抽屉里是最近心跳曲线与事件流水。

## 六、API 与 MCP（两个菜单）

### 6.1 型号选择器（两个菜单共用）

进入页面时**不显示任何工具**，顶部是型号选择器（卡片或下拉，单选）。选中后：

- 只列该型号的工具（默认工具 + 我自建的工具）；
- 切换型号时列表与示例整体刷新；
- 型号选择记在 URL query（`?model=esp32-devkit`），可分享、可回退。

> 这符合你「先要选择硬件类型才能出现对应的工具」的要求，也避免把几十种型号的上百个工具一次性铺满。

### 6.2 「API」菜单内容

每个工具一张折叠卡：

- 接口名 + 方法 + 路径（如 `POST /api/v1/hardware/devices/{id}/gpio`）；
- 参数表（来自 `paramsJson`，与 MCP 的 inputSchema 同源）；
- `curl` / `Python` / `TypeScript` 三段可复制示例（`{deviceId}` 用当前账号的设备自动填充）；
- 写类工具标注「需授权」。

**对外通道口径**：硬件 API 统一挂在 `/api/v1/hardware/**`，用**同一把 `ek_` Key**（不引入第二套 Key）。理由：`ek_` 已经是本站唯一的机器通道凭据，再发一套会让用户多管一把钥匙。

### 6.3 「MCP」菜单内容

每个工具一行：工具名（`hw__<modelCode>__<toolCode>`）、说明、参数 schema、读/写、是否已授权。

页面同时给**接入配置片段**（可直接粘进 Claude Desktop / Cursor / Codex 的配置）：

```json
{
  "mcpServers": {
    "aiworkin-hardware": {
      "type": "http",
      "url": "https://<站点域名>/api/v1/hardware/mcp",
      "headers": { "x-api-key": "ek_..." }
    }
  }
}
```

**为什么单独一个端点**：平台 MCP 在 `/api/v1/mcp`，硬件 MCP 在 `/api/v1/hardware/mcp`。两个独立端点，`tools/list` 各返回各的，平台 MCP 的工具清单里**永远不会**出现硬件工具，反之亦然。这就是你说的「不要和平台的 MCP 混起来」的硬隔离。

### 6.4 工具两种执行通道

| transport | 适用 | 平台怎么执行 |
| --- | --- | --- |
| `HTTP` | 设备能跑常驻服务（Jetson） | 平台按 `method + path` 直接请求设备地址，带设备令牌，超时 5s |
| `DEVICE` | 设备只能主动出网（ESP32） | 平台落一条 `hw_device_events(kind=COMMAND)`，设备下一次心跳或拉取时取走，执行后回执 `RESULT` |

`DEVICE` 通道的超时口径：指令 30 秒内无回执记 `timeout`，事件流水里留痕，MCP / API 返回明确的「设备未在时限内回执」。

### 6.5 Agent 调用（站内 Agent 与外部 MCP 客户端）

- **外部 MCP 客户端**：连 `/api/v1/hardware/mcp`，`tools/list` 只返回该账号**已接入设备所属型号**的工具（默认 + 自建）。没有任何设备时返回空清单并附说明。
- **站内 Agent**：在统一工具清单里新增一类 `hardware`，命名空间 `hw__<modelCode>__<toolCode>`，与现有 `mcp__c<id>__` 并列；派发时走硬件服务。
- **写类工具授权闸**：与平台 MCP 的「可自动执行的动作」同一套口径——未授权只出草案、`dryRun` 只出草案、无人值守默认只出草案。**这是本方案必须补的一块，见第八节。**

## 八、缺口分析：用 API / Agent 调用还差什么

这是你特意问的部分。我按「不补就调不通 / 调得通但不安全 / 调得通但不好用」三档列。

### 8.1 不补就调不通（硬缺口）

| # | 缺口 | 现状 | 要补什么 |
| --- | --- | --- | --- |
| G1 | **设备到平台的通道** | 全站没有任何设备接入通道；现有免登录回调只有飞书 / 企微 / 获客插件三种 | 新增设备心跳与指令回执的公开端点 + 设备令牌校验 |
| G2 | **设备令牌体系** | `api_keys` 只有 `ek_` 一套，给设备发 `ek_` 等于把账号全权限交出去 | 新增设备令牌（只存哈希、只走设备通道、可单独吊销） |
| G3 | **平台 MCP 不认识动态工具** | `/api/v1/mcp` 的 `tools/list` 只返回固定的 `MCP_TOOL_NAMES`（6 个元工具 + 5 个邮件工具），业务接口靠 `list_operations` 间接调 | 新增独立硬件 MCP 端点，`tools/list` 按型号动态返回 |
| G4 | **站内 Agent 不认识硬件工具** | `runAgentTool` 只认 `mcp__` 前缀 + 固定业务/内置名 | 新增 `hw__` 前缀分支 + 工具清单新增 `hardware` 类 |
| G5 | **设备侧 SDK 不存在** | 没有任何固件 / SDK | 开发包必须真的包含可编译的 SDK（见第十节），否则「直接安装」无从谈起 |

### 8.2 调得通但不安全（必须补）

| # | 缺口 | 现状 | 要补什么 |
| --- | --- | --- | --- |
| G6 | **连接器类工具没有授权闸** | `agent-connectors.service.ts:655` 的 `callTool` 只有「存在 / 启用 / 在本次任务范围」三查，**没有** grantedActions、没有 forbidden、没有 dryRun | 硬件工具从第一天就带授权闸；同时建议把连接器也补齐（见 8.4） |
| G7 | **设备指令可被 Agent 无限下发** | 无频控 | 每设备每分钟指令上限、每账号每日上限；超限返回明确原因 |
| G8 | **开发包与工具定义可被篡改** | 上传后无校验 | 开发包记 SHA-256，页面展示；工具定义变更写审计 |
| G9 | **设备令牌泄露面** | 令牌写进固件，可能被反编译 | 令牌可一键重置（旧令牌立即失效）；支持「停用设备」；事件流水可查异常来源 IP |

### 8.3 调得通但不好用（体验缺口）

| # | 缺口 | 要补什么 |
| --- | --- | --- |
| G10 | 用户不知道「我的设备支持哪些工具」 | MCP / API 页先选型号，并只列**已接入设备**的型号；未接入时引导去「添加硬件」 |
| G11 | 调试成本高 | MCP 页提供「试调」按钮，直接打一次真实请求并展示原始响应；失败时给出排障提示（设备离线 / 超时 / 参数不符） |
| G12 | 多设备同名难区分 | 设备名 + 序列号 + 最近在线时间同列；工具调用必须带 `deviceId` |
| G13 | 用户自建工具没人管 | 自建工具仅本人可见、仅本人可用；首版不上架「型号默认」与市场（结论见 §十四 第 6、7 条） |

### 8.4 连接器授权闸：已确认一起修（2026-11-08）

`ContentAgentMcpConnector` 这类用户自建 MCP 连接器的工具，在站内 Agent 里**没有写动作授权闸**：模型一旦选中就无条件执行。平台 MCP 有「永久排除 + 勾选授权 + 无人值守只出草案」三层，连接器一层都没有。

**结论：与智能硬件同批修复，并把闸做成通用能力**（硬件工具直接复用，不再写第二套）。修法见 8.5。

### 8.5 连接器授权闸的修法

#### 现状（证据）

| 层 | 平台 MCP（`/api/v1/mcp`） | 连接器工具（`mcp__c<id>__<tool>`） |
| --- | --- | --- |
| 永久排除 | `MCP_FORBIDDEN_ACTIONS` | 无 |
| 勾选授权 | `agent_action_grants` 表 + `grantedActions()` | 无 |
| 无人值守 | `unattendedDenialOf()`：`trigger=schedule` 且未显式放开 → 只出草案 | 无（`callBuiltin` 传了 `allowWrite`，但那是给 `mcp__c0__` 的，外部连接器不经过） |
| dryRun | 有 | 无 |
| 留痕 | 执行与拦截都写智能体记忆 | 无 |

代码位置：[agent-connectors.service.ts:655](file:///E:/wwwroot/oem-enterprise/backend/src/content/agent-connectors.service.ts#L655) `callTool` 只有「格式 / 范围 / 存在 / 启用 / 工具存在 / 地址存活」六查，随后直接 `client.callTool()`。

#### 关键设计决策：**按连接器授权，不按工具名授权**

连接器的工具是**运行时探测**出来的（`specsOf` → `listTools()`，缓存 `TOOL_CACHE_MS`），远端随时可能增删改名。若按工具名存授权：

- 远端把 `send_email` 改名成 `send_email_v2`，授权静默失效 → 用户以为放开了，实际每次只出草案；
- 远端新增一个危险工具，旧授权不会覆盖它，但用户也无法预知要勾哪个；
- 工具名由第三方控制，直接进授权表等于让第三方决定本站的授权粒度。

因此授权粒度定为**「连接器 + 读/写」**：用户信任的是「这个连接器」，不是它今天恰好暴露的某个工具名。这与现有 `AgentActionGrant` 按 operationId 授权的口径不同，原因也写清：operationId 是本站契约里的稳定标识，工具名不是。

#### 数据模型（复用现有表，加 2 列）

```
agent_action_grants（现有表，加 2 列）
  + scopeType   VarChar(16)  default 'ACTION'   // ACTION＝契约动作（现有行）；CONNECTOR＝连接器
  + connectorId Int          default 0          // scopeType=CONNECTOR 时有效
  action 列在 CONNECTOR 行存固定值 'CONNECTOR'
  unique(userId, action) → unique(userId, scopeType, action, connectorId)
  新增 index(userId, scopeType)
```

唯一键必须一起换：CONNECTOR 行的 `action` 是固定值，旧的 `(userId, action)` 会让同一账号只能存下一条连接器授权。换成四列后 ACTION 行的唯一性没有放松（`scopeType`、`connectorId` 对它们都是常量），因此是替换而不是新增。

不新建表：授权闸的读写、审计、验密逻辑全部复用 `AgentMemoryService.saveGrants`，只扩一个分支。

#### 运行时闸（`callTool` 里新增，位置在「地址存活」之后、真正调用之前）

```
1. 读本轮作用域 scope = currentAgentScope()
2. 无人值守：scope?.trigger === 'schedule' 且 scope.allowWrite !== true
   → 不执行，返回「无人值守只出草案」+ 草案（工具名 + 参数），ok=false
3. 授权：grantedConnectors = 本人 CONNECTOR 类授权集合
   → 未包含该 connectorId → 不执行，返回「未授权：请到 Agent → 可自动执行的动作 → 连接器 勾选」+ 草案
4. 通过 → 执行，并写智能体记忆（domain='connector'，action=`mcp__c<id>__<tool>`，outcome=ok/failed）
   第 2、3 步拦截也写记忆（outcome=blocked，errorCode=SCHEDULE_DENIED / NOT_GRANTED）
```

**为什么不做 dryRun**：连接器工具的参数 schema 由远端给，本站无法像契约那样预校验并生成「与真实报文逐字一致」的草案。硬做一个假草案会误导用户。改为「拦截时把模型打算调的工具名与参数原样回给用户」——用户看到的就是模型要发的东西。

**为什么不做永久排除**：本站无法判断第三方工具哪个危险，写死名单会误伤。改为**默认全拒 + 用户逐个连接器放开**，风险落在用户自己勾选的那一步。

#### 界面（Agent → 可自动执行的动作）

现有面板按 `domain` 分组列契约动作。新增一个独立分区「**MCP 连接器**」，每个连接器一行：

```
[✓] 连接器「我的知识库」  mcp__c12__*  · 14 个工具 · 最近探测 2 分钟前
    远端工具随连接器变化，勾选即信任该连接器的全部工具
```

- 默认**不勾选**（与现状相反：现在是隐式全放开，改成显式授权）。
- 新增勾选要验登录密码（沿用现有 `assertSensitivePassword` 口径），取消随时可行。
- 连接器被删除 / 停用 → 授权行保留但置灰（恢复后自动生效），不静默删数据。

#### 迁移与兼容

- 迁移 `0041`（与硬件同批）加两列，默认值保证现有行语义不变。
- **存量连接器不做自动授权**：升级后用户需重新勾选，否则只出草案。这是有意为之——现状是「无闸」，任何自动迁移都等于把无闸状态原样搬进新模型。升级说明里要写清这一条。
- 前端面板在「零授权 + 有连接器」时给一条提示，避免用户以为坏了。

#### 验收

| 场景 | 期望 |
| --- | --- |
| 对话中调用已授权连接器的工具 | 正常执行，智能体记忆留痕 |
| 对话中调用未授权连接器 | 不执行，返回草案 + 勾选指引 |
| 定时任务调用已授权连接器（任务未放开写） | 不执行，返回无人值守草案 |
| 定时任务调用已授权连接器（任务已放开写 + 验密） | 执行 |

| 远端新增工具 | 随连接器授权直接可用（不需要重新勾） |
| 远端删除工具 | 调用返回「没有名为 X 的工具」 |

## 九、硬件选型建议（除了 ESP32、Jetson Orin Nano）

选型标准：① 有稳定的官方 SDK / 工具链；② 能主动出网（心跳可行）；③ 社区大、资料多，用户二次开发成本低；④ 与「企业 AI 工作台」的使用场景能对上。

### 9.1 建议优先补充

| 型号 | 定位 | 为什么值得加 | 接入形态 |
| --- | --- | --- | --- |
| **ESP32-S3 / ESP32-C6** | 现有 ESP32 的升级款 | 官方主推、带 USB-OTG 与 AI 指令加速，是现在新项目首选；和 ESP32 共用 SDK，**几乎零额外成本** | DEVICE 通道 |
| **Raspberry Pi 5 / Pi Zero 2 W** | 单板 Linux | 生态最大、用户最多，企业做边缘网关 / 展示屏最常见；能跑常驻服务 | HTTP + DEVICE 双通道 |
| **Jetson Orin Nano**（首批已定） | 边缘 AI | 官方 2024 年底有 Super 版；「Orin Nano2」按你的意思后续单独做 | HTTP 通道 |
| **RK3588 开发板**（如 Orange Pi 5 / Radxa Rock 5） | 国产边缘 AI | 国产替代主流，NPU 算力够，价格低于 Jetson；国内客户接受度高 | HTTP + DEVICE |
| **Arduino UNO R4 / Nano ESP32** | 入门教育 | 入门门槛最低，适合做「先跑通再升级」的引导路径 | DEVICE 通道 |
| **STM32 系列（如 STM32H7 / NUCLEO）** | 工业 MCU | 工业现场主流，做设备数据采集的客户会问 | DEVICE 通道（需自建联网模组） |

### 9.2 可选（看你的客户群）

| 型号 | 适合谁 | 备注 |
| --- | --- | --- |
| **树莓派 Pico / RP2040** | 教学、轻量控制 | 需外接联网模组，接入成本略高 |
| **ESP8266（NodeMCU）** | 存量设备 | 老设备兼容，不建议作为主推 |
| **NVIDIA Jetson AGX Orin** | 高算力边缘 | 单价高，适合做「高端方案」展示 |
| **工业网关（如有人物联 / 映翰通）** | 工厂现场 | 多为 Modbus/485 转 MQTT，需要额外协议适配 |
| **智能音箱 / 摄像头类成品** | 消费场景 | 通常只能走厂商云，不适合「用户自研固件」的定位 |

### 9.3 我的建议

**首批做 4 个型号**：ESP32（已有）+ ESP32-S3 + Raspberry Pi 5 + Jetson Orin Nano（确认 SKU）。理由：

- ESP32 与 ESP32-S3 共用 SDK，增量成本最小；
- Raspberry Pi 5 覆盖「能跑 Linux、想快速验证」的人群，且 HTTP 通道最好演示；
- Jetson 覆盖「边缘 AI」的高价值场景。

其余型号等首批跑通后再按客户需求补，避免一开始铺太宽、每个都维护不到位。

## 十、开发包（Dev Kit）内容规范

开发包不是「一个 zip 随便塞点东西」，必须能让用户**照着文档在 30 分钟内跑通心跳**。建议固定结构：

```
aiworkin-hardware-<model>-<version>/
├─ README.md                 对接总览：3 步接入（拿令牌 → 填配置 → 烧录/运行）

│  ├─ quickstart.md          快速开始（含截图）

│  └─ tools.md               本型号默认工具清单与参数
├─ sdk/                      二次开发用
│  ├─ <model>/               对应平台的 SDK（ESP-IDF 组件 / Python 包 / Node 包）

├─ firmware/                 直接安装用
```

**「直接安装」路径**：烧录 `firmware/` 里的预编译固件 → 设备连 WiFi → 在页面「添加硬件」拿令牌 → 通过串口/配网页填入令牌 → 心跳上线。

**落地位置**：开发包源码在本仓库根目录 `hardware-devkit/`，按型号分包，打包后即为上表结构：

## 十二、与平台 MCP 的隔离口径（逐条）

| 维度 | 平台 MCP | 硬件 MCP |
| --- | --- | --- |
| 端点 | `/api/v1/mcp` | `/api/v1/hardware/mcp` |
| 服务端名 | `aiworkin-enterprise-mcp` | `aiworkin-hardware-mcp` |
| 工具来源 | 契约派生（`list_operations` 间接调全部业务接口） | 按型号的 `hw_tools` 表 |
| 工具命名 | `describe_capabilities` / `read_data` / `write_data` 等 | `hw__<modelCode>__<toolCode>` |
| 工具清单 | 固定 11 个 | 随型号、随设备、随用户自建动态变化 |
| 授权 | 智能体记忆的「可自动执行的动作」 | 独立的 `hw_tool_grants` |
| 界面 | 开放集成 → MCP Server | 智能硬件 → MCP |
| 后台 | 功能治理 | 智能硬件 → 默认工具 |

**硬保证**：平台 MCP 的 `tools/list` 代码里没有任何读取 `hw_tools` 的路径；硬件 MCP 的 `tools/list` 也不返回任何平台元工具。两者共用的是「JSON-RPC 信封解析」这一层协议代码，业务完全隔离。

| 3 | 设备令牌 vs `ek_` | **独立设备令牌**，只走设备通道，不能调任何业务接口 |
| 4 | 对外 API 通道 | `/api/v1/hardware/**`，用现有 `ek_` Key |
| 5 | MCP 端点 | **独立端点** `/api/v1/hardware/mcp`，与平台 MCP 完全分开 |
| 6 | 用户自建工具可见性 | **仅本人可见可用** |
| 7 | 自建工具上架 | **首版不做**，只在自己账号内用 |
| 8 | 写类工具授权口径 | 沿用平台 MCP 三层：未授权只出草案、无人值守只出草案、`dryRun` 只出草案 |
| 9 | 开发包 SDK | **平台提供可编译 SDK**（ESP32 用 ESP-IDF 组件、Jetson 用 Python 包） |
| 10 | 连接器授权闸 | **一起修**，闸做成通用能力供硬件复用，修法见 8.5 |

> 型号口径说明：官方型号为 **Jetson Orin Nano**（含 2024 年底的 Super 版）。「Orin Nano2」按你的意思作为**后续独立型号**另做，首批不建。

## 十五、风险与边界

- **真机验证成本**：B7 需要实际硬件。没有真机时只能用脚本模拟心跳，**不能**声称「已跑通真机」。
- **固件安全**：设备令牌写进固件存在被提取风险，方案已提供重置与停用；若客户要求更高，需要引入设备证书（mTLS），成本显著上升，不在首版范围。
- **型号维护负担**：每加一个型号就要维护 SDK + 默认工具 + 文档，建议按 9.3 控制首批范围。
- **不改变现有平台 MCP**：本方案对 `/api/v1/mcp` 零改动，避免影响现有 Codex / Claude / Cursor 用户。
