# 浏览器代理「网页采集 → 多维表格」方案（Agent 一句话把页面数据落进表）

> 状态：**设计待拍板**（§十二 决策点未确认前不动代码）。
> 关联底座：`docs/浏览器代理插件升级方案.md`（侧边栏 Agent / 工具网关 / Extract 模式）、`docs/本地Chrome插件RPA控制方案.md`（设备通道 / 会话引擎）。
> 上位设计：`docs/Agent编排与插件能力契约方案.md`——本文是"能力面消化一个具体任务"的样例；大脑如何知道插件能做什么、插件能力要补哪些（K1/K2/K3 就是本文的 harvest），在那份文档的 §二/§三/§四。
> 触发场景（用户原话的示例）：右边开一个百度地图，在插件侧边栏说「在搜索框输入“昆明药店”，把页面上的药店名称、地址、电话收集起来，新建一个多维表格存进去（或指定放进某张表），表头要和字段对上」。本文把它抽象成**六个可泛化能力**，并逐条对齐现有底座。
> 补充口径（用户追问）：示例只是示例——**页面可能是任意站点、可能根本不需要存数据、分支全靠 Agent 对话判断**。对应 C5 与 §五 G/H。

## 一、需求拆解：一句示例背后的六件事

| # | 能力 | 示例里的表现 | 泛化后的等价场景 |
|---|---|---|---|
| C1 | **按语义操作页面** | 找到搜索框 → 输入「昆明药店」→ 触发搜索 | 电商筛选、企业目录检索、后台报表查询条件填写 |
| C2 | **把页面重复条目收成结构化行** | 20 条药店 × 名称/地址/电话 | 商品列表、招聘职位列表、供应商名录、榜单、评论列表 |
| C3 | **结构化落库并自带表头** | 新建表 + 建列（名称/地址/电话）+ 批量写行 | CRM 线索池、选品表、竞品监控表 |
| C4 | **目标可指定、可复用、可定时** | 「放进已有的《药店线索》表」/「每天跑一次」 | 周期性采集、同类站点复用、工作流编排 |
| **C5** | **按意图自适应：不一定存、不一定进表、甚至不一定采** | 「这家店电话多少」只回话不建表；「帮我点进第二个」纯操作无落库 | 任意站点的问答式读取、纯操作、采集后只导出预览、需要时才反问澄清 |
| **C6** | **Agent 必须准确知道插件能做什么** | 「为什么 Agent 不知道可以等元素出现、可以勾选框？」 | 任意任务的编排前提：能力可发现、可协商、可回执、可缺口上报 |

C1 与 C4 的底座已经具备（侧边栏 Agent 的 `act` 循环 + 计划任务 + 工作流）；C5 也**天然免费**——分支就落在既有决策循环的 `reply / question / action / tool` 四个出口里（§五 H），不需要新流程；C6 的落地在上位文档 `docs/Agent编排与插件能力契约方案.md`（本文的 harvest / landRows 就是那份清单里的 K1/K13）；**C2 与 C3 是本文的主战场**，而 C2 对「任意页面」是否成立，集中在 §五 G 的泛化层。

## 三、能力缺口（逐条带证据）

| 缺口 | 证据 | 后果（示例场景下） |
|---|---|---|
| **G1 没有「列表收割」动作** | `RC_ACTIONS` 闭集里没有 harvest（`chrome-rpa.ts:52-63`）；`read` 只取**单个**元素文本（`rpa-executor.js:288-307`），`snapshot` 只给 120 个**可交互**元素 + 正文截断（`:112-149`） | 20 条药店 × 3 字段只能靠多次 `read`，或指望 LLM 从截断正文里猜 |
| **G2 观测正文默认只有 2000 字** | `agentExec({action:"snapshot"})` 未传 `maxChars`（`chrome-agent.js:167`），执行器默认 `|| 2000`、封顶 6000（`rpa-executor.js:439`） | 一个搜索结果页的完整列表通常 >6000 字，条目会**静默丢失**，Agent 还以为抓全了 |
| **G3 会话步数上限 25（≤60）** | `chrome-device.service.ts:57`、`chrome-rpa.ts:343` | 逐条 `read` + 逐行 `DataTable_addRow` 在 30 行时必然超步数，采到一半停在中途 |
| **G4 契约里只有单行写入** | `DataTable_addRow` = POST `/:id/rows`（`automation.ts:2185-2191`）；批量 `createRows` 只挂在机器通道（`data-table-open.controller.ts:48`），**没有对应 operationId** | Agent 通过 `/tool` 只能一行一次调用，与 G3 叠加直接卡死 |
| **G5 多维表格不在插件 Agent 的工具面里** | `PLATFORM_TOOL_DOMAINS = ['rpa','mkt','generated-skills','help']`（`chrome-agent.service.ts:77-85`），而表格端点域是 `data-tables`（`mcpDomainOfPath('/enterprise/data-tables')`，`contracts/src/mcp.ts:157-162`） | 决策提示词根本看不到表格工具；模型只会「把结果念给你听」，不会落库。注：`/tool` 网关按 operationId 通用放行（`rpa-chrome.public.ts:255-276`），所以是**看不见**，不是**调不动** |
| **G6 建表与建列是两次调用，且写行会拒未知列** | `create` 只收 name/description（`data-table.service.ts:206`）；`normalizeData` 遇到未知列键直接报错（`:1153-1185`） | 「表头要和字段对上」这件事现在要靠模型自己串 3~4 次工具调用，任何一次拼错列键就整批失败 |
| **G7 内容脚本只注入顶层框架** | `chrome.scripting.executeScript({ target: { tabId } })` 未开 `allFrames`（`chrome-rpa.js:353`） | 结果区在 iframe 里的站点（地图、部分后台）读不到，需要框架策略或降级 |
| **G8 抽取结果在前端无处安放** | `RpaChrome_extracts`/`saveExtract`（`automation.ts:2912/2920`）在前端**零引用**；`docs/浏览器代理插件升级方案.md:118` 画的「结果卡 + 导出到多维表格」按钮尚未实现 | 用户看不到「抓到了什么、落进了哪张表」，无法核对与二次投递 |
| **G9 没有「陌生站点自动识别列表」的能力** | `harvest` 的提案只接受显式 `item`/`fields` 选择器（本文 §五 A），而 `collector.js:595-650` 的候选选择器是**平台内置、逐站点写死**的；站点技能只沉淀已写好的配方（`chrome-agent.service.ts:113-127`） | 「任意页面都能采」不成立：用户不给选择器就退化成「只有好写的站点能用」，混淆 class 的现代 SPA 直接抓不到 |
| **G10 大脑不知道插件的全部能力（编排前提缺失）** | 决策提示词手写 11 条动作例子（`chrome-agent.service.ts:49-61`）并声明「别的动作一律无效」，而闭集已有 `close_tab` + `act` 的 `check`/`key`/`submit`（`chrome-rpa.ts:53-86`）且后端已放行（`chrome-device.service.ts:717-729`）、`wait` 支持等元素出现（`rpa-executor.js:310-322`）；`chrome` 能力从未过派发门（`assertDispatchable` 只有 distribution/acquisition 两个调用方） | 本方案的第 3 步「等结果容器出现」与收割配方的 `selector` 定位，模型都学不到 → 只能用 `wait ms` 死等；旧插件被派新动作只会三连失败。**能力面不清晰，任何新原语（harvest）都会遇到同一个问题** → 见 `docs/Agent编排与插件能力契约方案.md` §三 |

## 四、总体设计（意图分流 + 五段流水线，三段是新的）

```
 目标（自然语言）
   │
   ▼
 ⓪ 意图分流   Agent 从话里判定「要不要采 / 要不要存 / 存成表还是台账」→ 决定 persist 档与 mode 档（§五 H）
   │          只问不存、纯操作两类在这里就直接走既有 reply / act 出口，下面③④不发生
   ▼
 ① 规划      Agent 判定 mode=extract/act，产出「收割配方」：条目选择器候选 + 字段清单 + 表头 schema
   │          配方优先取自站点技能（site skill），命中就不再让模型猜选择器；没有配方先 discover 探测（§五 G-a）
   ▼
 ② 触达      既有闭集动作：navigate / act(type 搜索框) / act(click) / wait / scroll   ← C1，已具备
   │
   ▼
 ③ 收割      ★新动作 harvest：一条指令把「重复条目 × 字段」收成行数组（含滚动加载、上限、缺失字段如实回报）
   │          观测改为结构化：{ total, items[≤N 预览], missed[], note }，不再依赖正文截断
   ▼
 ④ 落表      ★新工具 DataTable_landRows：一次调用 = 定位/新建表 + 补列（表头→列键）+ 值归一 + 批量写 + 去重 + 回链
   │          产物同时写 RpaChromeExtract 留痕（可选带 session/step）
   ▼
 ⑤ 呈现/复用 侧边栏结果卡（前 N 行 + 「打开表格」）；★新页签 /rpa?tab=status 的「采集结果」列表；
              计划任务定时重跑；工作流按 action 节点编排 harvest→landRows            ← C4，接线即得
```

设计原则：**LLM 只做规划与语义映射，不做逐行搬运**。行数据全程以 JSON 数组在插件→平台→库里直传，既省步数也避免模型抄错数字、电话。

第二条原则（对齐「示例只是其中一个场景」）：**②③④⑤ 全都不是必经环节**。

- ④ 落表是一次**工具调用**，只在目标要求"保存/进表/给我一张表"时才发生；用户只想知道结果，Agent 走已有的 `reply` 分支直接把数据回在对话里（`chrome-agent.js:280-290`），零改动、零落库。
- ③ harvest 也不是必经环节：详情页单字段问答用 `snapshot` + 一次语义抽取即可；纯操作类目标（填表、点按钮）根本不该出现 harvest。
- ① 的配方命中是**加速器**而非前置条件：陌生站点没有配方照样能跑（见 §五 G 的探测与自适应阶梯）。
- 一切分支都由 Agent 从自然语言判断，缺关键信息走已有的 `question` 反问通道；界面上的下拉/按钮只是快捷方式，不是唯一入口。

## 五、关键设计

### A. 新闭集动作 `harvest`（页面列表收割）

契约（`packages/contracts/src/chrome-rpa.ts`）新增动作名与参数 schema：

```jsonc
{
  "action": "harvest",
  "item": { "selector": "div.poi-result",           // 条目根容器
            "candidates": ["...", "..."] },          // 候选列表，全落空报 PAGE_CHANGED
  "fields": [
    { "key": "name",    "candidates": ["h3", ".poi-name"],              "from": "text" },
    { "key": "address", "candidates": [".addr", "[aria-label*=地址]"],  "from": "text" },
    { "key": "phone",   "candidates": [".tel"],                         "from": "text", "optional": true }
  ],
  "region": "#searchResultPanel",     // 可选：只在结果区内查，避开左侧地图画布
  "scroll": { "rounds": 8, "ms": 1200 },  // 懒加载列表边滚边收（照 collector 的 40 轮口径收紧）
  "limit": 200
}
```

执行器返回：`{ url, total, items: [{name,address,phone}], missed: ["phone"], note }`。

要点
1. **纯确定性**，不经 LLM：与 `collector.js` 同一套「候选选择器 + 落空如实报错」范式，字段级 `missed` 比整页失败更有用。
2. **行内值不截断成谜**：每字段单独 `max`（默认 200 字），整包 `limit` 上限 200 行，超限带 `truncated:true`（对齐 `RpaChromeExtract.rows` 的 500 上限与 `createRows` 的 200 行上限）。
3. **密码框与输入值一律不取**（沿用 `collectElements` 的口令护栏，`rpa-executor.js:121-126`）。
4. `snapshot` 的正文预算改为**按模式给**：extract/crawl 会话在 `observe()` 里显式传 `maxChars`（建议 12000，执行器上限同步放开），修掉 G2 的静默丢数据。
5. `read` 顺带补 `mode:"all"`（返回 `querySelectorAll` 的文本数组），给「字段级候选不够、要整段回捞」留个逃生口——但它不是主路径。

### B. 表头 schema：从「字段清单」到「列键 + 类型」

多维表格的列有两条硬规矩（`fieldInput` `:495-537`、`normalizeData` `:1153-1185`）：
- 列键 `field_key` 必须 `^[a-z0-9_]+$`，**中文表头不能直接当列键**；
- 写行时未知列键**直接报错**，必填列缺值**直接报错**。

所以落表前必须有一次「表头 → 列键 + 类型」的规范化，口径与 `/data-table` 的一句话建表完全一致（`DataTable_aiPlanTable`，`data-table-ai.service.ts:412`）：

| 来源 | 做法 |
|---|---|
| 新建表 | LLM 依目标产出 `{name, description, fields:[{name(中文表头), field_key(english), field_type, required}]}`，字段名沿用 harvest 的 `fields[].key`，表头取站点技能里的中文标签 |
| 已有表 | 读现列（`DataTable_get`）→ 用 LLM 做一次「抽取字段 ↔ 列键」映射（`mapping`）；映射不齐的必需列**不静默跳过**，按 §五 E 的文案给出补齐入口 |
| 类型推断 | 纯数字→`number`；`http(s)://`→`url`；含邮箱→`email`；`YYYY-MM-DD`→`date`；`是/否`→`boolean`；其余 `text`（与 `FIELD_TYPES` 八类一致，`data-table.service.ts:12-21`） |

值归一交给既有的 `coerce`（`createRow/createRows` 内部已用），落表工具不自己写一套清洗。

### C. 新工具 `DataTable_landRows`（原子落表，本方案唯一的新写入面）

一条工具调用完成全部写入，替掉「create → addFields → N×addRow」的四段式（G3/G4/G6 的根因）。

**请求**（`POST /enterprise/data-tables/land-rows`）

```jsonc
{
  "rows": [ { "name": "昆明星川药店", "address": "…", "phone": "0871-…" } ],
  "headers": [ { "key": "name", "label": "名称", "field_key": "name", "field_type": "text" } ],
  "target": {
    "mode": "new",                      // new | existing
    "table_name": "昆明药店线索 2026-11-12",
    "description": "浏览器代理自百度地图采集",
    "table_id": 0,                      // existing 时与 table_name 二选一
    "mapping": { "name": "shop_name" }, // existing 时：抽取字段 → 已有列键
    "on_missing_columns": "add",        // add（本人表补列）| reject（只报不改）
    "dedup_by": ["name", "address"],    // 空＝不去重，整批追加
    "dedup_action": "update"            // update | skip
  },
  "source": { "kind": "chrome_extract", "sessionId": 128, "stepIndex": 7, "extractId": 96, "url": "https://map.baidu.com/…" }
}
```

**响应**：`{ tableId, name, url: "/data-table?table=123", created, updated, skipped, addedFields, truncated, warnings[] }`。

**内部实现口径（全部复用现有服务，不新写权限判定）**
1. `target.mode=new` → `DataTableService.create()`（归属 `created_by=user.userId`，`:206`）→ `addFields()`（`:551`，一次建齐全表头）。
2. `target.mode=existing` → `authorize(..., 'create')` 校验新增权（`:388`）→ 需要补列时再 `requireOwner`（**只有归属人能改结构**，非归属且缺列 → 走 §五 E 的拒收文案）→ `writableTables/assertWritable` 同一口径判定列齐不齐（`:291`/`:350`）。
3. 写入：`createRows` 分批（每批 ≤200，`:843`），>200 行自动分批并如实回报 `batches`。
4. 去重：`dedup_by` 命中同值行则 `updateRows`（`:901`）或 skip；整批按 `(tableId, dedup键)` 幂等，**重复投递不产生重复行**——这条是定时重跑（C4）能开起来的前提。
5. 系统行归属：`created_by` 记发起账号，`source.url/sessionId` 存进 `json` 列（如 `_source` 列，类型 `json`），供表格里直接看到「哪一页抓的」。
6. 审计：`identity.audit(userId,'多维表格采集落表', '#<id> <n> 行 · <url>')`，与建表/加列同一份台账风格。
7. 顺带落一条 `RpaChromeExtract`（`schemaNote` 写清「要了哪些字段、怎么抽的」），让 `/data-table` 与采集台账可互相回溯。

**为什么不用「工作流」代替这个工具**：工作流的 `action` 节点已能按任意 operationId 编排（`workflow-catalog.ts:291`），但 harvest 发生在用户本机浏览器、需要一次会话，工作流侧目前**没有浏览器节点**（目录里没有，`docs/…设计方案.md` 的 `maxBrowserActions` 预算是预留位）。落表原语先做成同步工具，工作流补 `browser.session` 节点后再复用同一个 handler，两入口同一条实现（与 `browser-agent-tools.service.ts` 的收口思路一致）。

### D. 把需要的工具精准放进 Agent 工具面（不要整域灌入）

改 `chrome-agent.service.ts:77-85`：在域白名单之外补一份**operationId 精选清单**，只加这五个：

`DataTable_landRows`（写）、`DataTable_list`（读）、`DataTable_get`（读）、`DataTable_aiPlanTable`（读，schema 起草）、`RpaChrome_saveExtract`（写，留痕）。

理由：整域放开会把 27 个 `DataTable_*`（含飞书同步、授权、删表）全塞进每步决策的提示词，`PLATFORM_TOOL_LIMIT=120` 直接被吃掉，成本与误操作面同时上涨。**删表/改授权类动作不进 Agent 工具面**（红线口径同 `MCP_FORBIDDEN_ACTIONS`）。

同时补一条决策提示词规则（`:56-70` 那一段）：「目标要求保存/收集成表格数据时，先收割（harvest）再一次性 `DataTable_landRows`；禁止逐行写入；行数据必须由 harvest 结果直传，不得由模型复述」。

### F. 复用与定时（C4）

- **站点技能存配方**：一次成功后，把 `{item 候选, fields, headers 中文表头, dedup_by}` 写成 site skill（`RpaChrome_saveSkill`，`schema.prisma:2205-2225`），下次同站点直接命中配方，LLM 不再猜选择器；配方漂移时报 `PAGE_CHANGED` 并提示「技能里的选择器需要更新」。
- **计划任务**：`RpaChrome_saveSchedule` 带 `{goal, mode:'extract', 目标表}`，到点走绿灯闸派给在线设备，落同一张表并按 `dedup_by` 增量更新——「每天把昆明药店扫一遍进表」现在就能配。
- **工作流**：`harvest → DataTable_landRows` 与「通知/派单」节点串起来，采集结果直接变成 `MyTask`（`schema.prisma:12186`）或 CRM 线索（`crm_create_lead`，`agent-business-tools.ts:107`）。

### G. 任意页面的泛化机制（这一层决定「示例只是举例」能不能成立）

§五 A 的 `harvest` 若只接受**显式选择器**，就退化成「只有人写好了配方才好用」——陌生页面照样收不到。真正支撑任意页面的是下面三件事，它们是本方案对通用性的主要加码。

**G-a 探测模式 `harvest(mode:"discover")`：让模型从页面结构里选组，而不是凭空写选择器。**

一条指令返回「页面上所有重复出现的元素组」候选，不做任何字段抽取：

```jsonc
{ "action": "harvest", "mode": "discover", "top": 5 }
→ { "groups": [
    { "count": 24, "item": "div > ul.resultList > li",         // cssPath，可当配方
      "signature": "li>a+h4+span+span",                        // 结构指纹（同签名即同组）
      "sampleText": ["昆明星川大药房  北京路 128号  0871-6...", ...],
      "fieldPaths": [ { "i":0, "role":"link", "text":"昆明星川大药房" }, { "i":2, "text":"北京路128号" }, ... ] },
    { "count": 8, "item": "...", "signature": "...", ... } ] }
```

实现要点：按「兄弟节点的结构签名」（标签 + 排序后的 class 词集 + 子节点标签序列 + 子节点数）分组，`count ≥ 3` 才候选，按 `组数 × 文本量 × 特异度` 排序取前 K 个——纯确定性算法，不经模型。

模型拿到候选组后只做两个决定：**选哪一组**、**每个字段对应组内第几个子节点**。第二次 `harvest` 就带着这组 `item/fieldPaths` 全量收，从此该行数据不再经过模型。这样「陌生页面」的成本是**多一次探测步**，而不是「必须有人写配方」。

**G-b 字段三种取法，按站点抗折腾程度递进**

| 取法 | 报文 | 适用 | 抗改版 |
|---|---|---|---|
| 选择器候选 | `{"key":"name","candidates":["h3",".poi-name"]}` | 语义化 class 的站点 | 弱 |
| **标签邻接** | `{"key":"phone","afterLabel":"电话","take":"next"}` | 详情页、后台、企业目录（`电话：xxx` 形态） | **强** |
| **内置模式** | `{"key":"phone","pattern":"phone"}` | class 是哈希的 SPA（地图、电商列表） | **最强** |

`pattern` 首批内置 `phone / mobile / email / url / date / money / idno / postcode`（正则表放在执行器一处、可单测），`take` 支持 `self|next|parent|before|after|line`。这一层是刻意的取舍：**结构混淆的现代前端，稳定抓手是值形态而不是 class 名**；选择器只用来定位「条目边界」，字段一律优先走标签邻接或模式匹配。

**G-c 自适应阶梯：收不到就降级，且降级如实告知**

| 档 | 手段 | 保真度 | 成本 | 何时用 |
|---|---|---|---|---|
| L1 | 站点技能配方（选择器 + 表头） | 高、可复现 | 1 步 | 跑通过的同类站点第二次起 |
| L2 | discover 探测 + 字段取法 | 高、可复现 | 2 步 | 陌生列表页（默认走这里） |
| L3 | 文本 + 语义抽取（一次 LLM 出 rows） | 中，可能漏/串 | 1 次模型调用 | 段落式、非重复结构（榜单文、评论） |
| L4 | 交人工：如实说明「页面结构受风控/在框架内/需登录」+ 停止 | — | — | 前三档都落空 |

L3 是把 `snapshot` 正文预算放开（§五 A-4）后按 L2 的表头做一次结构化输出；它**必须显式标注"语义抽取，未逐条核对"**，且落表时写进 `warnings[]`，不能与 L1/L2 的确定性结果混为同一种可信度。

沉淀闭环：L2/L3 第一次成功后，把「组签名 + 字段取法 + 表头」写成站点技能（§五 F、N6），下次自动升到 L1；配方失效时报 `PAGE_CHANGED` 并提示技能里的配方需要更新——**通用性的钱只花第一次**。

### H. 意图分流与持久化档位（「用户并不一定要存数据」）

| 用户说法 | Agent 分支 | 持久化 |
|---|---|---|
| 「这个页面里有哪些药店？」 | `harvest` → `reply`（把行数组摘要回在对话里） | **不落库**（`persist:none`） |
| 「搜昆明药店，把名称地址电话给我」 | 触达 → harvest → 结果卡（可复制/JSON） | 默认仅会话留痕 |
| 「新建个多维表格存进去」 | → `DataTable_landRows(mode:new)` | `persist:table` |
| 「放进《药店线索》那张表，别重复」 | → `landRows(mode:existing, dedup)` | `persist:table` |
| 「把这些做成线索」 | → 逐条 `Crm_createLead`，或先 `landRows` 再整表转 | 落 CRM，不经 `persist` 档 |
| 「每天这个点跑一次进那张表」 | 计划任务 + 同一 landRows（幂等靠 dedup） | `persist:table+scheduled` |
| 「帮我把这个后台的月度报表导出」 | 纯 `act` 操作，不出现 harvest | 无 |
| 「这个页面是干什么的」 | `snapshot` → `reply` | 无 |

`persist` 作为落表/落台账入参的一档（`none | extract | table`），缺省由目标语义决定，**默认 `none`**：只有话里出现"存/记/放进表/导出来/给我一张表"才升档。三档含义：

- `none`：只在对话与结果卡里回，不写任何业务表；
- `extract`：写 `RpaChromeExtract` 采集台账（可回放、可事后补投递），不动用户表格；
- `table`：走 §五 C 的 `landRows`。

需要如实说明的边界：**会话步骤与截图留痕（`RpaChromeStep`/`screenshotKey`）是审计底座，任何档位都关不掉**——「零痕迹采集」不在本方案承诺范围内；能选的是"数据要不要落成你的表/台账"。

## 十一、工作量与风险

- **量级**：D2 + D3 是核心（约占总量的六成），都是「新 primitive + 复用既有服务」，不动会话体系、不新建表。
- **风险 1（最高）：选择器脆弱**。地图/搜索类页面改版即失效。缓解：候选选择器 + site skill 配方 + `PAGE_CHANGED` 不静默 + 官方 API 兜底（N8）。
- **风险 2：iframe**。当前只注顶层框架；跨源框架需 `allFrames` 与聚合策略，改动小但覆盖面要实测。
- **风险 3：成本与步数**。逐行写入的老路一旦被模型学会就会打爆 `maxSteps`；决策提示词必须硬写「禁止逐行写、行数据直传」。
- **风险 4：数据合规**。批量抓联系方式的边界（站点条款、个人信息保护）需要在授权与人工确认上留闸（N9）。
- **风险 5：并行会话冲突**。迁移号、`frontend/src/app/rpa/*`、`docs/*` 常有其他会话在写，动手前先看 mtime。
- **风险 6（结构性）：能力目录与实现漂移**。今天已经漂了三处（提示词少 4 个动作、`chrome` 无派发门、采集平台声明比实现宽）；本方案再加 harvest/landRows 只会漂得更快。缓解：D0 先行 + `scripts/verify-extension-caps.mjs` 守卫进 CI（详见上位文档 §五 治理与 §四 S1–S5）。
