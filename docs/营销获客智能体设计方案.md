# 营销获客智能体（AI 获客）设计方案

> 版本：v0.1（方案，待评估）
> 日期：2026-11-07
> 参考包：xiaobei（`TeamWiseFlow/xiaobei`，本地解包 `xiaobei-master`；重点读 `crews/sales-cs`、`crews/main`、`skills/*`、`awada`、`docs/sales-cs-bootstrap.md`）
> 要求：只借鉴需求与机制，不抄代码；全部基于本系统契约优先 / 组织隔离 / 统一 AI 网关 / 积分计费 / 平台机制底座重写；入口放在「工作台 → 营销工具」。
> 结论先行：**不新建第二套 IM、浏览器、账号和知识体系**。新增一个 `acquisition` 模块承载「社媒线索雷达 + 触达编排 + 客户档案 + 销售剧本 + 跟进计划 + 接待质检 + 获客看板」；AI 接待复用现有服务台，客户数据复用 CRM，浏览器动作复用 AIPDD Enterprise 插件，AI 能力复用统一网关，计费复用积分科目。

## 一、参考包分析：xiaobei 是什么，值得借鉴什么

### 1.1 它是一个「跑在本机的获客团队」，不是一个网页工具

xiaobei 本体是 OpenClaw 上的多 crew（智能体团队）发行版：一个常驻 Gateway + 微信通道（awada）+ 一组专家包与技能，用户通过微信指挥。

| Crew | 角色 | 获客相关性 |
|---|---|---|
| `main` | 小贝：新媒体运营 / 创业伴侣，负责任务路由、业务知识库、内容与发布 | 内容获客、线索来源、知识治理 |
| `sales-cs` | 对外销售客服，绑微信/企微/飞书通道 | **AI 销售接待、客户档案、跟进** |
| `it-engineer` | 运维排障、配置与调度 | 定时任务与通道运维（本系统由平台承担） |
| `content-producer` | 视频/视觉生产 | 内容素材（本系统已有内容创作与分发，不重复） |

获客能力并不只在一个 crew 里：**发现**来自 `expert-bd` + 各平台 hunter + `smart-search`，**触达**来自评论/私信/邮件/表单填写，**接待与跟进**来自 `sales-cs`，**情报**来自 `expert-osbi`，**内容引流**来自 `main` 与各平台专家包。

### 1.2 把获客链路拆成 6 个能力（带源码落点）

| # | 能力 | xiaobei 落点 | 关键机制（值得学的地方） |
|---|---|---|---|
| 1 | 潜客发现 | `expert-bd`；`xhs-hunter` / `douyin-hunter` / `tiktok-hunter` / `kuaishou-hunter` / `x-hunter` / `weibo-hunter` / `wx-mp-hunter`；公共 `smart-search`；`db/bd_record.db` | 按平台写「站点规则 + 搜索 URL + 登录态」，搜索结果只当线索、原文必须回页面核实；每站默认两次搜索预算，不偷偷扩搜 |
| 2 | 触达 | 评论区回复/私信/邮件/点赞关注；`web-form-fill`；`proactive-send` | 主动消息与普通回复分开；发送后必须查回执（`queued/running/submitted` ≠ 已送达）；`unknown` 先对账不重发 |
| 3 | AI 销售接待 | `crews/sales-cs/AGENTS.md`、`SOUL.md`、`IDENTITY.md`、`USER.md` | 会话主流程强制：读客户状态 → 识别意图 → **先更新档案再回复** → 最后统一输出；纯文本（微信不渲染 Markdown） |
| 4 | 客户档案与跟进 | `customer-db`：`cs_record`（peer 主键、business_status、purpose、prompt_source、club_in）+ `follow_up`（pending→sent_once→completed） | 两个标识符分离（`peer` 用于库，`user_id_external` 用于渠道路由，互不反推）；延迟购买意向按「时间映射表」建跟进任务；回执账本防重复 |
| 5 | 情报 | `expert-osbi`；`db/info_record.db`；`osbi/` | 竞对/市场/公开直播调研走独立专家包，与「找人」分域 |
| 6 | 治理 | `DECLARED_SKILLS`、`ALLOWED_COMMANDS`、external crew 约束、`business_knowledge` 软链 | 对外 crew 默认 deny，只放行声明式脚本；不提供原子 SQL；禁止自我修改；敏感事项升级人工；业务知识由 main 统一维护 |

### 1.3 五个真正值得借鉴的机制（设计思想，不是功能清单）

1. **一个客户一行档案 + 两个标识符分离**
   `peer` 是库内主键（由系统 hook 从 senderId 归一），`user_id_external` 是渠道原始路由 ID。写库只用 `peer`，发送只用 `user_id_external`，**不用其中一个反推另一个**。
   → 因果链：社媒/微信的显示名会变、不同账号可能重名；混用会导致「发给错的人」或「同一个人建了两份档」。

2. **先更新、再回复；工具在前、回复在后**
   任何会改状态的 turn 不得包含面向客户的文本；所有工具执行完，最后统一输出一条完整回复。
   → 因果链：先回复后写库，中途失败就出现「客户以为约好了、系统里没记录」；分多条输出会刷屏。

3. **延迟购买意向 → 跟进任务状态机**
   `pending → sent_once → completed`，带 `follow_up_at / reason / context_summary / sent_text / retry_count`；客户说「明天/下午/等工资」有时刻映射表；发送回执单独记账，最多两轮，未确认不重发。
   → 因果链：不做状态机就会重复轰炸；不做回执核对就会「以为发了」或「发两次」。

4. **销售剧本是文件，也是数据**
   `AGENTS.md`（流程）＋`SOUL.md`（角色/边界/升级人工）＋`IDENTITY.md`（自称）＋`USER.md`（客户视角与输出格式）＋`business_knowledge.md`（产品/价格/红线，由 main 维护、其他 crew 软链只读）。
   → 因果链：话术散落在提示词里就无法审计、无法版本化、无法解释「为什么这个客服这样说」。

5. **对外角色的最小权限与失败关闭**
   声明式技能清单 + 命令白名单（无通用解释器）+ 无原子 SQL + 禁止自我修改 + 明确升级人工条件 + 业务知识只读软链。
   → 因果链：对外智能体一旦能任意执行命令或改自己的规则，一次提示注入就能变成「用公司账号群发/删库」。

### 1.4 不照搬的部分（以及本系统怎么处理）

| xiaobei 的做法 | 本方案的处理 | 原因 |
|---|---|---|
| 本机常驻 Gateway + Camoufox 反检测浏览器 | **服务端不装浏览器**；采集与触达在用户的 AIPDD Enterprise 插件里执行 | 本系统硬约束：不给服务器装 Chrome/渲染服务；账号凭据不出本机 |
| SQLite 多库（`cs_record` / `bd_record` / `info_record` / `published_track`） | MySQL + Prisma；线索进 CRM / 多维表格，发布台账复用 distribution | 一体化系统不引入第二套存储与统计口径 |
| crew 目录、`AGENTS.md` 软链、workspace 文件 | 「销售剧本 Playbook」数据化 + 版本快照 + 知识库绑定 | 需要多租户隔离、版本审计与后台可视化 |
| awada 微信通道（企业微信承载） | 复用 `im`、腾讯企点·企微运营、服务台自定义渠道 | 已有官方通道与合规链路，不重复接 |
| 全平台采集/发布 + 视频制作 + DNA 复刻 | 本期不做视频/DNA；采集平台与现有分发渠道对齐并留适配器位 | 控制范围；内容生产已有专门模块 |
| `expert-ir`（投资人关系） | 不在本期，线索类型预留 `INVESTOR` | 与营销获客主链路不同 |

## 三、设计原则与硬约束（实现前逐条核对）

1. **契约优先**：新增 `packages/contracts/src/acquisition.ts`（zod + `acquisitionEndpoints`），汇总进 `endpoints.ts`；`pnpm --filter @enterprise/contracts build` 后再接后端。前端只经 `endpoint(endpoints.Acquisition_xxx)` 调用。
2. **组织隔离**：所有表带 `(orgType, orgUserId)`；服务经 `HrmScopeService.resolve(user)` 取 scope，与 `mkt/geo/seo` 一致。提升到 CRM 时按**操作人**的 `ownerUserId` 落 CRM（CRM 是用户域），并写 `AcqProfile.crmLeadId` 建立双向引用。
3. **统一 AI 网关**：全部调用走 `AiGateway`（`aiChat/tryChat/aiJson`），模块名 `acquisition`；**缺 Key 不抛穿业务链路**，评分/草稿/接待走规则式兜底；只有用户主动点「AI 生成」才 `requireModel` 抛引导性错误。
4. **浏览器动作只在客户端**：服务端只下发任务、接收回执；不装浏览器、不代登录、不存平台 Cookie/密码。
5. **凭据不出本机**：插件复用浏览器已登录会话；服务端不接收平台账号密码。
6. **对外动作先审后发**：草稿 → 内容安全（`PublishReviewService.guard`）→ 人工确认（可配自动）→ 执行；频控、冷却期、黑名单、退订优先于「多发」。
7. **客户域名归客户**：线索落地页、分享链接、退订链接一律用客户自有域名与证书；只在客户域名池内切换。
8. **计费只新增科目**：新增 `acq_*` 科目，默认免费额/可用额度；**不改变任何既有扣费**；没配置科目时只记用量不扣分。
9. **全链路留痕**：证据快照、AI 结论快照、发送回执、审核记录、导出记录都可追溯。
10. **失败关闭 + 诚实标注**：没 AI Key、没装插件、平台改版、登录失效 → 明确状态与下一步，不伪装成功。
11. **单飞与幂等**：同一监控源同时只跑一个批次；同一线索同一渠道 7 天冷却；发送回执 `unknown` 先对账，不自动重发。
12. **可整体关闭**：功能目录开关 + 组织级 AI 主开关；关闭即后端拦截，不只隐藏菜单。

## 四、总体架构

### 4.1 产品结构

```
工作台 → 营销工具（/marketing-tools）
└── 卡片「AI 获客」（整卡可点）
    ├── 线索雷达      监控源 / 采集批次 / 线索池 / 证据详情
    ├── 触达任务      草稿审核 / 发送队列 / 回执对账 / 频控与黑名单
    ├── 客户档案      销售语义 / 时间线 / 跟进计划 / 提升 CRM
    ├── 销售剧本      角色 / 边界 / 开放话术 / 异议处理 / 知识绑定 / 版本
    ├── 接待质检      会话评分 / 问题清单 / 改进建议 / 批量复盘
    └── 获客看板      漏斗 / 渠道 / 合规 / 成本
```

插件安装说明放在卡片内（与「多平台内容分发」同款面板），不新开菜单。

  ├─ outreach.service.ts            草稿、审核、频控、队列、回执对账
  ├─ profile.service.ts             销售档案、事件时间线、CRM 提升/同步

### 4.3 四条主数据流

**A. 发现**
`监控源(定时)` → `采集批次` → 插件按平台规则打开搜索/话题/评论区 → 回传 `{url, 正文摘录, 作者公开信息, 互动数, 时间}` → 服务端规范化、去重 → AI 意图评分 → `AcqLead + AcqLeadEvidence` → 进入线索池/多维表格。

**B. 触达**
筛选线索 → 生成 1–3 版草稿（剧本 + 证据 + 品牌上下文）→ 内容安全 + 人工确认 → 入 `AcqOutreachTask` 队列 → 插件领取 → 在已登录页面执行 → 回传 `submitted/succeeded/failed/unknown` → 服务端对账 → 回写线索状态与档案时间线。

**C. 接待**
客户回复（服务台 widget/自定义渠道、企微、邮件）→ 服务台既有入站管线 → 注入「剧本 + 知识 + 档案」→ 意图分流 → 回复 → 结构化抽取（purpose/source/预算/时间/决策角色）→ 更新 `AcqProfile`；出现延迟购买意向则建 `AcqFollowUp`。

**D. 跟进**
调度器扫描到期跟进 → 生成不超过三句话的跟进文本 → 走原渠道发送 → 回执账本 → `pending → sent_once → completed`（最多两轮，客户回复即完成）。

### 4.4 模块边界（谁负责什么）

| 事项 | 归属 |

| 客户/商机/合同/回款 | `crm`（acquisition 只读引用 + 提升入口） |
| 会话收发、AI 模式、客服分配、FAQ | `service-desk` |
| 企微官方能力（活码/群发/会话存档质检） | `tencent-qidian` |
| 企微/飞书成员与消息同步 | `im` |
| 内容生产与分发 | `content` / `distribution` |

| 浏览器执行 | `extensions/aipdd-enterprise` |
| AI 模型与计量 | `ai` + `points` |

## 五、功能详细设计

### 5.1 线索雷达（Prospecting Radar）

**监控源（AcqSource）**

| 字段 | 说明 |
|---|---|
| 平台 | 首期：小红书、抖音、知乎、微博、B 站、微信视频号（公开页）、公众号（公开文章）；预留 TikTok / X / 快手 |
| 查找方式 | 关键词 / 竞品名 / 话题标签 / 指定账号评论区 / 指定笔记或视频的评论 |
| 过滤 | 地域词、时间窗（近 7/30 天）、最少互动数、排除词、排除已成交客户 |
| 节奏 | 手动 / 每日 / 每周；`activeHours`；单源单日条数上限（默认 200） |
| 平台会话 | 由用户在浏览器登录，插件复用；服务端只记「上次执行结果」 |

**采集批次（AcqRun）**
每次执行生成一行：`startedAt/finishedAt/status(claim 单飞)/stats(扫描数/新增/重复/被过滤)/error`。插件掉线或平台改版时批次为 `PARTIAL` 并给出原因，**不把空结果当成功**。

**一条线索（AcqLead）的判定**
- 平台 + 平台用户标识相同 → 同一人（跨批次合并，保留最早来源）；
- 证据 URL 相同 → 同一条内容（去重）；
- 同一人不同内容 → 多条证据，`intentScore` 取最高并记录「证据数」；
- 已提升 CRM 的线索再次出现 → 只追加证据与时间线，不重复建档。

**AI 意图评分（0–100，输出 JSON）**

| 维度 | 分值 | 判定依据 |
|---|---|---|
| 需求明确度 | 30 | 是否直接说「求推荐/多少钱/怎么买/有没有能做 X 的」 |
| 预算信号 | 20 | 提到预算、报价、对比价格、要方案 |
| 时间信号 | 20 | 「最近/这周/下个月/急着用」 |
| 决策角色 | 15 | 本人决策 / 帮公司问 / 同行打听 |
| 匹配度 | 15 | 与品牌上下文、产品能力、地域/行业是否匹配 |

输出：`{score, level(HOT/WARM/COLD), tags[], reason, opening, risk}`。`reason` 必须引用证据原文片段；`opening` 是一句自然的开场（不承诺价格）。**证据正文按不可信内容包裹后送模型**（防提示注入）。

无 AI Key 时规则式兜底：关键词命中表 + 互动阈值 + 来源权重，`mode=rule` 明确标注。

**线索池操作**
筛选（平台/分数/标签/时间/状态）、批量打标、批量提升 CRM、写入多维表格（复用 `DataTableService`，逐行写入、按 `platform+userId` 去重）、导出（复用 `ExportJob`）。

### 5.2 触达编排（Outreach）

**触达类型（首期）**

| 类型 | 执行位置 | 说明 |
|---|---|---|
| 评论回复 | 插件在内容详情页 | 只回复与线索相关的公开评论；同一内容只回一次 |
| 私信 | 插件在平台私信页 | 首条必须人工确认；平台未开放私信则降级为「复制话术」 |
| 邮件 | 服务端阿里云邮件推送 | 已有通道；走模板 + 变量 |
| 企微好友/群发 | 腾讯企点官方接口 | 已有能力；不重复实现 |

**草稿生成**
输入：剧本 + 线索证据 + 品牌上下文（`MktContext`）+ 客户档案（若有）+ 渠道限制（字数/是否允许链接）。
输出：1–3 版不同角度（共鸣式/直给式/提问式），每版带「为什么这样说」。用户可编辑后保存。

**审核与风控（顺序不可颠倒）**
1. 退订/黑名单/竞品员工/已成交客户 → 直接拦截；
2. 频控：同账号每日评论 ≤ 20、私信 ≤ 30（可配）；同线索冷却 7 天；同内容不重复评论；两次操作间隔 20–60 秒随机；
3. 内容安全：`PublishReviewService.guard(text)`，命中即拒绝并记录；
4. 人工确认（默认开启；可按渠道关闭，但私信首条始终人工）；
5. 入队。

**执行与回执**
插件领取任务时带一次性令牌（绑定用户 + 5 分钟有效 + 仅 `pull/report` 两个动作）。回执状态：`submitted / succeeded / failed / unknown`。**`unknown` 先查询原操作，不新建任务重发**；`failed` 先查是否已部分发送。只有 `succeeded` 才把线索状态推进为「已触达」。

### 5.3 客户档案（Sales Profile）

不替换 CRM，而是给「有对话的人」加一层销售语义。主键二选一：`crmLeadId`（已提升）或 `channelPeerKey`（尚未提升的入站客户）。

| 字段 | 取值 | 来源 |
|---|---|---|
| `businessStatus` | `free / engaged / qualified / customer / churned` | 对话抽取 + CRM 阶段同步 |
| `purpose` | 客户主要用途（自由文本 + 标签） | 对话抽取 |
| `source` | GitHub/公众号/视频号/小红书/朋友推荐/投放/其他 | 对话抽取 + 线索来源 |
| `budget / timeline / decisionRole` | 预算区间 / 时间窗 / 决策角色 | 对话抽取，可为空 |
| `objections` | 顾虑清单（价格/效果/迁移/合规） | 对话抽取 |
| `healthScore` | 0–100 | 互动频次、回复时延、意向变化、逾期跟进 |
| `ownerUserId` | 跟进人 | 组织内成员 |
| `nextActionAt` | 下一步时间 | 跟进计划 |
| 时间线 | 线索来源→每次触达→每次会话→每次跟进→阶段变化 | 事件表 |

映射：`free→NEW`、`engaged→FOLLOWING`、`qualified→INTERESTED`、`customer→SUCCESS`、`churned→FAIL`；反向由 CRM 阶段变化回写档案。

### 5.4 销售剧本（Playbook）

把 xiaobei 的 `AGENTS/SOUL/IDENTITY/USER + business_knowledge` 拆成可版本化的数据：

| 区块 | 内容 |
|---|---|
| 角色 | 对外自称、性格、能做什么/不做什么 |
| 目标 | 本剧本的推进目标（了解需求/约演示/进群/成交） |
| 语气与格式 | 纯文本、短答优先、表情克制、链接数量限制 |
| 开放话术 | 3–5 个自然开场，按线索类型分组 |
| 异议处理 | 价格/效果/信任/迁移/合规，每个给「承接→结论→证据→下一步」 |
| 边界 | 不承诺价格/时效/赔付/定制；不虚构资质与案例 |
| 升级人工 | 退款、投诉、合同条款、无法确定的问题 |
| 知识绑定 | `kb` 知识库 id 列表 + 服务台 FAQ id 列表（只读引用） |
| 产品口径 | 引用 `MktContext` 与产品资料，不内联复制价格表 |

**版本与生效**：保存即生成不可变版本；发布后新会话使用新版本，进行中的会话固定「开始时的版本」，审计可查。剧本变更必须由组织管理员操作，AI 不能自我修改。

**组装顺序（优先级从高到低）**：平台安全约束 → 剧本边界 → 知识（KB/FAQ）→ 客户档案 → 最近会话。超出知识范围一律「不确定 + 转人工」，不编造。

### 5.5 AI 销售接待（复用服务台）

不新建聊天系统，在 `ServiceDeskService` 的提示词组装处增加两个可选项：`playbookId` 与 `profile`。

- **模式**：沿用 `OFF / CANNED / SUGGEST / AUTO / BOT`；销售场景推荐 `AUTO`（可转人工）或 `BOT`（纯 AI，需剧本边界完整）。
- **入站渠道**：服务台站点 widget / 自定义渠道、企微（企点或 IM 通道）、邮件。渠道会话键与 `AcqProfile.channelPeerKey` 对应。
- **每轮流程**：读档案 → 识别意图（了解/试用/购买/付款/售后/抱怨/其他）→ 按剧本回复 → 抽取结构化信息 → 写档案与时间线 → 必要时建跟进。
- **合规**：不承诺价格/时效/赔付；投诉先道歉并记录；敏感争议转人工；所有对外文本过内容安全（可按组织配置）。
- **失败降级**：模型不可用 → 回退 `SUGGEST`（给人工建议）或固定文案；不空回复、不把框架错误文本发给客户。

### 5.6 跟进计划（FollowUp）

**触发条件（同时满足）**：客户已表达购买意向（问价/怎么买/对比版本），且明确要等一段时间。

**时间映射（与 xiaobei 一致）**

| 客户说法 | `followUpAt` |
|---|---|
| 明天 | 次日 10:00 |
| 后天 | 两天后 10:00 |
| 下午 | 当天 14:00（已过 13:00 则次日 14:00） |
| 晚上 | 当天 19:00（已过 18:00 则次日 19:00） |
| 下周 | 7 天后 10:00 |
| 等工资 / 月底 | 5 天后 10:00 |
| 过两天 / 几天后 | 3 天后 10:00 |
| 晚点再谈 / 稍后 | 当天 14:00（已过 13:00 则次日 10:00） |
| 具体日期/时间 | 按客户说的时间，未指明则 10:00 |

**状态机**：`pending → sent_once → completed`；客户明确说「不用跟了/我自己买」或主动回复 → `completed`；同一客户新建前先取消旧 `pending`。

**调度**：`AcquisitionScheduler` 每 5 分钟扫描到期；仅在 `activeHours` 内发送；最多两轮；发送前重新检查黑名单与退订。

**回执账本（AcqFollowUpReceipt）**：记录发送意图、文本、账号、`operationId/messageId`、状态。有意图无回执先对账；不覆盖旧账本；账本不可读则停止该条发送。

### 5.7 接待质检（QC）

对会话按五个维度评分（各 20 分）：需求识别、信息完整、边界合规、推进节奏、情绪处理。
输出：总分、维度分、问题清单（引用原话）、改写建议、培训要点。批量维度：客服/剧本/渠道/时间段。
结论写入快照表（`AcqQcReview`），保留「当时的判断」，不随会话后续变化而改写。

### 5.8 获客看板（Dashboard）

| 区块 | 指标 |
|---|---|
| 漏斗 | 采集曝光 → 线索 → 已触达 → 已回复 → 商机 → 成交 |
| 渠道 | 平台/监控源/剧本/客服的线索量与转化率 |
| 触达合规 | 发送量、成功率、失败原因、退订/拉黑、内容安全拦截 |
| 跟进 | 到期数、已发、完成、逾期、第二轮占比 |
| 成本 | AI 调用次数与积分、触达次数、单线索成本 |
| 导出/分享 | 复用 `ExportJob`；看板可生成 `PublicShare` 只读投影 |

### 5.9 与既有工具的联动

1. **内容分发回流**：distribution 发布日志里的作品 URL 可作为「评论监控源」，评论者进入线索池。
2. **活码引流**：活码来源渠道写入 `AcqProfile.source`，扫码后进服务台会话。
3. **达人建联**：`connections` 的达人写入线索池，类型 `KOL`，走合作邀约剧本。
4. **大数据名单**：批量导入为 `LIST` 类型线索（无社媒证据），走邮件/外呼，不伪造社媒评分。
5. **lead-prospecting**：Google 线索可一键并入同一线索池（`source=GOOGLE`）。
6. **营销技能库**：开场/异议处理/复盘作为可运行技能，产出进 `MktArtifact`，可一键保存为剧本片段。
7. **CRM**：提升线索 → 建 `CrmLead`（按操作人 `ownerUserId`），同步阶段与跟进记录。
8. **BI**：看板数据可作为数据集接入，不另建报表引擎。

### 5.10 浏览器插件扩展（AIPDD Enterprise v1.3.0）

插件从「只发布」扩成「发布 + 采集 + 触达」，权限不扩张（仍为 `tabs/storage/<all_urls>`）。

**新增脚本**
- `collector.js`：目标平台搜索页/话题页/详情页/评论区，按页面规则抓取结构化条目；
- `outreach.js`：在评论/私信页面填入文本并提交，逐步校验提交结果。

**页面通信协议（在现有 `aipdd-page` / `aipdd-extension` 基础上扩展）**

```text
页面 → 插件  { source:'aipdd-page', type:'collect', jobId, payload:{ platform, mode, query, urls[], limits } }
插件 → 页面  { source:'aipdd-extension', type:'accepted' | 'harvest' | 'result', jobId, items[], error }
页面 → 插件  { source:'aipdd-page', type:'outreach', jobId, payload:{ platform, action, targetUrl, text, maxPerHour } }
插件 → 页面  { source:'aipdd-extension', type:'outreach-result', jobId, status, receipt }
```

**执行约束（写进插件）**
- 串行执行，随机间隔 20–60 秒；单账号每小时上限由服务端下发；
- 用户可随时暂停/停止；停止后不再领取新任务；
- 不读取/导出 Cookie，不注入非目标域，不绕过验证码；遇到登录墙/验证码/风控页 → 停止并回报 `NEED_LOGIN`；
- 失败保留标签页，人工可接手；结果未知不重试。

**版本同步**：`extensions/aipdd-enterprise/README.md`、`manifest.json`、`backend/src/distribution` 的 `EXTENSION_INFO` 与下载文件名、`verify-distribution.mjs` 断言四处一起改。

## 八、后端实现要点

1. **装配**：`http/services.ts` 中在 `crmService`、`serviceDeskService`、`mktService`、`publishReviewService` 之后构造 `acquisitionController`，避免构造顺序问题。
2. **调度**：`AcquisitionScheduler`（进程内定时器，仿 `PointsDailyScheduler`）：
   - 每 5 分钟：到期跟进 + 回执对账；
   - 每分钟：检查 `AcqSource.nextRunAt`，到点生成 `AcqRun`（用唯一约束/状态 CAS 保证单飞）；
   - 每 10 分钟：把超时 `CLAIMED/RUNNING` 批次标 `PARTIAL`；
   - 环境开关 `ACQ_SCHEDULER_DISABLED` / `ACQ_SCHEDULER_TICK_MS`。
3. **AI 调用**：统一 `this.ai.tryChat({ userId, module: 'acquisition', action, ... })`；评分用 `aiJson` + 严格 schema 校验，解析失败降级规则式；不重试付费步骤。
4. **内容安全**：触达发送前 `publishReview.guard(finalText)`；未配置时返回 `off` 并放行主链路（只告警一次），不阻断。
5. **事件**：`acquisition.lead.created`、`acquisition.outreach.sent`、`acquisition.followup.due`、`acquisition.profile.stage_changed` 写 `WebhookOutbox`，客户系统可订阅。
6. **幂等**：线索唯一键 `(org, dedupeKey)`；证据唯一 `(leadId, url)`；触达发送前检查「同线索同渠道最近 7 天成功记录」；插件回执按 `jobId` 去重。
7. **限流**：按用户 × 组织双维（复用 §5.7 安全口径）；插件拉任务每次最多 5 条；导出/批量提升有每分钟上限。
8. **审计**：发送、导出、删除、剧本发布、提升 CRM 全写 `auditLog`（谁、何时、对谁、做了什么）。
9. **提示注入防护**：证据正文、客户消息都按「不可信内容」包裹（明确分隔 + 指令优先级说明）；模型输出只作为建议，不直接执行工具。

## 十、安全、合规与治理

| 风险 | 措施 |
|---|---|
| 平台反爬/账号风控 | 只读公开页面；串行 + 随机间隔 + 日上限；验证码/登录墙立即停；用户自行登录并承担账号风险提示 |
| 触达骚扰/广告法 | 先审后发；频控 + 冷却 + 黑名单 + 退订；不群发同文；不承诺效果/价格 |
| 个人信息保护 | 只采集公开可见信息；最小化存储；证据保留期可配；导出需权限并审计；展示脱敏手机号/微信号 |
| 提示注入 | 证据与客户消息包裹为不可信内容；模型不能直接触发发送/导出；工具调用走白名单 |
| 越权 | 全部按 `(orgType, orgUserId)` 过滤；跨组织 id 一律 404；插件令牌绑定用户与动作 |
| 插件供应链 | 插件包走 §5.9 审查流程（确定性预检 + AI 审查），通过才可下载；服务端不执行包内脚本 |

| 数据删除 | 删除线索级联证据/事件；删除档案保留匿名统计；导出文件到期清理 |
| 组织级总闸 | 功能开关 + AI 主开关；关闭后接口返回明确错误，前端不渲染入口 |

## 十三、验收标准

### 13.1 功能主线（必须逐项走通）

1. 新建小红书关键词监控源 → 插件采集 → 线索池出现带证据的线索 → AI 评分有理由 → 提升为 CRM 线索。
2. 选中线索生成私信草稿 → 内容安全通过 → 人工确认 → 插件发送 → 回执 `succeeded` → 线索状态变「已触达」→ 7 天内同渠道不可再发。
3. 客户回复进入服务台 → AI 按剧本接待 → 档案写入 `purpose/source` → 客户说「明天再说」→ 生成次日 10:00 跟进 → 到期发送 → `sent_once`。
4. 剧本修改并发布 → 新会话使用新版本 → 历史会话仍显示旧版本。
5. 单条会话质检 → 五维评分 + 问题原话 + 建议 → 看板漏斗与渠道数字对得上明细。

### 13.2 边界与失败

- 未配 AI Key：评分/草稿/接待走规则或固定文案，界面明确 `规则模式`，主链路不中断。
- 未装插件：采集与触达显示「未连接插件 + 安装指引」，不产生假成功。
- 平台登录失效/验证码：批次 `PARTIAL` 或任务 `NEED_LOGIN`，停止后续动作。
- 回执 `unknown`：进入「待对账」，不自动重发；人工确认后才可继续。
- 跨组织访问：一律 404；导出未授权：403。
- 功能关闭：接口拒绝且前端不渲染卡片。

## 十四、风险与开放问题

| 风险 | 影响 | 应对 |
|---|---|---|
| 平台 DOM/接口频繁改版 | 采集/触达失败 | 选择器与页面规则版本化；失败保留页面；批次标记 `PARTIAL` |
| 平台规则与账号风险 | 封号/限流 | 低频、串行、人工确认、用户自担提示；不提供「全自动养号」 |
| 触达合规（广告/个人信息） | 法律风险 | 先审后发、退订、黑名单、保留证据与审计；默认保守限额 |
| AI 编造承诺 | 商誉/纠纷 | 剧本边界 + 知识约束 + 质检 + 「不确定转人工」 |
| 线索质量与噪声 | 销售反感 | 意图评分 + 证据链 + 阈值过滤；支持「不感兴趣」反馈训练规则词表 |
| 插件权限过大 | 安全质疑 | 权限不扩张；不读 Cookie；令牌短时绑定；包审查 |

**需要用户确认的开放问题**

1. 首期平台范围是否就按「小红书 / 抖音 / 知乎 / 微博 / B 站 / 视频号 / 公众号」？TikTok / X / 快手是否首期就要？
2. 触达是否允许「审核后自动发送」，还是首期一律人工点发送？（方案默认：评论可自动、私信首条人工）
3. 证据原文保留期默认 180 天是否合适？
4. AI 接待首期接哪些渠道：仅服务台 widget，还是同时接企微？
5. 线索提升 CRM 时，归属人默认「当前操作人」还是「组织管理员指定」？
